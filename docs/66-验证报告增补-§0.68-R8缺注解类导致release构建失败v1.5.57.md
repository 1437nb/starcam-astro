# 验证报告增补：§0.68 R8 缺注解类导致 release 构建失败 —— v1.5.57 发版修复

## 一、问题（发版时发现）

v1.5.57 代码已推送（`e63894f`）但一直**没有发版** —— `apk/` 里最新只到 v1.5.55，
GitHub Releases 最新也停在 v1.5.55。补发时在构建服务器上执行 `assembleRelease`：

```
ERROR: R8: Missing class com.google.errorprone.annotations.CanIgnoreReturnValue
       (referenced from: com.google.crypto.tink.KeysetManager ...  and 52 other contexts)
Missing class com.google.errorprone.annotations.CheckReturnValue
Missing class com.google.errorprone.annotations.Immutable
Missing class com.google.errorprone.annotations.RestrictedApi
> Task :app:minifyReleaseWithR8 FAILED
```

## 二、根因

§0.66 为 API Key 引入 `EncryptedSharedPreferences`（androidx.security.crypto），
其依赖 **Google Tink**。Tink 的字节码引用了 `com.google.errorprone.annotations.*`
—— 这些是 **annotations-only 的编译期注解**，不随 Tink 的运行时依赖一起发布。

R8 在 release 构建的 "Missing classes" 检查阶段把它们当**致命错误**（而非警告），
于是 `minifyReleaseWithR8` 直接失败。

**爆炸半径**：v1.5.56 与 v1.5.57 都打不出 release 包。也就是说 §0.66 之后，
`assembleRelease` 一直是坏的，只是日常迭代只构建 debug（用户规则）所以没暴露。

另有两个连带事实需要记录：

1. **构建服务器上没有签名密钥**。§0.66 把 `keystorePropsFile` 从硬编码的
   `C:/dev/starcam-keystore.properties` 改成「环境变量 → -PkeystoreProps →
   `~/.starcam/…`」三级查找后，服务器上三级都不命中 → `signingConfig = null`
   → release 产物**未签名**。
2. **GitHub 上的 v1.5.55 release APK 是未签名的**。本机 `apksigner verify` 报
   `DOES NOT VERIFY / Missing META-INF/MANIFEST.MF`，APK 里也没有
   `APK Sig Block 42`；对照 v1.5.53/v1.5.49 的 release 包都验证通过（v2 scheme）。
   未签名 APK 无法在 Android 上安装 —— 这是个既存缺陷，本次一并修正。

## 三、修复

`code/app/proguard-rules.pro` 追加 R8 自动生成的 `missing_rules.txt` 内容：

```proguard
-dontwarn com.google.errorprone.annotations.CanIgnoreReturnValue
-dontwarn com.google.errorprone.annotations.CheckReturnValue
-dontwarn com.google.errorprone.annotations.Immutable
-dontwarn com.google.errorprone.annotations.RestrictedApi
```

这些注解只参与编译期静态检查，对运行行为无影响，忽略是安全的。
（R8 在失败时会把建议规则写到
`app/build/outputs/mapping/release/missing_rules.txt` —— 以后遇到同类失败直接照抄该文件。）

**签名**：把 `starcam-release.jks` 与 `starcam-keystore.properties` 放到构建服务器的
`~/.starcam/`（权限 600），正好命中 `build.gradle.kts` 的第三级默认查找路径，
无需改代码、无需在命令行传密钥。

## 四、构建服务器上的两个坑（供后续发版参考）

### 4.1 R8 堆内存

服务器仅 1.8GB 内存。R8 用默认/800m 堆会 `OutOfMemoryError: Java heap space`
（**Java 堆溢出，不是物理 OOM** —— 与编译期那次被内核 OOM-kill 不同）。
实测可用配置：

```bash
-Dorg.gradle.jvmargs="-Xmx1400m -XX:MaxMetaspaceSize=400m -XX:+UseSerialGC"
```

R8 是单线程任务，`UseSerialGC` 省内存。此配置下 release 构建 **3m13s 成功**。

### 4.2 全量重编译会 OOM

`testDebugUnitTest --rerun-tasks` 会触发全量 Kotlin 重编译，1.8GB 机器上
被内核 OOM-kill（`dmesg` 可见 `Out of memory: Killed process ... (java)`）。
**分两步**：先让编译产物就绪，再跑测试（复用产物，不重编译）。实测
测试阶段仅 45 秒、145 项全绿。

## 六、GitHub Releases 的两条实测约束（本次踩到）

### 6.1 资产名**不能含非 ASCII 字符**

GitHub 的 release asset 上传接口会**静默把非 ASCII 字符替换成 `.`**：
`StarCam-v1.5.57-索引内存可归还-release.apk` → `StarCam-v1.5.57-.-release.apk`。
隔离测试（同一接口连传两个名）确认不是本地编码问题：

| 请求的 name | 服务端实际存的名字 |
|---|---|
| `StarCam-test-ascii-release.apk` | `StarCam-test-ascii-release.apk` ✅ |
| `StarCam-test-中文名-release.apk` | `StarCam-test-.-release.apk` ❌ |

**这与「APK 命名铁律」不冲突**：铁律要求的是**本地产物**文件名带更新内容简述
（由 `updateDesc` 驱动），中文照常有；GitHub 资产名沿用历史惯例用英文 slug
（对照 v1.5.55 `native-extract-fix`、v1.5.53 `overlay-align-fix`）。
版本号与更新内容在 Release **标题**与**正文**里体现。

### 6.2 上传必须用 `http.client`，不能用 `urllib.request`

`urllib.request` 会把 URL 里已经百分号编码的 `%E7%B4%A2…` 再按 latin-1 处理一遍，
中文照样被吞。新增 `tools/gh_upload_asset.py` 用 `http.client` 直接拼 raw path
绕过该问题（同时对已存在的同名资产做「先删后传」的覆盖语义）。

用法：
```bash
python tools/gh_upload_asset.py <tag> <apk> [<apk> ...]
```

## 七、遗留

- **v1.5.55 的 release APK 是未签名的**，已在 GitHub Releases 上。建议要么重发一个
  签名包覆盖，要么在 release notes 里提示用户改用 debug 包 / 等待新版。本次
  v1.5.57 是签名包，用户升级到 v1.5.57 即可绕开该问题。
- 构建服务器上的签名密钥属**敏感文件**，未入库（`~/.starcam/`，600 权限）。
  换机器发版时需重新放置，否则又会静默产出未签名包 —— 建议后续在
  `assembleRelease` 后加一道「产物必须已签名」的校验，避免静默失败。
