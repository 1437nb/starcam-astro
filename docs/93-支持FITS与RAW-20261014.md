## 1. 目标与取舍

目标用户手里有两类"专业"素材：望远镜/冷冻相机的 **FITS**（`.fit/.fits/.fts`）与相机的
**RAW**（`.cr2/.nef/.arw/.dng/.orf/.rw2/.raf`…）。两者都能拍星空，但既有链路只认
JPEG/PNG（`BitmapFactory`）。本批把这两类接进「导入 → 解码 → 显示 → 求解」整条链。

**取舍（有意为之）**：

| 格式 | 做法 | 为什么 |
|---|---|---|
| FITS | **纯 Kotlin 解码器**（自研，无依赖） | FITS 结构简单（2880 字节块头 + 大端数据）；自研可离线、可 JVM 单测、与既有 Python 参考实现口径可逐点比对 |
| RAW | 只取**内嵌预览 JPEG**（相机 ISP 渲染过的），不碰传感器原始数据 | 解原始数据要引 libraw/rawspeed（交叉编译 + 授权 + 体积 + F-Droid 合规）；而本 APP 的既有链路（JPEG→提星→匹配）正好直接吃预览，预览的星点质量对"认出哪片天"完全够用。将来要做测光/叠图再引 libraw 不迟 |

**明确不做**（会让上层明确报"读不出图"，不静默失败）：压缩 FITS（`.fits.fz`，Rice/HCOMPRESS）、
FITS 表格 HDU（BINTABLE，本就不是图像）、RAW 的传感器线性数据。

## 2. FITS：`util/FitsImage.kt`

### 2.1 与参考实现**逐条对齐**（关键纪律）

`tools/convert_narrowfield.py` 是本仓库把 FITS 转成真值台 `.gray` 的实现，既有窄场/中场
真值台（`NarrowFieldRegressionTest` / `TieredCatalogTest`）用的就是它的产物。设备端如果
口径不一致，同一张 FITS 在手机上与在回归台上就会给出**不同的星点**（最坏：上下颠倒，
匹配必失败）。因此逐条对齐：

1. 数据按**大端**读（`>f4` 等）；
2. 行序**自下而上 → 翻转**成自上而下；
3. NaN/±Inf → 0；
4. 拉伸：**1.0% 与 99.5% 分位**线性映射到 0..255 后截断（与 `numpy.percentile` 线性插值同口径）；
5. BITPIX 8/16/32/-32/-64，且应用 `BSCALE/BZERO`。

**实测验证**（验证机，31 张真实 FITS）：与参考 `.gray` **逐点最大差 ≤ 0.00005**
（float32 舍入级）—— 见 `FitsNarrowFieldTest` 的 `FITS-REAL` 输出。

### 2.2 兼容性细节

- **多 HDU**：主 HDU 无数据（`NAXIS=0`）时向后扫描第一个 `NAXIS=2` 的扩展 HDU
  （不少望远镜产品把图像放扩展里）；
- 头部解析容忍：`END` 之前的多块头、引号内斜杠（`DATE-OBS = '2024/01/01'`）、
  FITS 的 `D` 指数（`1.5D-3`）、引号转义（`''`）；
- **降采样**：长边超过上限（生产用 2200）时按**整数倍面积平均**（与 `BitmapFactory`
  的 `inSampleSize` 同语义），既不放大噪声也省内存；
- 全平场（无对比度）走 min–max 兜底，避免整幅变 0。

### 2.3 元数据 → 求解先验（FITS 的"EXIF"）

`FitsMeta` 抽出对求解有用的头部字段，接到既有先验机制上（**与 EXIF 同一条闸门**）：

| FITS 头 | 用途 |
|---|---|
| `CDELT1/2 × NAXIS` | **视场**（度）→ `StarSolver.readFovDeg` 的"可信视场"（§0.103：>45° 宽场跳过深域重试） |
| `DATE-OBS` | 拍摄时刻（FITS 约定即 UTC）→ 太阳系天体标注、天顶先验 |
| `SITELAT/SITELONG`（或 `LATITUDE/LONGITUD`） | 观测站经纬度 → 天顶先验 |

一条**刻意的例外**：FITS **不做"当前定位兜底"**（`needsLocationFallback` 对 FITS 直接
返回 false）。望远镜素材的拍摄者在观测站，用手机当前位置去标注天文台拍的照片，
比不标更糟。

### 2.4 接入点：一处分派，九处受益

`ImageUtils.decodeSampledBitmap` 按扩展名分派（FITS / RAW / 其余走原路径），
因此**批量识别、结果页、缩略图（历史/相册/演示）、上传压缩、原生引擎取样**这些
既有调用点全部自动获得支持，无需逐处改动。FITS 没有位图概念，解码后合成
ARGB_8888 灰度位图供显示/渲染/取样；8 位量化发生在**拉伸之后**（先浮点拉伸再取整）。

## 3. RAW：`util/RawPreview.kt`

### 3.1 提取策略（三级）

1. **TIFF IFD 走查**（TIFF 系 RAW 全覆盖）：
   - `JPEGInterchangeFormat(0x0201)` + `Length(0x0202)` —— CR2/ARW/NEF 常见；
   - `Compression(0x0103)=6/7` 时 `StripOffsets(0x0111)` + `StripByteCounts(0x0117)`（多段拼接）；
   - `SubIFDs(0x014A)` 递归 —— 不少机型把预览放子 IFD；
   - 大端/小端都支持；按"能切出完整 JPEG（SOI…EOI）"校验后再比大小取最大。
2. **非 TIFF 容器兜底**：单遍线性扫描所有 `SOI…EOI` 对，**用栈配对嵌套**
   （JPEG 里嵌 EXIF 缩略图的场景也取到外层大图），取最大。
3. 都失败 → 返回 null，上层照常报"无法读取照片文件"。

### 3.2 不按 EXIF Orientation 旋转（有意）

各家 RAW 的内嵌预览通常已是相机认为的"正"方向，而 TIFF 的 `Orientation` 标签语义与
外层 JPEG 的 EXIF 不完全一致 —— 二次旋转会把好图转歪。宁可原样。

## 4. 入口：Home 新增「FITS / 相机 RAW 文件」

系统照片选择器（`PickVisualMedia`）只认图片，选不到 `.fits/.cr2`，因此新增一个
**系统文档选择器（SAF，`OpenMultipleDocuments`）** 入口：

- 拷贝到缓存时**保留原文件名与扩展名**（解码分派靠扩展名）—— 新增
  `ImageUtils.copyUriToCacheKeepingName`；
- 文件名做**净化**（去掉路径分隔符、非 ASCII 可打印字符一律替换），防 `../` 越界写入；
- 多选时沿用既有批量识别路径（`onPickImages`）。

## 5. 验证

| 项 | 结果 |
|---|---|
| `FitsImageTest`（9 项，CI 跑） | BITPIX -32/16、BSCALE/BZERO、NaN/Inf、行序翻转、扩展 HDU、元数据、D 指数、降采样、非 FITS 拒绝 |
| `RawPreviewTest`（8 项，CI 跑） | 小端/大端 TIFF、SubIFD、条带、非 TIFF 兜底、嵌套取外层、无 JPEG 返回 null |
| `FitsSolveEndToEndTest`（2 项，CI 跑） | 合成星空 → 写 FITS → 解码**逐点等于**独立算出的期望（最大误差 0.0000）→ 走生产编排求解：`ra=83.01 dec=-4.98 fov=20.0 inliers=107 sep=0.02° err=0.0%`（渲染参数 ra=83.0/dec=-5.0/fov=20.0） |
| `FitsNarrowFieldTest`（2 项，验证机；素材不入库 → CI 跳过） | ① 31 张真实 FITS 与 Python 参考实现**逐点一致**（≤0.00005）；② 两条链（FITS 解码 / 参考 .gray）逐场**同结论** |
| 全量口径 | 本地 **255 项 / 38 类**，CI **238 项**（跳过 9 类 / 17 项） |

### 5.1 一个值得记下的观察（不是本批的缺陷）

用**生产口径**（检出上限 100、带 WCS 视场提示）跑同一批素材时，密场 15° 的
`cas15/cyg15/sgr15/sco18` 解不出，`summer20` 还出现一个浅域尺度坍缩假解
（报视场 141°、6 内点）。而既有真值台的口径（检出 64、不带提示）下这些场次是
**既有能力边界内的已知状态**。两个变量（星点上限、视场提示）都会改变匹配结论 ——
属**匹配器调参**话题，不该混进解码链验证，也不在本批范围内（已在
`FitsNarrowFieldTest` 的注释里写明）。留作后续单独评估。

## 6. 残余风险

1. **RAW 的端到端（解码→显示）未在设备上实测**：单元测试覆盖了"从容器里取对字节"，
   之后走的是与 JPEG 完全相同的既有路径；但真实 CR2/NEF/ARW 的预览尺寸差异、
   大图 OOM 表现需要真机确认；
2. FITS 的兼容性只覆盖了本项目手上的素材（SBIG/ASI 风格 + DSS 下载图，BITPIX=-32 为主）：
   `BITPIX=16`、多 HDU、`BSCALE/BZERO` 仅由合成夹具覆盖；
3. 超大 FITS（例如 4096×4096 以上）的解码耗时与内存未实测（分位拉伸要对全像素排序，
   实测 1.44M 像素约百毫秒量级；更大图会线性增长）。
