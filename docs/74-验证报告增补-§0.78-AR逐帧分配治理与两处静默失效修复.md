# §0.78 AR 逐帧分配治理与两处静默失效修复

> 承接 §0.77。本批处理代码审查报告（`72-代码审查问题清单-20260922.md`）里
> **A6、A7 两条历史欠账**与 **B10、B11 两条「功能实际不可用」**。
> 与 §0.77 不同，这一批**会改变行为**（渲染路径与导出路径），因此逐项写清契约与风险。

---

## 一、A6：AR 逐帧分配治理

审查结论是：`CameraScreen` 注释里「每帧零新建对象」的硬性要求，在它**下游的三个
渲染模块内部**实际已被打破。按「分配量 × 改动风险」排序处理如下。

### A6a 渲染层（`LayeredRenderer.kt` / `MessierCatalog.kt`）

| 原状 | 处置 |
|---|---|
| `draw()` 每次调用新建 **9 个 `Paint`**（约 60fps → 540 个/秒，构造带 native 开销） | 收敛为 `RenderPaints` 的 **3 个**（描边/文字/填充），draw 内只改属性 |
| `MessierCatalog.label(isEnglish)` 每次调用拼字符串（110 天体 × 60fps ≈ 6600 String/秒） | 改为 `labelZh` / `labelEn` **预生成**（构造时算一次） |
| `shrink()` 每条连线返回新 `FloatArray(4)`（典型 50~200 条/帧） | 新增 `shrinkInto(out, ...)` 写入调用方缓冲；`shrink()` 保留并改为它的包装 |

**为什么 `RenderPaints` 由调用方持有、而不是放进 `LayeredRenderer` 这个 object：**
`draw()` 会同时被主线程（Compose 预览）与 IO 线程（保存相册 / 查看器的位图渲染）调用，
`Paint` **不是线程安全的**，共享一份会互相踩。Compose 侧用 `remember { RenderPaints() }`。

### A6b 姿态链（`DeviceOrientationTracker.kt` / `QuatMath.kt`）

`predictedPointing()` 是 AR 画布的逐帧入口（`CameraScreen` 的绘制 lambda，
经确认**只在主线程调用**），原实现每帧：

| 原状 | 处置 |
|---|---|
| `QuatMath.quatToMatrix(q)` → 每帧一个 `FloatArray(9)` | 新增 `quatToMatrixInto(q, out)`，写入复用 scratch |
| `new GeomagneticField(...)` —— 构造要读 WMM 模型，却在每帧路径上 | 按 **0.01° 网格 + 整点小时** 缓存（磁偏角每小时变化 < 0.1°） |
| `getBestLocation()` —— 内部先做 `hasPermission()`，即 **2 次 `checkSelfPermission` 的 Binder IPC**；姿态由传感器事件驱动可达 50Hz → 约 100 次跨进程调用/秒 | tracker 内加 **30s TTL 缓存**（位置本身由 `startListening` 在后台持续刷新） |
| `right/up/axis` 各一次 `clone()`（3 个数组/帧） | **就地旋转**，省掉 clone |

`right`/`up`/`axis` 自身**仍必须新建** —— 它们随 `DevicePointing` 交给调用方持有，
复用会被下一次调用覆盖。省掉的是 clone，不是这三个数组。

> 契约：三个入参必须是调用方现场新建的临时数组（`predictedPointing` / `computePointing`
> 均如此），`rotateBasisAroundUp` 会就地修改它们。

### A6c 投影层（`ArSkyProjector.kt` / `StarChartOverlay.kt` / `CameraScreen.kt`）

这是**最大的一笔**。`ArSkyProjector` 原本已经做过不少零分配优化（`visibleIdx`、
`ptScratch`、可复用的 `ProjectedSky` 容器），剩下的：

| 原状 | 处置 |
|---|---|
| 每帧逐颗 `new Star2D(...)`，可见星约 **2000 颗/帧**（12 万/秒） | 在 **`ProjectedSky` 容器上**新增 `starPool`：按 `entries` 下标复用 Star2D（池的归属见下文踩坑） |
| `out.stars.withIndex()` —— 每个元素分配一个 `IndexedValue`（约 2000/帧） | 改索引循环 `for (slot in out.stars.indices)` |
| A 矩阵 `floatArrayOf(9)` / `cam` `FloatArray(3)` / 校准 `c` `FloatArray(3)` | 全部改为 object 级 scratch 复用 |
| `CameraScreen` 每帧新建 9 个 Paint（经 `draw()`） | `remember { RenderPaints() }` 传入 |

**为此把 `StarChartOverlay.Star2D` 的 `x`/`y`/`visible`/`belowHorizon` 从 `val` 改为 `var`**
（`entry` 保持 `val`）。这是本批唯一的数据模型变更，契约写在类注释里：

> 池化对象**只在当前帧内有效**，跨帧持有其引用会读到下一帧的值。
> 结果页路径（`projectStars`）**不使用池化**，行为与从前完全一致。

安全性论证：AR 路径上 `out.stars` / `out.lines` / `out.labels` 都是**每帧重建**的
（`ProjectedSky.reset()` 会 clear），下游 `LayeredRenderer.draw`、`arHitTest`、
`constellationLabels` 都在同一帧内消费完 —— 且绘制与点击同在主线程，不会真正并行。

#### ⚠️ 踩坑：池的归属位置（第一版是错的）

第一版把 `starPool` 放在 `ArSkyProjector` 这个 **object** 上，全量单测直接失败：

```
ArSkyProjectorTest > correctionShiftsChartToCenter FAILED   (ArSkyProjectorTest.kt:138)
```

该测试比较**两次 `project()` 调用**的结果（有/无校准向量）：

```kotlin
val without  = project(...)                      // 拿到池对象引用
val withCorr = project(..., correction = ...)    // 同一批池对象被改写
distToCenter(without)                            // 读到的其实是第二次的值 → dWithout == dWith
```

正是 `Star2D` 契约里写的「跨帧持有引用会读到下一帧的值」—— 测试有效抓住了它。

**修正：池挂到 `ProjectedSky` 容器上**，而不是 object 上。于是：

- **同一个容器跨帧复用**（AR 的真实用法：`arSky` 由 `remember` 持有）→ 零每帧分配，目标达成；
- **不同容器互不干扰** → 语义与从前完全一致，上面的测试自然通过。

这条背后有个更一般的规律：**对象池的归属必须与「复用的生命周期边界」对齐。**
池挂在全局单例上，等于把「一次投影」的生命周期偷偷放大成了「整个进程」。

## 二、A7：结果页全分辨率位图移出主线程

`renderAnnotatedBitmap` 新建 2200px 级 ARGB_8888 位图（**≈14MB**）并跑一遍全星表投影。
问题在于它有**两套调用路径，一套对一套错**：

| 路径 | 原状 | 处置 |
|---|---|---|
| 「保存到相册」`SaveToGalleryButton` | 已正确 `withContext(Dispatchers.IO)` | 不动 |
| 点开大图 `StarPhotoOverlay.onTap` | **主线程同步合成** | 移到 `Dispatchers.IO`，回调里再打开查看器 |
| 查看器 4 个图层开关回调 | **主线程同步合成** | 统一走新增的 `rerender` —— IO 渲染 + **防抖** |

防抖（`renderingNew` 标志）解决的是另一个问题：全分辨率合成要几百毫秒，
快速连点图层开关会同时堆出多张 14MB 位图（原生内存峰值）。

**未做显式 `recycle()`**：`annotatedBitmap` 正被 Compose 持有并绘制，
回收时机无法可靠判定；错误回收会直接 `trying to use a recycled bitmap` 崩溃。
位图由 GC 管理，真正的风险是**并发持有多个**，已由防抖消除。
（若将来要在真机上进一步压峰值，正确做法是 `LaunchedEffect(bitmap)` 里延迟回收上一张，
而不是在赋值处回收。）

## 三、B10 / B11：两处「功能实际不可用」

### B10 CSV 导出在 Android 8/8.1 上必然失败

`HistoryStore.exportCsv` 在 API < 29 分支写
`Environment.getExternalStoragePublicDirectory(DIRECTORY_DOWNLOADS)` —— 写公共目录需要
`WRITE_EXTERNAL_STORAGE`，而 manifest 只声明了 `READ_EXTERNAL_STORAGE`（`maxSdkVersion=32`）
且没有运行时申请逻辑 → 必然 `SecurityException`，再被外层 `catch` 吞成「导出失败」。

**处置**：API 26~28 改写到 `context.getExternalFilesDir(DIRECTORY_DOWNLOADS)`
（免权限；Android 8/9 上该路径对文件管理器可见，与 `ImageUtils` 保存图片的做法一致）。
API 29+ 仍走 MediaStore 写入系统「下载」目录，行为不变。

### B11 自建本地 astrometry 服务不可达

`PlateSolveClient.isSecureServerUrl()` 明确接受 `http://127.0.0.1` 与 `http://localhost`
（为用户自建 astrometry.net 服务联调），设置页也引导用户填服务器地址。但 targetSdk 34 下
平台默认 `cleartextTrafficPermitted=false`，明文 HTTP 一律被拒 —— **代码承诺的这条通路
实际从未可用**，用户只会看到求解失败。

**处置**：新增 `res/xml/network_security_config.xml`，**只对回环地址**开放明文，
其余域名仍强制 HTTPS；manifest 的 `<application>` 加
`android:networkSecurityConfig="@xml/network_security_config"`。

> 刻意没有用 `android:usesCleartextTraffic="true"` —— 那会对全网开放明文。

## 四、本批未做（留待下一批）

按收益/风险比排序，以下项**本次刻意未动**：

1. **`CameraScreen` 绘制 lambda 里被闭包捕获的 5 个局部 `var`**（`addHit` 的
   `p1x/p1y/p2x/p2y/hitCount`）—— Kotlin 会装箱成 Ref 对象，约 5 个/帧。
   改法是用 `FloatArray(5)` 承载，但会牵连后续十余行取值代码，收益相对已修项很小。
2. **`OverlayScene` 每帧构造**（1 个对象/帧）—— 要改就得动它的字段可变性，
   而它是结果页与 AR 共用的类型，牵连面大于收益。
3. **HUD 字符串格式化导致整屏重组**：`pointingState` 以传感器频率（≈16Hz+）更新，
   每次都触发 `CameraScreen` 整体重组并重做两处 `String.format`。
   正确做法是把 HUD 抽成独立 composable 只读必要字段，属 UI 结构改动。
4. **`constellationLabels` 每帧一个 `HashMap` + 若干 List**（可见星座约 10~30 个）。
5. **`Line2D` / `Messier2D` / `Solar2D` 未池化**（50~200 / ≈16 / ≤9 个/帧）。
   `Line2D` 池化需要把它改成 `var a/var b` 并处理「端点不在 AR 星表内」的情形。

### 需要真机确认的

本批改动**没有任何离线测试能覆盖渲染与内存**（`Star2D` 池化只在 AR 实时路径生效，
结果页渲染不走池化，所以单测看不出来）。建议真机验证：

1. AR 星图是否正常（星点、连线、星名位置与改动前一致）—— 池化的核心风险点；
2. 点开大图与切换图层开关时是否还卡顿、快速连点是否稳定；
3. Android 8/8.1 上导出 CSV 是否成功（这是 B10 的验证面）；
4. 自建 `http://127.0.0.1` astrometry 服务是否能连上（B11 的验证面）。
