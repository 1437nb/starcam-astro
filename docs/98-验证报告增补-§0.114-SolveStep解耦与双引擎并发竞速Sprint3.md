## 1. 任务背景与问题分析

根据系统性弱点分析报告（`starcam_weakness_analysis.md`）：
1. **`StarSolver.solve` 单体函数耦合严重（§4.1）**：
   - 之前所有的星点提取、自研三角匹配、官方 native 先验盲解、官方全天盲解、官方降采样重试以及在线 Nova API 兜底全部混杂在单个 700+ 行的 `StarSolver.solve` 内部；
   - 难以独立编写单步单元测试，增加或调整某种求解算法需直接侵入主状态机。
2. **`ResultScreen` 承担求解生命周期与状态控制（§4.2）**：
   - 旧代码在 Composable `ResultScreen` 内通过 `LaunchedEffect` 直接发起长时间求解协程；
   - 状态逻辑、星点检测回调（`onStarsDetected`）、取消管理直接嵌入 UI 树，阻碍 UI 纯函数化并使测试与重用困难。
3. **串行接力耗时未能充分利用多核硬件（§2.2）**：
   - 官方盲解在有明确先验或合适视场下只需数秒，自研匹配在特定星野下仅需 0.1s~1s；但在串行模式下，若首选引擎遇到疑难天区未命中，必须等待其完整超时后才启动下一个引擎，导致总耗时恶性叠加；
   - 现代智能手机普遍配备 6~8 核 CPU 与 4GB~12GB RAM，完全有能力在非极端内存场景下支持自研引擎与官方引擎并发竞速。

## 2. 核心方案与实现

### 2.1 `SolveStep` 解耦架构（`com.starcam.astro.astro.steps`）
- **步骤接口与契约抽象**：
  - 定义 [`SolveStep`](file:///c:/starcam/code/app/src/main/java/com/starcam/astro/astro/steps/SolveStep.kt) 接口：`val name: String` 与 `suspend fun execute(ctx: StepContext): StepOutcome`；
  - `StepContext` 封装图片路径、视场先验、传感器/天顶指向先验、全局总预算死线 `deadlineMs`、求解会话 `session` 及取消令牌 `token`；
  - `StepOutcome` 规范化为三种结果：`Success(result, note)`、`Failure(reason, error, note)` 与 `Skipped(reason)`；
- **独立步进封装**：
  - [`LocalMatcherStep`](file:///c:/starcam/code/app/src/main/java/com/starcam/astro/astro/steps/LocalMatcherStep.kt)：封装 SEP 与 box-blur 星点提取、自研 8400+ 星表网格三角匹配与诊断；
  - [`NativeSolveStep`](file:///c:/starcam/code/app/src/main/java/com/starcam/astro/astro/steps/NativeSolveStep.kt)：封装官方 astrometry.net 0.97 引擎的三重求解策略（传感器指向先验、天顶指向先验、分段盲解）与 0.5x 降采样重试；
  - [`OnlineNovaStep`](file:///c:/starcam/code/app/src/main/java/com/starcam/astro/astro/steps/OnlineNovaStep.kt)：封装 nova.astrometry.net 在线 API 兜底解析。
- **流水线编排**：
  - [`StarSolver.solve`](file:///c:/starcam/code/app/src/main/java/com/starcam/astro/astro/StarSolver.kt) 精简为主调度器，负责构建上下文、生命周期打点与步骤编排。

### 2.2 `ResultViewModel` 解耦 UI 状态与业务逻辑
- **架构迁移**：
  - 创建 [`com.starcam.astro.ui.result.ResultViewModel`](file:///c:/starcam/code/app/src/main/java/com/starcam/astro/ui/result/ResultViewModel.kt)（继承自 `AndroidViewModel`）；
  - 将 `state: StateFlow<ResultUiState>`、`detectedStars: StateFlow<List<DoubleArray>>`、`detectedStarTotal: StateFlow<Int>` 以及 `SolveToken` 的持有移至 ViewModel；
  - 在 `viewModelScope` 中启动异步求解任务，当 ViewModel 销毁时，在 `onCleared()` 中自动触发 `solveToken.cancel()`，杜绝页面关闭后的后台线程泄露；
- **Composable 纯界面化**：
  - 精简 [`ResultScreen.kt`](file:///c:/starcam/code/app/src/main/java/com/starcam/astro/ui/result/ResultScreen.kt)，移除 ~120 行 `LaunchedEffect` 求解调度逻辑；
  - UI 仅保留声明式视图渲染，通过 `viewModel(key = ...)` 注入实例，重试与取消操作直接绑定至 `viewModel.retry(...)` 与 `viewModel.cancel()`。

### 2.3 双引擎并发竞速（Parallel Engine Racing）
- **准入安全判定（`canRace`）**：
  - 为防止低内存设备由于同时分配两套求解上下文引发 OOM，设置严格准入门槛：
    1. 用户在设置中启用了并发竞速（`parallelEngineRacing == true`）；
    2. 设备总内存 > 3GB（`totalMemMb > 3000`）；
    3. 系统未处于低内存警告状态（`!activityManager.isLowRamDevice`）；
    4. 仅限宽视场/全天盲解（FOV >= 15°），超窄视场大图不进行并发。
- **协程通道与快速取消机制（`raceSteps`）**：
  - 使用 `Channel<StepOutcome>(1)` 收集首个有效结果；
  - 为 `LocalMatcherStep` 和 `NativeSolveStep` 分别派生子令牌 `localToken` 与 `nativeToken`；
  - 启动两个并发协程执行步进；一旦任意引擎产生有效求解（`Success`），立即向 Channel 发送产物并由 `select`/接收端在 $<1\text{ms}$ 内取消落败方的子令牌，立刻释放其内部 CPU 资源；
  - 最终整体耗时降至 $\min(t_{\text{local}}, t_{\text{native}})$。
- **用户控制与设置项**：
  - [`SettingsRepository.kt`](file:///c:/starcam/code/app/src/main/java/com/starcam/astro/data/SettingsRepository.kt) 增加 `parallelEngineRacing: Boolean`（默认开启）；
  - [`SettingsScreen.kt`](file:///c:/starcam/code/app/src/main/java/com/starcam/astro/ui/settings/SettingsScreen.kt) 增加「双引擎并发竞速」切换开关与说明。
