## 5.1 立即可以做（纯代码/远端可验证）

1. **官方引擎 × 网络小图服务器复现（可选，低优先）**
   - 目标：让 apod4（34° 北斗）在服务器上被 solve-field 解出，形成"官方 vs 自研"同图对照。
   - 手段：`--uniformize`、提星参数（`--sigma`、`--no-remove-lines`）、更窄 scale 区间 + 更大 `--depth`。
   - 服务器 2 核算力是硬约束；若 3 次实验无果即归档（结论已在 04 §4.6 记录）。

2. **RealPhotoMatchTest 增强（中优先）**
   - 当前只读 `*.gray` 观察输出；可加"已知真值断言模式"（apod4 北斗 RA/Dec ±3°、FOV ±15%），
     让该测试进入 40/40 常驻防回归。
   - 素材已在 `/opt/realphotos`（含 `.gray`、CREDITS 真值对照表可写进测试注释）。

3. **官方引擎索引/引擎选项暴露到设置页（中优先，产品向）**
   - `SettingsScreen` 目前有 EngineMode；可增加"官方引擎限时/索引档位"选项，便于真机调参。

4. **疏散星团暗星区（M44）路线评估（中优先）**
   - 结论基线：919 亮星表（HIP ≤~5 等）在 M44 区域星稀少 → 自研引擎无法解。
   - 选项 A：不处理（官方引擎覆盖——但官方引擎依赖 GPS 先验或慢速盲解）；
   - 选项 B：星表扩到 HIP ≤ 7 等（约 9000 颗，三角形索引内存约 10 倍，需评估 APK 体积/构建内存）；
   - 选项 C：对疏散星团照片提示用户"请开启定位以加速识别"。
   - 建议先做 C + 文案，B 作为独立实验（用远端生成索引测内存/耗时）。

## 5.4 代码审查提醒（接手后先看这几处再动手）

1. `astro_bridge.c` 的线程轮询超时与 `solver_free` 正确性（涉及 .so，改动需重交叉编译，成本高）。
2. `LocalStarMatcher.votePairs` 的多线程合并（`key = photoIdx shl 20 | hip` 的位宽假设：photoIdx < 4096、hip < 2^20）。
3. `StarSolver.kt` 的时间预算分布（21s 先验轮 + 盲解分段 12s/16s + 在线兜底），调参会影响真实体验。
4. `StellarSolverNative.parseJson` 的 CD → WcsTransform 符号处理（第 11 坑）。
5. 文档与代码同步：`docs/验证报告.md` 是唯一权威记录，改动后更新 §0.x。
