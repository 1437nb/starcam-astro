## 1. §0.105 · EXIF GPS 时间解析在时/分/秒 < 10 时必败

> ⚠️ **2026-10-15 勘误（见 `docs/94`）**：本节的分析前提（`parseUtcEpoch` 收到
> `"22/1,30/1,15/1"` 原始分式形态）**与真机不符** —— androidx ExifInterface（1.3.7）
> 对标准 RATIONAL 三连返回的是格式化后的 `"HH:MM:SS"`，因此"59.5% 秒数失效"描述的
> 是一个不存在的输入形态；真机上的实际缺陷是**时分秒被静默当成 0（epoch 变当天零点）**，
> 与版次有关的完整对照见 `docs/94` §2。修复与回归测试也已按真实形态重做（§0.109）。
> 本节的代码修复方向（不再依赖字符串拼接的两位宽）保留，但其数值影响面的表述以此勘误为准。

### 现象与根因（已核实）

`§0.100` 把 `SimpleDateFormat` 换成 `DateTimeFormatter` 时漏掉一处**语义差异**：

```kotlin
val text = "$date $hh:$mm:$ss"          // hh/mm/ss 是 Int，内插不补前导零
LocalDateTime.parse(text, exifTimeFmt)  // 模式是 "yyyy:MM:dd HH:mm:ss"
```

`SimpleDateFormat` 默认宽容（`isLenient`），`"… 2:5:9"` 能解析；`java.time` 的 `HH/mm/ss`
要求**固定两位宽**，单数位直接抛 `DateTimeParseException`，被 `catch` 吞成 `null`。

**独立复现（纯 JDK，本机实测）**：穷举一天 86400 秒，旧写法只能解析 **35000 秒（40.5%）**——
即 **59.5% 的 GPS 时间整段失效**，与审计数字逐位吻合。失效后果：`parseUtcEpoch` 返回 null →
回落到 `DateTimeOriginal`（本地时区墙钟），天顶先验与太阳系标注静默降级；拍摄地与设备时区
不一致时还会拿错时刻（月亮每小时走 0.55°）。

**为什么一期测试没抓到**：`ExifPriorsTimeParseTest` 的用例全用 `22/1,30/1,15/1`（22、30、15
全是两位数），恰好绕过边界。

### 修复

日期与时分秒**分开组装**，从根上不依赖前导零（时间分量本来就是 Int）：

```kotlin
private val exifDateFmt = DateTimeFormatter.ofPattern("yyyy:MM:dd", Locale.US)
...
LocalDate.parse(date.trim(), exifDateFmt).atTime(hh, mm, ss).toEpochSecond(ZoneOffset.UTC)
```

`parseLocalEpoch` 保持原样（它的输入本来就是完整字符串）。

### 回归测试

`ExifPriorsTimeParseTest` 新增 `utcEpochParsesSingleDigitTimeComponents`（10 项 → 11 项）：
三个互不相同的单数位（8:5:9）、一位/两位混合（9:10:3）、整数写法与分式写法同值、
单数位秒（22:30:5）。期望秒值按"2024-08-12 日序数 225 → 1723420800"手算，不经 java.time 反推。

## 2. §0.106 · `release_indexes()` 对**正常在飞**求解 use-after-free

### 现象与根因（已核实 + 实测复现）

索引回收闸门原先只看 `g_leaked_threads`（**超时 detach** 的线程数），而**正常求解期间它是 0**
（只有超时让渡才 +1）。于是这条路径成立：

```
前台识别中（worker 正在 solver_run 里高频读 index_t*）
  → 系统 onTrimMemory(TRIM_MEMORY_RUNNING_LOW)
  → StarCamApplication.trimIndexCache() → StellarSolverNative.releaseIndexes()
  → release_indexes()：g_leaked_threads == 0 → 当场 index_free() 在用的索引
  → worker 读到已释放内存：段错误
```

触发点在 `StarCamApplication.kt`（前台低内存回调），恰恰是"内存紧张 + 正在识别"同时发生
——低端机最常见的场景。

### 修复（`astro_bridge.c`）

1. 新增 `g_active_solvers`：**当前持有索引引用的活跃 solver 总数**（正常在飞 + 已让渡）。
   在「挂索引」的**同一临界区**（`g_index_mutex` 内）+1 —— 这样 `release_indexes` 看不到
   "索引已挂、计数还没记"的窗口；
2. 递减与索引引用的最后一次使用同时发生：正常路径在 `solver_free(sp)` 之后；
   让渡路径由 worker 在 `solver_free(job->sp)` 之后（`job->counted` 标志标出"这笔账要随
   所有权一起转交"，直调 `run_with_timeout` 的调用方不会被误减）；
3. 闸门改为 `g_active_solvers == 0 && g_leaked_threads == 0`；
4. 顺手消掉审计指出的第二个窗口：泄漏计数**先记后移交**（CAS 失败即撤回），
   旧顺序在"CAS 成功但记账前被抢占"时会让计数短暂变负；
5. `indexCacheStats` 增报 `activeSolvers`（诊断用）。

### 主机测试（`bridge_host_test.c` 场景 5）

新增「正常在飞求解 vs 索引回收」，走**完整生产路径** `run_solver`（挂索引 → 定时求解），
而不是直调 `run_with_timeout` —— "谁该记账"只有整条路径测得出。桩里加了**在飞 UAF 检测器**
（`index_free` 清零存活标记，`solver_run` 睡眠期间每 5ms 轮询，观察到即置 `uaf_observed`）。

**A/B 实测**（同一份测试源码，只把闸门条件退回修复前）：

| 版本 | 场景 5 结果 |
|---|---|
| 修复前（只看 `g_leaked_threads`） | **3 项断言红**：`freed=1`（当场释放了在飞索引）、在飞检测器 `uaf=1`、回收后无法再回收 |
| 修复后 | 5 项全绿（拒绝回收 → 求解结束计数归零 → 放行回收） |

### 顺带：让主机测试进 CI（审计 §2.4）

- 新增 `code/app/src/main/cpp/test_stubs/`（6 个最小头文件替身，含配套 README 说明纪律：
  签名必须与上游一致、宏取值抄上游）；
- `tools/run_bridge_host_test.sh` 改为**优先真源码树 → 缺则回退仓库内桩**；
- CI `unit-test` job 增加一步 `Native bridge host test`（JDK 就绪后即跑，**<1 秒**，
  无 NDK、无 astrometry 源码树依赖）。

**`.so` 重编**：§0.106 改的是 `astro_bridge.c`，必须重编 `libstellar_solver.so` 才对
APK 生效。本机（构建服务器）重编并核验：`5,068,144 → 5,068,240` 字节，
md5 `1f4cbf62… → 7e3ee7bc…`，6 个 JNI 符号集合**逐字一致**，
`PT_LOAD` 4 段全 `0x4000`（16 KB 页要求）。

## 3. §0.107 · 诊断状态跨锁读 + 陈旧失败字段

### 3.1 LocalStarMatcher：留档改为随结果锁内返回

**问题（已核实）**：投票轮/打分轮数字是进程级 `@Volatile` 单槽，`StarSolver` 在
`match()` **返回后（已出锁）**才读 `debugVoteStats` / `lastMatchUsedFallback` /
`debugDeepRejectedReason` 等。批量识别两 worker 并发时，A 刚出锁、等在锁上的 B 立刻进入
并在入口清零/覆写这些字段 → A 读到 null 或 B 的数字（日志串台）。

**修复**：新增 `matchWithDiagnostics(...): MatchAttempt`（`result` + `MatchDiagnostics` 快照），
快照在 `solveLock` **内**取；`match()` 保持原签名（内部委托，行为不变）。
`StarSolver` 改读本次快照的三处：`usedFallback`、`deepRejectedReason`、失败摘要统计。

**顺带修正浅/深域口径**：失败摘要原先打的是单槽数字 —— 跑过深域重试后那是**深域**的数字，
摘要却与失败页的「浅域」块并列阅读。现改为优先用快照里的**浅域（主路径）**数字
（未涉深域时两者同值，非深域场景一字不变）。

`ResultScreen` 仍读全局字段（**保留是有意的**）：失败页只在单张流程打开，一次只有一个求解，
不存在串台；批量失败不经过它。

### 3.2 StellarSolverNative：失败诊断入口归零

桥只在 `star-extraction-failed` 时输出 `rc/gmean/gmax`；`no-solution`/`timeout` 的 JSON
没有这几个键，而解析用 `if (o.has(...))` —— 旧值会一直挂着，让后续失败日志打印**上一张
照片**的 `rc/gmean`。现在 `solveBitmapImpl` 入口先把四个字段清空。

### 回归测试（新增 `MatchDiagnosticsTest`，4 项，CI 照跑）

1. `深域跳过的原因随快照返回`：5 颗星 + 可信视场 76°（>45°）→ 必败输入走到闸门 →
   快照带「已跳过」原因、`usedFallback=false`、主路径数字非空；（用真实照片不行 ——
   它在浅域就解出来了，根本到不了闸门。）
2. `快照不被后续求解改写`：两次求解前后，第一次的快照逐字段不变（旧写法的病根）。
3. `并发两个求解的留档不串台`：两张照片（5031/5040）各带自己的期望留档串，
   2 worker × 6 轮并发，逐字比对；先跑单独基线并断言两个串**可区分**（否则测试无判别力）。
4. `备用表命中时快照置位`：5031 的真实检出表 + 100 颗同量级噪声（§0.88 真机形态）→
   主表解不出、干净备用表命中（实测 `inliers=12`）→ 快照 `usedFallback=true`。

## 7. 残余风险（如实记下）

1. 真机 `onTrimMemory` 触发路径**未在设备上实测**（主机测试覆盖的是同一段 C 逻辑；
   建议下次真机验证时看一次 `indexCacheStats.activeSolvers` 在识别中的读数）；
2. `ResultScreen` 读全局字段的窗口在"批量 + 失败页"组合下不可达，但**没有测试**钉住
   这个前提（如果将来批量也打开失败页，需要一并改用快照）；
3. 并发留档测试是**概率性**互斥证据（6 轮 × 2 worker）；它保证的是"修好之后不串台"，
   不能反证"旧代码必串台"（旧代码的结构性缺陷由 `matchWithDiagnostics` 的引入本身消除）。
