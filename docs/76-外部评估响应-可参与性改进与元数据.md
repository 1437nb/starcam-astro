# 外部评估的响应：可参与性改进（风险一/二）与仓库元数据

> 起因：2026-09-22 收到一份第三方《StarCam项目分析报告-合并版》。报告的技术评价
> 与工程质量评价都很正面，短板集中在「开放性」——项目在「为自己开发」与
> 「为社区开发」之间还没完成切换。
>
> 本文记录对其中三条的处理：**（一）单点维护与单工作区约束**、
> **（二）CI 测试覆盖结构性折扣**、**（四）仓库元数据缺失**。

---

## 一、风险（一）：单点维护与单工作区约束

### 报告的说法

> 工程外依赖（astrometry 静态库目录、NDK r26d、签名密钥）全部落在绝对路径上，
> 且不入库。结果是：仓库已经开源，但外部开发者即使拿到全部源码，也无法完成一次
> 完整的 release 构建。这会实质性抑制外部贡献——7 个 Star、0 个 Fork 的现状与
> 这种门槛不无关系。

### 核对后的结论：**门槛被高估了**

回到仓库逐项核对，实际情况是：

| 事实 | 依据 |
|---|---|
| 求解引擎 `.so` **已经入库** | `code/app/src/main/jniLibs/arm64-v8a/libstellar_solver.so` 被 git 跟踪 |
| Gradle **不参与** native 构建 | `app/build.gradle.kts` 里没有 `externalNativeBuild` / `ndk` / `cmake` 配置 |
| `cpp/astro_bridge.c` 只是**源码存档** | 改它才需要用独立脚本重建 `.so`，日常开发用不到 |
| 单元测试**不需要** native 库 | CI 在 ubuntu 上跑通过（x86 环境没有 arm64 `.so`） |

所以真实门槛是这样分层的：

| 参与方式 | 需要准备 |
|---|---|
| 读代码、改 Kotlin/JVM 逻辑、写文档或翻译、跑测试、**构建 debug APK** | JDK 17 + Android SDK 34，**无工程外依赖** |
| 改 native 桥接 `astro_bridge.c` | 另需 NDK r26d + astrometry.net 0.97 静态库 + cfitsio 3.47 交叉产物 |
| 打 release 包 | 另需签名密钥 —— **只有维护者需要** |

报告说的「无法完成一次完整的 release 构建」**是准确的**（release 确实需要签名密钥），
但由此推出「外部开发者无法参与」并不成立 —— 除了改 native 和发版，克隆下来就能跑。

### 实际缺口：**没有把门槛讲清楚**

真正的短板不是门槛高，而是**没有任何一份文档说明门槛在哪**：
`AGENTS.md` 是为 AI 助手写的（且「唯一开发目录」那段本就是防分叉约定，不是对外限制），
`build_so.bat` 只有 Windows 批处理 + 硬编码绝对路径。

**处理**：新增 `docs/75-外部贡献者指南与工程外依赖说明.md`，内容包括

1. 三种参与方式的门槛速查表（上表）；
2. 快速开始（clone → `local.properties` → `assembleDebug`）；
3. 工程外依赖清单与 `.so` 重建步骤 —— 含一份**跨平台等价命令**：
   原 `build_so.bat` 是 Windows 批处理且路径全写死，非 Windows 贡献者无法使用，
   指南里给出了对应的 bash 版本（NDK clang + 8 个静态库 + cfitsio 的完整链接行）；
4. **诚实标注的缺口**：`astrometry-local` 依赖目录是怎么从零产出的
   （astrometry.net 0.97 源码配置、cfitsio 3.47 交叉编译参数）**目前没有可复现脚本** ——
   依赖目录是被直接搬到本机的。指南把「需要什么」讲清楚了，「怎么产出」仍待补。

README 中英两版各加了一节「参与贡献」，指向这份指南。

## 二、风险（二）：CI 测试覆盖存在结构性折扣

### 报告的说法

> 真值回归台（宽场、暗星、窄场等关键修复的唯一保护）在 CI 中因素材依赖被跳过，
> 145 项对 150 项。这意味着仓库的最强保护网只在作者本机能生效，一旦作者环境变更
> 或素材丢失，回归能力将不可恢复地下降。素材不入库的决策（隐私与体积）本身合理，
> 但缺少替代方案（如合成素材生成器）作为 CI 侧的降级保护。

### 处理：补一层**合成素材**的降级保护

素材不入库确实是必要取舍（含私拍原图），所以方向不是把素材塞进仓库，
而是补一个**不依赖任何外部素材**的真值回归。

关键观察：`SyntheticMidFieldTest` 里的 `render()` **本来就是纯合成** ——
用星表按已知 TAN WCS 渲染灰度图（高斯 PSF + 可复现伪随机噪声）。
它之所以在 CI 里被跳过，是因为同类的**对照**与**投影自检**需要 DSS 实拍图。

**改动两步**：

1. **抽出共享渲染器** `SyntheticSkyRenderer`（测试工具，object）——
   把 `project` / `sigmaForMag` / `noise` / `render` 从 `SyntheticMidFieldTest` 中搬出，
   后者改为调用它。渲染逻辑一字未改，只是换了归属，避免两份实现漂移。
2. **新增 `SyntheticRegressionTest`**（3 项，纯合成，**不在** `skipPhotoTests` 排除列表里）：

| 用例 | 真值（渲染参数即真值） | 结果 |
|---|---|---|
| `wideField65Deg` | RA 30° / Dec 0° / fov 65° / 900px | SOLVED，中心偏差 0.02°，视场误差 0.2% |
| `midField20Deg` | RA 120° / Dec 45° / fov 20° / 700px | SOLVED，中心偏差 0.02°，视场误差 0.0% |
| `narrowField12Deg` | RA 200° / Dec −40° / fov 12° / 600px | SOLVED，中心偏差 0.01°，视场误差 0.0% |

渲染统一用 mag≤6.5（仓库星表最深档），让匹配器自己决定走浅域还是深域 ——
这才是生产路径的真实形态；窄场那条因此会触发深星表域兜底。
判定口径与 `SyntheticMidFieldTest` 一致（中心角距 < fov×0.25、视场相对误差 < 25%），
实测精度比容差高两个数量级。

### 它**不是**等价替代

这一点写在测试类的注释里，也写进 README：合成图是**理想素材** —— 星点干净、
无星云污染、无传感器缺陷。它验证的是「匹配管线在已知真值下能否解出」，
**替代不了**真实照片上的假阳性守卫（`apod1/2/5`、`pleiades`、`m44` 必须保持
UNSOLVED 那类断言），也暴露不出素材缺陷。它是一层降级保护，不是修复。

## 三、风险（四）：仓库元数据缺失

### 现状核对

| 字段 | 报告 | 实测 |
|---|---|---|
| `description` | 空 | **null** ✓ 属实 |
| `homepage` | 空 | **空串** ✓ 属实 |
| `topics` | 未提 | **已有 5 个**（android / astronomy / astrophotography / offline-app / stargazing） |

### 处理：**未能自动执行，需维护者手动**

两处受阻：

1. 本机 `git credential fill` 返回**空** —— 凭据管理器里没有 github.com 的 token，
   所以 `tools/gh_api_push.py` 那套凭据路径当前不可用；
2. GitHub 连接器没有「修改仓库元数据」的接口（只有 create / search / issues / PR 等）。

已把可复用的脚本收进 `tools/set_repo_meta.py`（幂等；description / homepage / topics
三项一次改完；凭据同样从 `git credential fill` 取，不落盘不打印），
并在其文档字符串里写明前置条件。

**待人工执行**（约 1 分钟，GitHub 仓库页右上角齿轮）：

- **Description**
  > 纯离线的 Android 星空识别与天文摄影标注应用：本地盲解天区坐标（astrometry.net 引擎 + 自研 8400+ 星表匹配），含 AR 实时星图
- **Homepage** → `https://github.com/1437nb/starcam-astro/releases`
  （项目无独立站点，指向 Releases —— 用户下载 APK 的入口）
- **Topics** → 在现有 5 个基础上补：`astrometry`、`plate-solving`、`star-catalog`、
  `ar`、`kotlin`、`jetpack-compose`
  （⚠️ topics 是**整体替换**语义，必须带上原有的 5 个）

或先交互式登录一次凭据，然后 `python tools/set_repo_meta.py`。
