## 1. 结论与证据口径

本轮整理 **10 项代码缺陷**，原判 P1 四项 / P2 六项；补核平台网络配置后，D04 调整为 P2，修正为 **P1 三项 / P2 七项**。另列测试、构建和文档方面的欠账。

- **生产函数复现**：直接编译当前 Kotlin 源码，在本机独立 JVM 中调用；未连接在线服务、未使用私人照片。
- **控制流 / 几何模型**：使用相同的协程结构，或生产 WCS 函数配合已知旋转几何，验证问题机制。模型耗时不是手机实测耗时。
- **静态确认**：能在现有调用链定位触发条件与遗漏，未声称已经在真机重现用户症状。
- **待验证风险**：与上述缺陷分列，不能算作已发生的崩溃、误解或数据丢失。

P1 表示应优先处理，P2 表示应安排修复；均不表示所有用户、所有输入必然触发。

## 2. 缺陷明细

### D01 — 取消与总预算没有贯穿到底层

位置：

- `code/app/src/main/java/com/starcam/astro/astro/StarSolver.kt:442`、`:447`、`:506`、`:518`、`:620`、`:672`
- `code/app/src/main/java/com/starcam/astro/astro/LocalStarMatcher.kt:1284`、`:1948`
- `code/app/src/main/java/com/starcam/astro/astro/StellarSolverNative.kt:363`
- `code/app/src/main/cpp/astro_bridge.c:154`
- `code/app/src/main/java/com/starcam/astro/astro/PlateSolveClient.kt:162`

存在三个断点：

1. `raceSteps` 为两路计算新建子 `SolveToken`，只靠每 100ms 轮询父 token 的协程传播取消；没有 `finally` 兜底。外层超时或页面退出取消 Job 时，轮询协程也随之取消，子 token 可能一直是 false。`withTimeoutOrNull` 自身不会把这个普通对象设为已取消。
2. 原生求解是同步 JNI 调用，没有求解句柄或取消入参。C 侧只在自己的时限到达时置 `quit_now`；取消协程或 `nativeToken` 无法终止正在运行的调用。`coroutineScope` 要等子协程结束，因此先拿到胜者仍可能等待原生败者。投票池任务也没有接收 token，`Future.get()` 可继续等待计算。
3. 在线客户端使用同步 `Call.execute()`，没有与协程取消绑定的 `Call.cancel()`。已有 30 / 90 / 180 秒连接、读取、写入超时，不等于当前剩余求解预算；用户取消后，在飞请求可能继续，取消也可能阻塞到该调用结束。

此外，`evaluateLocalSolve` 固定启动 10 秒原生复核，不接收当前 token 或剩余预算。

验证：与现有控制器相同结构的 40ms 超时模型返回约 **415ms**，子 token 仍为 false；30ms 胜者与 400ms 不可中断败者的模型约 **402ms** 才返回。它证明取消结构的缺口，未实际运行 Android / JNI 引擎。

修复方向：以求解为单位统一传递单调时钟 deadline 和取消信号；所有退出路径在 `finally` 中取消子 token / 投票 futures；为原生调用和 OkHttp Call 提供真正的中止机制。增加「胜者提前返回」「超时停止计算」「页面退出停止请求」的行为测试。

### D02 — FITS 流式头部修复没有覆盖整图解码

位置：`util/FitsImage.kt:81`、`:333`、`:356`、`:370`。

`readMeta` 已是流式读取，但显示图片走 `decode → readBytes → readGray → finish`。它先读取整个文件，再分配全分辨率 `raw`、`flipped`、排序副本和拉伸数组，最后才按 `maxDim` 降采样。`maxDim=2200` 限制输出尺寸，不能限制中间内存。

验证：现场生成 **6000×4000、BITPIX=16、48,003,840 字节**的合法尺寸合成 FITS，调用当前生产 `FitsImage.decode(path, 2200)`：

- `-Xmx128m`：`OutOfMemoryError: Java heap space`。
- `-Xmx256m`：同样 OOM。

一个全分辨率 float 数组已占约 96MB。单张结果页会把这类 Error 转成失败提示；批量外层只捕获 `Exception`，不能把 OOM 正常归入单张处理失败。因此不能把旧报告的「Header 防 OOM」视作整个 FITS 导入链已解决。

修复方向：按目标分辨率流式 / 分块读取像素；用抽样或有界直方图求拉伸分位数；减少翻转、拉伸的全图副本；在分配前检查像素数与预算。增加独立低堆大图测试。

### D03 — 在线 WCS 与批量 / 历史图片方向不一致

位置：

- `util/ImageUtils.kt:27`、`:109`、`:132`
- `astro/steps/OnlineNovaStep.kt:48`、`:85`
- `ui/batch/BatchScreen.kt:95`、`:115`
- `ui/result/ResultViewModel.kt:101`、`:225`、`:263`

普通图片解码未应用 EXIF 旋转；`compressForUpload` 却会通过 `rotateByExif` 旋转上传副本。因此在线 WCS 对应的是旋转后的图片。

单张首次在线结果正确使用 `result.displayBitmap`；但：

- 批量导出忽略该位图，用原始 `bmp` 绘制在线 WCS。
- 历史保存原始 `imagePath` 与在线 WCS；重开时重新解码原图，仅用 `rescaledFor` 缩放 WCS。

有 EXIF 旋转的图片会把不同方向的像素坐标系当成单纯尺寸变化，造成标注旋转 / 错位；90° / 270° 情况还会发生横纵轴错配。

验证：上传图 1500×2000、原图显示 2200×1650、EXIF 顺时针 90°，上传图点 `(500,400)` 逆旋转回原图应为约 `(440,1100)`。生产 WCS 的现有纯缩放路径得到约 **`(733.33,329.83)`**。这是几何验证，未发起真实在线求解。

修复方向：让 WCS 与图片一起携带方向 / 像素基准；批量使用引擎返回的显示位图，历史保存可重建同一方向的元数据或规范化图片。补 EXIF 6 / 8 的首次显示、批量导出、历史重开一致性验证。

### D04 — HTTPS 校验可被伪回环地址绕过

位置：`astro/PlateSolveClient.kt:321`。

`isSecureServerUrl` 用 `startsWith("http://localhost")` 和 `startsWith("http://127.0.0.1")` 放行 HTTP，未解析真正的 host。

生产函数实测均返回 true：

| 输入（保留为代码，均未访问） | URI 解析出的真正 host |
|---|---|
| `http://localhost.example.com/api` | `localhost.example.com` |
| `http://127.0.0.1.example.com/api` | `127.0.0.1.example.com` |
| `http://localhost@example.com/api` | `example.com` |

这些输入能通过应用函数，但仓库 `res/xml/network_security_config.xml` 对回环地址之外的明文 HTTP 仍有独立限制，标准 Android 环境会在请求阶段拦截。此前将函数反例直接推导为可公网明文外发的结论不成立；本项应按校验一致性问题处理，而非已证实的照片 / Key 泄漏。

修复方向：使用 URL 解析器，明确检查 scheme、host 和 userInfo；HTTP 例外只允许精确的回环主机。加入相似域名、用户信息段、端口等反例测试。

### D05 — AR 标定混用了不同时间的画面与姿态

位置：`ui/camera/CameraScreen.kt:428`、`:443`、`:454`、`:455`、`:475`、`:491`。

先提取画面并运行匹配，结束后才读取 `currentPointing` 和当前时刻，用旧画面的 `ra/dec` 与新姿态求 `deltaAz`，再写回航向偏移。中间没有画面对应的姿态快照，也没有移动量 / 解龄门禁。

例如匹配期间手机转动 20°，真实标定偏差为 0，算出的差值仍可能约为 20°；它满足目前 ≤45° 的准入条件。内点数高只能证明照片解可信，不能证明照片与当前姿态来自同一时刻。

修复方向：绑定帧时间戳、姿态与定位快照；解算期间移动超阈值时弃用该次标定。需要实体手机复测效果，不能仅凭代码推断实际跳动频率。

### D06 — AR 每帧零分配约束仍被统一绘制器打破

位置：`ui/camera/CameraScreen.kt:833` → `astro/LayeredRenderer.kt:117`、`:149`、`:262`、`:275`、`:418`。

Paint 与投影对象已复用，但每帧 `draw` 仍创建 `FloatArray(4)`、`occupiedBoxes`，星名路径还会 `filter + sortedBy`。每个标签的放置函数又创建四象限列表、Pair、边界盒及 `LabelPlacement`；`fontMetrics` 读取也有对象返回。

这是可从代码直接确认的分配，不是尚未证明的「可能分配」。尚未进行真机 allocation / frame timing 测量，因此不报告具体 GC 次数、帧率或卡顿幅度。`docs/106` 对投影端池化的修复不能覆盖此处绘制端的分配。

修复方向：把绘制 scratch 与占位盒池放入调用方持有的渲染上下文，复用排序索引和字体指标，四象限按标量遍历；增加稳定场景的分配与帧时间检查。

### D07 — 不同文件可能被上传去重误拦截

位置：`astro/PlateSolveClient.kt:61`、`:306`、`:311`。

`computeFileKey` 只调用一次 `input.read(buf)`，最多哈希文件前 16384 字节，再与总长度拼接。相同大小、相同文件头、后续像素不同的文件会得到同一键；文件流单次 read 也不保证读满缓冲区。

验证：生成两个 32768 字节文件，仅修改第二个文件第 20000 字节。当前生产函数返回相同键，而两文件内容确实不同。若二者在飞时间重叠，第二张会被错误提示为重复提交。

修复方向：流式读取到 EOF；测试必须包含「前缀相同、长度相同、后缀不同」的文件。

### D08 — 毫秒上传文件名无法隔离并发任务

位置：`astro/steps/OnlineNovaStep.kt:42`；并发入口 `ui/batch/BatchScreen.kt:151`。

所有在线步骤共享 cacheDir，文件名只有 `upload_<currentTimeMillis>.jpg`。两个任务同毫秒进入时会指向同一文件，后续压缩、读取和 `finally delete` 互相影响，存在上传错图或另一任务读不到文件的路径。

本项确认的是缺少唯一性保证；本次没有用两张真实照片复现冲突，不报告实际发生概率。

修复方向：使用原子创建的临时文件或求解唯一 ID，并让每个任务只清理自己拥有的文件。

### D09 — 竞速失败丢失更完整的诊断

位置：`astro/StarSolver.kt:498`、`:512`、`:519`、`:628`。

当前只保存 `firstFailure`，两路都失败就返回它。若原生引擎先失败、本地引擎随后返回包含 `diagStars`、总星数与 `graySnapshot` 的失败，后者会被丢弃。

调用方只能从返回值恢复失败现场，因此可能把「检出了星点但没匹配」显示为星点为空，并丢失可供重放的像素。诊断内容不应由哪路先失败决定。

修复方向：收集两路结果，合并引擎错误；本地星点和灰度等信息按来源保留。加入两种失败顺序及 Failure / Skipped 组合测试。

### D10 — 英文批量导出仍使用中文标注

位置：`ui/batch/BatchScreen.kt:115`；`astro/OverlayRenderer.kt:27`。

批量调用 `OverlayRenderer.render(bmp, solve, solarPositions = solar)` 未传 `isEnglish`；该参数默认 false。因此即使应用处于 English，输出图片的星座、星名、深空天体标签仍走中文分支。批量失败说明也还存在中文常量。

修复方向：明确给每次批量操作绑定语言快照，透传至绘制器并统一失败文案；使用与单张结果相同场景对照导出。

## 3. 待验证风险与工程欠账

这些项目不计入上述 10 项已确认缺陷，也不表示应该立即扩展产品范围。

1. **竞速结构化报告的并发写入**：两路 `ctx.copy` 共享同一个 `JSONObject report`，`SolveLogStore.addStep/setStars` 与 `writeSuccessLog` 对其修改没有共同同步；两路都接近成功时还可能各自写成功结论。磁盘日志有锁不等于 report 对象也线程安全。需增加并发报告完整性验证，或改成各步骤独立产出、控制器统一合并。
2. **真机验收缺口**：AR 视场、地平线贴合、移动时自动标定和渲染性能仍缺本轮实体设备验收。静态审查不能代替传感器与相机的现场验证。
3. **深域与密场**：PROGRESS 中深域门槛标定、未知 FOV 调度、银河密场检测污染等仍需针对性真值回归。本次未使用私人素材重测，旧报告数字不能冒充最新结论。当前 `allowDeepRetry` 已参考是否调度原生引擎，并非完全没有准入控制。
4. **测试保护不完整**：现有 40 类 / 308 项报告是此前执行结果，且采用 `skipPhotoTests=true`，并非全部私有照片回归。`canRace` 测试主要验证是否允许竞速；`SolveStepTest` 的预算测试是时间算式，不是超时中止行为。本项目 `src` 目前没有 `androidTest` 测试目录，设备 / UI 验证仍需单独补齐。
5. **native 从零构建未闭环**：`tools/build_so.bat` 链接工程外预构建 `.a`，不能独立完成其源码获取、校验、交叉编译与补丁复现。日常 Kotlin 修改可构建，但新机器不能只靠仓库从零重建原生依赖。
6. **文档与维护成本**：旧代码地图仍有 919 星 / 40 项测试等口径；README 主题介绍落后于当前四主题；PROGRESS 中旧审计已完成与旧阻塞项并存，易误导排期。`LocalStarMatcher` 约 2972 行、`CameraScreen` 1676 行、`ResultScreen` 1609 行，属于后续维护成本，不单独认定为功能错误。

以下属于已有明确决策的取舍：不投入 5° 以下手机场景外的窄场扩展；暂不预构建深域二进制索引；F-Droid 上架尚未完成。不要把它们重新包装成紧急代码缺陷。
