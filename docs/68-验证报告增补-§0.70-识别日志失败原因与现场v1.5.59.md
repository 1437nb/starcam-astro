# 验证报告增补：§0.70 识别日志 —— 失败原因与现场留存 v1.5.59

## 一、需求（开发者 2026-09-18 提出）

> 「能不能在 APP 加入日志功能，把解不出来的图的失败原因输出」

这个需求直指本项目**最大的效率瓶颈**：从 §0.43 起，
「用户说识别不了 / 开发机复现不出」反复出现，每次都要靠截图推断，
而 §0.64 已明确记录「从截图反推坐标不可靠」。

现有的 §0.64 调试转储（`dumpLocalFail`）只在 **debug 构建**写盘，
而用户装的是 **release 包** —— 这就是它从未派上用场的原因。

## 二、设计（三项要求由开发者确认）

| 维度 | 选择 |
|---|---|
| 形式 | **文件日志（可导出）+ 失败页显示摘要**（两者都要） |
| 范围 | **成功与失败都记**（成功记一行摘要，便于看成功率） |
| 版本 | **release 也启用** |

核心设计决策：

1. **release 生效** —— 去掉 `isDebugBuild` 门槛。这是与旧转储的关键区别。
2. **失败现场无损压缩** —— 1649×2200 的 float 像素数组原始 13.8MB，
   10 份现场就是 138MB，对手机不可接受。改 gzip 后实测 **2.0MB（14.5%）**，
   且无损，开发机解压后逐字节相同、重放结果不受影响。
3. **日志绝不干扰识别** —— 所有写入都包在 `try/catch` 里吞掉异常；
   滚动截断（512KB）与现场份数上限（10 份）都自动执行，避免占满存储。
4. **隐私** —— 只写应用自己的外部目录（`Android/data/<pkg>/files/logs`），
   不上传、不联网；日志内的照片路径**只留文件名**，不写完整路径。

## 三、实现

### 3.1 新模块 `data/SolveLogStore.kt`

两类产物：

```
files/logs/
├── starcam-log.txt              人类可读滚动日志（512KB 上限，超出截尾）
└── fail-20260918-013045/        失败现场（最多保留 10 份）
    ├── report.json              结构化报告（引擎轨迹 / 星点 / 判定）
    └── input.gray.gz            匹配器实际吃到的像素（gzip，无损）
```

`report.json` 字段：`logVersion / time / image(仅文件名) / width / height /
device / android / appVersion / steps[]（每步引擎的 outcome+detail+costMs）/
starCount / stars[[x,y,brightness]] / verdict / totalMs`。

### 3.2 接入 `StarSolver.solve()`

三个引擎分支全部接入，**成功与失败都记**：

| 位置 | 记录内容 |
|---|---|
| 官方引擎成功 | index / nmatch / logodds / 耗时 |
| 官方引擎失败 | **`nstars` / `rc` / `gmean`**（原生层留下）——判断「提星失败 vs 匹配失败」的关键 |
| 内置星表成功 | 内点数 / 像素尺度 / 耗时 |
| 内置星表失败 | **归因三分支**：提星失败 / 星点太少 / 星点够但未匹配（附投票轮与打分轮统计） |
| 在线识别成功 | 任务号 / 耗时 |
| 全部失败 | 落盘现场（report + gzip 像素） |

**新增观测量** `LocalStarMatcher.debugVoteStats`：逐星投票轮的
`work / votedStars / topVote / avgMargin`。此前这些数只在调试函数
`debugVoteTable` 内部可见，生产路径上没有 —— 而它正是区分
「真信号缺失」与「亮度阈值把关太严」的最直接证据。

失败归因文案示例（用户在结果页直接看到）：
```
星点 170 颗但未匹配；投票候选=work=20 votedStars=15 topVote=20 avgMargin=1.30；
打分轮=cand=25488 scored=25472 work=45 ms=3002（best=6 inFrame=84）
```

### 3.3 UI

**失败页**（`ResultScreen`）：新增可折叠「查看技术细节」区，展示检星数、
引擎轨迹、投票轮/打分轮统计；两个按钮：**复制**（诊断文本）、**复制日志路径**。

**设置页**（`SettingsScreen`）：新增「识别日志」区块 —— 开关（默认开）、
统计行（文件数/现场份数/占用）、刷新统计、清空日志、日志目录路径。

### 3.4 测试

新增 `SolveLogStoreTest`（**9 项**）：

- 摘要包含尺寸与星点数 / 无步骤时不渲染引擎段 / 摘要带上判定结论；
- `addStep` 在缺 `steps` 字段时自愈（`detail`/`costMs` 为 null 不写空字段）；
- 星点列表�� 200 上限约束，且 `starCount` 记**真实总数**（诊断更看重这个）；
- 报告骨架字段齐全且**不含完整路径**（隐私）；
- **gzip 往返**：写入格式 == 开发机读取格式，逐字节相同；
- **压缩率**：证明 gzip 确实显著压缩。

测试期需真实 `org.json` 实现（Android 内置的那个在单测里是「未实现桩」，
调用即抛 `not mocked`），故在 `testImplementation` 加 `org.json:json:20240303`
（只进测试 classpath，不进 APK）。

## 四、验证

| 项 | 结果 |
|---|---|
| 日志单测 | **9 项全绿** |
| 全量单测 | **154 项 / 16 类 / 0 失败**（原 145 + 新 9） |
| 照片回归 | apod4 SOLVED、南宁照 SOLVED（inl 25）、6 张假阳性全 UNSOLVED —— **日志接入未影响识别** |
| gzip 压缩率（真实照片实测） | 13.8MB → **2.0MB（14.5%）**，10 份现场仅 20MB |
| release APK | 16,536,942 bytes，签名证书 `b04a854f…`（与历史版本一致） |
| debug APK | 26,932,041 bytes |

## 五、怎么用（给用户）

1. 识别失败后，结果页下滑点「▸ 查看技术细节」→「复制」，把内容发给开发者；
2. 更完整的信息在**设置 → 识别日志 → 日志目录**：
   用文件管理器进入该目录，取 `starcam-log.txt` 与最新的 `fail-*` 文件夹；
3. 开发者拿到后，把 `input.gray.gz` 解压成 `.gray`（gunzip 即可，
   格式为 `int32 w + int32 h + float32 数组`），直接喂给本机测试台精确重放。

## 六、遗留

- **真机验证待做**：本机 Android 模拟器不可用（宿主机不支持虚拟化），
  日志的端到端行为（落盘、设置页开关、失败页复制）需在实体手机上确认。
- 日志默认开启。若用户反馈占空间，可在设置页关闭；份数上限（10）与
  压缩（14.5%）已把最坏情况控制在 20MB 量级。
