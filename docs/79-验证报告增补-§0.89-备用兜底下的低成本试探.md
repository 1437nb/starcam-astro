## 1. 真机复测（§0.88 之后）

开发者报告：**识别成功，但耗时 40 余秒**。修复有效，延迟不可接受。

耗时结构（用 §0.88 之前那次的失败页实测值推算，同一台设备）：

| 阶段 | 真机耗时 | 说明 |
|---|---|---|
| 主星表（SEP 177 颗）浅域打分轮 | **约 24.5 秒** | `cand=20016 scored=20000 ms=24564 CUT=cap`，1.22 ms/候选 |
| 备用星表（box-blur 约 32 颗）浅域 | 约 1 秒 | 候选仅两百余个 |
| 其余（解码 / SEP 提星 / box-blur 检测 / 索引） | 约 15 秒 | 与本次改动无关的固定开销 |

也就是说，**24.5 秒是在为一分永远解不出的列表付满额**：它在 §0.87 的上限下跑到 2 万
候选，但那份列表的真解候选根本生成不出来（§0.88 已证）。

## 2. 修复：有备用兜底时先做低成本试探

`matchLocked` 的顺序与预算（仅在调用方**传入备用星表**时生效，其余调用路径逐位不变）：

1. **主星表 · 低成本试探**：候选上限降到 `SCORED_PROBE_CANDIDATES = 2000`；
2. 试探失败 → **备用星表 · 完整预算**（它是兜底，给足）；
3. 备用也失败 → **主星表 · 完整预算**（回到未启用备用时的默认搜索）；
4. 都失败 → 深域重试（§0.77 闸门不变）。

实现方式沿用 `runtimeCatalogMag` 的约定：`runtimeScoredCap` 为对象级状态、由 `solveLock`
保证只在单次求解内改写；试探调用用 `try/finally` 恢复。统计串新增 `CUT=soft` 标记以
区别于硬上限的 `CUT=cap`（失败页可见）。

**为什么上限是 2000**：实测宽场照片的获胜位置都 ≤1116（5031: 218、5087: 1116），
2000 覆盖它们且真机仅约 2.4 秒；更靠后的获胜（如 5092 的 8730）改由第 3 步的完整预算
承担 —— 顺序变了，**搜索空间没有变小**。

## 3. 语义变化（需要知道）

备用星表若能解出，它的解**优先于**主星表的解被采用（原先主星表先跑到底，只有它失败
才轮到备用）。理由：备用列表更稀疏、候选更少，「保守检测器的解优先」比「先为可疑列表
付满额」更划算；两者的**验收门槛完全相同**（`SCORED_MIN_ALIGNED/RATE/IN_FRAME`、
`plausibleFov`、`skySpanConsistent`），不新增任何放宽。

整张照片从 ~40 秒降到 **~18 秒**。
