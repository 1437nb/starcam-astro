## 1. 审计要的是什么

> **现状**：本地 190 项，CI 175 项，缺掉的恰是最重要的真实照片回归。
> **但仓库已自带 12 张公开演示 JPEG**（`assets/offline_photos/`），因此可以：
> ① 从公开演示图生成固定灰度输入；② 给其中一部分写入公开真值；
> ③ 固化「必须正确解出的正样本」与「必须保持 UNSOLVED 的假阳性样本」；
> ④ **测试必须经过 STAR SOLVER → 检测器选择 → LocalStarMatcher 的生产编排路径**
> （不只是直接调 matcher）。
> **教训**：v1.5.73 那次「测试直接调 matcher，所以没发现 StarSolver 选错列表」的事故，
> 已把这个缺口演示得很完整了。

第 ④ 条是本条的**技术核心**，也是本次改动量最大的一处：那段编排逻辑当时藏在
`StarSolver.solve()` 的 Android 分支里，JVM 单测够不着。

## 2. 做了什么

### 2.1 抽出「选表」纯函数：`DetectorSelection`（生产与测试同一函数）

新文件 `code/app/src/main/java/com/starcam/astro/astro/DetectorSelection.kt`，
把原来内联在 `StarSolver` LOCAL_MATCHER 分支里的**选表决策**整段搬出来：

```
两张提星表（box-blur / SEP）
   → §0.72 重合率复核（<30% 撤销 SEP 可信）
   → 主表（= 喂给匹配器的那张，§0.97 首选便宜的 box-blur）
   → 备用表（主表浅域无解时匹配器再试的那张）
   → 界面预览表（「看得更全」的那张，**与匹配输入无关**）
```

**语义与抽取前逐条一致**（含诊断文案），抽取本身不改变行为；顺带删掉了一个
只写不读的 `boxBlurStars` 变量。

它是纯 Kotlin（不 import 任何 Android/原生库），所以生产路径
（`StarSolver → DetectorSelection.plan → LocalStarMatcher.match`）与 CI 测试
**走的是同一个函数** —— 这正是 §0.97b 事故（主表被预览表顶掉、备用表与主表成
同一对象）能被测试钉住的前提。

### 2.2 CI 侧真值回归：`OfflinePhotosTruthTest`（不依赖私拍素材）

| 组成 | 说明 |
|---|---|
| 素材 | 仓库自带的 12 张公开演示 JPEG（`assets/offline_photos/`，随 APK 发布，无隐私问题） |
| 灰度 | 测试内**现场解码**（`JpegLuma`），系数与 `LocalStarMatcher.bitmapToGray` 完全一致；打印 8 位灰度的 `sha8` 供像素漂移排查 |
| 真值 | `DemoPhotoTruth`（公开真值表，与开发机台 `Photo12RegressionTest` **共用一份**，来源见该文件：docs/06 §0.12 官方解 + 目视核实） |
| 检出 | `detectStarsGray(..., maxStars = 100)` —— **生产** `detectStars(bitmap)` 的默认值（刻意的，不跟着测试自己的默认 64 走） |
| 选表 | `DetectorSelection.plan(...)` —— 生产同一函数 |
| 匹配 | `LocalStarMatcher.match(primary, w, h, hint=null, fallbackDetected=plan.fallback, fovHintDeg=null)` —— 生产同一入口、同一参数形态 |

判定（`DemoPhotoTruth.classify`，与开发机台同口径）：
`TRUE-SOLVE`（天区 ±3°、视场比值 0.65~1.55）/ `FALSE-POSITIVE` / `MISS`。

断言三条：
1. **假阳性必须为零**（错误天区、尺度坍缩/膨胀 —— 硬线）；
2. **12 张必须全部 TRUE-SOLVE**（防「识别能力整体失效」）；
3. 选表接缝不许报「备用表与主表同一对象」、主表必须就是检出表本身（§0.97b 两个事故形态）。

### 2.3 选表接缝的单元回归：`DetectorSelectionTest`（11 项，纯合成列表）

把 §0.97b 事故的**全部形态**钉住：主表被预览表顶掉、备用表与主表同一对象、
SEP 重合率过低仍当备用、两表都不可用时没走「再算一次 box-blur」的重试、
重试结果 <5 颗时要透传（失败文案依赖它）。

### 2.4 备用星表机制在真实照片上的接缝回归

用 5031 的真实检出表（28 颗，亮度 17~510）做两组对照：

| 组 | 构造 | 实测 | 断言 |
|---|---|---|---|
| ① 同量级噪声 | 干净表 + 100 颗 150~500 噪声 | 头部重合 **5/30 = 17%** < 门限 | §0.72 撤销 SEP 信任 → `fallback` 必须为 null |
| ② 暗噪声 | 干净表 + 100 颗 15~60 噪声 | 头部重合 **10/30 = 33%** ≥ 门限 | SEP 被选为备用（`fallback === 干净表`）→ 带备用表匹配必须 TRUE-SOLVE |

组①的结果同时是一次**真值台发现**：主表被前排噪声挤坏时，§0.72 会连带撤销
SEP 的备用手册资格（重合率是对**主表前排**算的）—— 这是既定设计（宁可没有备用，
也不让不可信的列表参与），本次把它固定成断言，避免以后被「顺手优化」掉。

## 5. 没有覆盖到的（残余风险）

1. **私拍素材台仍只在本机/验证机**（`RealPhotoMatchTest` / `Photo12RegressionTest` /
   `NarrowFieldRegressionTest` / `MidField` / `TieredCatalog` / `Scored` / `Fallback` /
   `PhaseTimingBench`）——公开演示图替代不了它们的窄场/暗星/私拍视角覆盖；
2. **SEP 原生路径在 CI 不可达**（JVM 无 `.so`）：CI 跑的是「SEP 不可用 → box-blur」
   这条**真实生产分支**（真机原生库加载失败时走的就是它），但 SEP 自身的检出质量
   仍只由真机日志与开发机台保护；
3. **备用表「真的救回一次匹配」的 CI 侧构造**尚未做成：需要用真实像素造出「主表
   浅域解不出、但两表头部重合率仍 ≥30%」的形态，实测难以稳定构造（见 §2.4 组①），
   该机制目前仍由开发机台的 `FallbackStarListTest` 覆盖；
4. **StarSolver 的重构**由「接缝单元测试 + 编译 + 真值口径不变」保护，其特有的
   日志/回调/Android I/O 部分没有 CI 级行为测试 —— 下次真机验证（或发版验收）
   时应顺带看一遍识别日志里的「提星：首选box-blur(N颗)…」行是否与选表一致。

### 附：`JpegLuma` 为什么要反射取 `javax.imageio`

Android 单测**编译**用的是 android.jar（Android 的 API 子集），里面没有
`javax.imageio`（属 JDK 的 java.desktop，Android 没有）→ 直接 import 编译不过；
而单测**运行**在完整 JDK 上，ImageIO 就在那里。编译期取不到、运行期存在，故用反射，
并且**取不到就明确失败**（素材在仓库里，回归保护不允许静默跳过）。
灰度系数与 `bitmapToGray` 完全一致，保证测试喂给检测器的像素口径与生产相同。
