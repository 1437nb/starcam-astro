# 77 · 验证报告增补 §0.87 —— 打分轮确定性预算（真机 5031 识别失败的根因）

> 版本：v1.5.65（未发版；versionCode 85）
> 日期：2026-10-04
> 现象来源：开发者报告「广角欠曝照片 `1787670195031` 在真机上无法识别」
> 关联：§0.62（打分轮与时间预算）、§0.43（弱星轮救回 5031）、§0.64（提星量纲）、§0.72（SEP 阈值语义）

## 1. 现象与反差点

- 真机：照片 `1787670195031`（76° 广角、欠曝，提星 32 颗、最亮 498）**识别失败**；
  失败页显示「画面内星表星 715 颗 / 打分轮最优对齐 7 颗」。
- 本地：同一张照片的 2200px 解码复刻（`testdata/gray12/1787670195031.gray`）
  在回归台 **稳定解出**：`ra=13.77 dec=71.06 fov=75.6 inliers=16`，打分轮 `16/30 = 0.533`，
  真值窗口（13.4, 71.0, 76.0）内。

715 这个数字只能是**深域**（mag≤6.5）的：浅域星表总共 514 颗，inFrame 不可能超过 514。
即真机浅域轮失败 → 触发深域重试 → 深域打分轮把浅域的现场覆盖掉。**真正要回答的问题是
「真机浅域为什么失败」**。

## 2. 先排除的假设（全部用本地实测证伪）

| 假设 | 实验 | 结论 |
|---|---|---|
| 提星数上限（真机 100/200 vs 本地 64） | `detectStarsGray(maxStars=32…200)` 扫描 | 检测器只找到 **32 个 blob**，上限从未生效；全档 16/30 解出 |
| 星点太少（真机 SEP 只提到少量星） | 只用最亮的 k 颗星（k=6…32） | **8 颗即可解出**（inl=8）；6 颗才失败 |
| 重采样滤波差异（本地 LANCZOS vs 真机 Android bilinear） | 同一原图四种缩放（lanczos/bilinear/box/nearest） | 四种全部解出（inl=11~16） |
| 传感器指向提示（hint）把正确天区滤掉 | 读 `matchLocked` | 主浅域轮以 `pointingHint=null` 调用，hint 只作用于抢先匹配 |
| 本地解被官方引擎复核否决 | 读 `crossCheckAccept` | `native == null` 时**放行**（fail-open）；本例复核不会否决 |
| SEP 星表被噪声污染 | 注入噪声星（亮/暗两种量纲） | **暗噪声（低于真星）任意数量都无害**；只有与真星同量级的亮噪声 ≥60 颗才会打破解算 |
| 冷 JIT 使打分轮超时 | 覆盖预算为 0/30/100/300/1000ms | 见 §3 —— **这一条成立** |

## 3. 根因：打分轮的获胜候选**恒在候选序列末位**

### 3.1 关键测量

给 `LocalStarMatcher` 加临时探针（记录获胜候选被刷新时的已评分序号 `winAt`），
对 12 张演示照全量测量（`scored` 为实际评分候选数）：

| 照片 | 结果 | winAt | scored | 说明 |
|---|---|---|---|---|
| 4963 / 4974 / 4984 / 4998 | SOLVED | −1 | — | 未走打分轮（投票轮/弱星轮解出） |
| **5031** | SOLVED inl=16 | **218** | **218** | 打分轮解出，获胜在**末位** |
| 5040 / 5049 / 5068 / 5076 | SOLVED inl=48~50 | **218** | **218** | 同上 |
| 5057 | SOLVED inl=9 | **218** | **218** | 同上 |
| **5087** | SOLVED inl=25 | **1116** | **1116** | 同上 |
| **5092** | SOLVED inl=24 | **8730** | **8730** | 同上 |

**凡是走打分轮的照片（8/8），获胜候选都恰好是最后一个被评分的候选**；重复 6 次稳定复现。

原因：候选按「与照片边长的比值偏差」升序排列，而照片是 gnomonic 投影、
像素距离 ∝ tan θ，**真三角形的比值偏差最大**（同一失真见 §0.62）→ 真解排到末位。

### 3.2 后果

打分轮**没有任何余量**：只要候选串没跑完，就必然错过唯一正解。

§0.62 为此轮加的 **3 秒墙上时钟预算**（依据是「真解候选通常出现在序列前段」——
该前提在宽场照片上被本次测量证伪）于是把**设备速度**变成了识别成败的变量：

- 本机（暖 JVM）：218 个候选约 200ms，余量 15 倍，稳定解出；
- 真机（冷启动/解释执行/降频）：同一轮被 3 秒切断在 64/128/192 号检查点 → 浅域返回 null
  → 深域重试（同样被切断）→ 失败页显示深域数字。

**复现证据**：把预算压到 0（模拟慢设备）后，浅域失败、深域重试留下
`best=7 inFrame=733`——与真机报告的 **7 / 715** 吻合（完整跑完的深域是 `9/837`）。

这也解释了为什么 §0.64/§0.28 起就把 5031 列为「真机已知弱项」：
它一直是「快机器解得出来、慢机器解不出来」的边界照片。

## 4. 修复

`LocalStarMatcher.scoredRound` 的预算改为**确定性候选数上限**：

```kotlin
private const val SCORED_MAX_CANDIDATES = 20_000L        // 原：SCORED_TIME_BUDGET_MS = 3000L
private const val SCORED_HARD_TIME_LIMIT_MS = 60_000L    // 病态慢机兜底（正常不会触及）
```

- 结果与设备速度**无关**：快慢机器都评同样多的候选。
- 开销与原预算同级：2 万候选 ≈ 本机 3 秒。
- 上限取值依据：窄场抽测 12 张中候选数最大 47232、**获胜序号最大 19483**，
  2 万可覆盖全部实测获胜位置。
- 截断可见：统计串新增 `CUT=cap` / `CUT=time` 标记，失败页可直接看到是否被截断。
- 新增常驻调试字段 `debugScoredWinAt`（获胜候选序号），由
  `ScoredRoundBudgetTest` 钉住「跑完整串才能解出」这一性质。

### 5.1 唯一假解 `summer20` 是既有行为，非本次引入

窄场报告里的 `summer20`（真值 20°，解成 57°/偏离 52°）是尺度膨胀型假解。实测其
**获胜候选在第 1237 位**（打分轮 4467ms / 2 万候选），远早于旧代码的 3 秒截断点
（同口径约 13000 候选）—— 即**旧代码同样会走到这个候选**，与本次修复无关。
该照片候选总数 20016，恰好触到 2 万上限（截掉 16 个，不影响结果）。

### 5.2 上限取值的边界（已知）

- 实测获胜序号最大 **19927**（窄场抽样），距 2 万上限仅 0.4% 余量。
- 旧 3 秒预算在本机只允许约 13000 个候选，故 2 万上限**严格优于**旧行为，
  不会丢任何旧代码能解出的照片。
- 若将来出现获胜序号 > 2 万的照片，提高 `SCORED_MAX_CANDIDATES` 即可
  （代价是失败路径变长；这是刻意留的显式开关，而不是隐藏的设备相关性）。


## 6. 遗留与未验证

- **真机尚未验证**：本修复消除的是「结果依赖设备速度」这一确定性缺陷，逻辑上足以
  解释真机失败，但需要在真机上复测确认。
- **真机 SEP 星表本身的质量仍未直接观测**：本地无法运行 native SEP（arm64 `.so`
  不能在 JVM 加载；本机无 x86_64 astro 工具链、无可用 AVD）。
  若真机复测仍失败，需要识别日志里的提星行（`sep=σ 全图检出N颗/取最亮M颗…flux=最低~最高`）
  与失败页**逐轮**（浅域/深域分列）数字。
