# 外部贡献者指南与工程外依赖说明

> 本文回答一个问题：**想参与这个项目，我需要准备什么？**
>
> 背景：仓库已经开源，但工程外依赖（astrometry 静态库、NDK、签名密钥）全部落在
> 维护者本机的绝对路径上且不入库。这容易让人误以为「拿到源码也跑不起来」——
> 实际情况**不是**这样，三种参与方式的门槛差别很大，本文把它们拆开写清楚。
>
> 写这份文档的起因是 2026-09-22 的一份第三方项目分析报告，其中「单点维护与
> 单工作区约束」被列为高优先级风险；核对后发现真实门槛远低于报告描述，
> 但**确实缺少一份把门槛讲清楚的说明** —— 这就是本文。

---

## 一、门槛速查

| 你想做的事 | 需要准备 | 说明 |
|---|---|---|
| 读代码、改 Kotlin/JVM 逻辑、写文档或翻译 | **JDK 17 + Android SDK 34** | 无任何工程外依赖 |
| 跑单元测试 | 同上 | 纯 JVM 测试，不需要 native 库 |
| 构建 debug APK 装机验证 | 同上 | 求解引擎 `.so` **已随仓库提供**，不必重建 |
| 改 native 桥接 `code/app/src/main/cpp/astro_bridge.c` | 另需 **NDK r26d + astrometry.net 0.97 静态库 + cfitsio 3.47 交叉产物** | 见本文第三节 |
| 打 release 包 | 另需签名密钥 `.jks` | **只有维护者需要**；贡献者用 debug 包 |

一句话：**除「改 native 桥接」和「发版」之外，克隆下来就能编译、能跑测试。**

依据（可在仓库内自行核对）：

- `code/app/src/main/jniLibs/arm64-v8a/libstellar_solver.so` 被 git 跟踪，是预编译产物；
- `code/app/build.gradle.kts` **没有** `externalNativeBuild` / `ndk` / `cmake` 配置 ——
  Gradle 不参与 native 构建，`cpp/astro_bridge.c` 只是源码存档，改它要用独立脚本重建 `.so`；
- `local.properties` 是唯一需要本机准备的文件（指向你的 Android SDK），不入库。

---

## 二、快速开始

```bash
git clone https://github.com/1437nb/starcam-astro.git
cd starcam-astro/code

# 指向你的 Android SDK（该文件不入库，缺失会报 "SDK location not found"）
echo "sdk.dir=$ANDROID_HOME" > local.properties

./gradlew :app:assembleDebug        # 构建 debug APK（约 3 分钟）
./gradlew :app:testDebugUnitTest    # 全量单元测试
```

> `--rerun-tasks` 只在需要**确认基线**时加：不加时 Gradle 可能 `FROM-CACHE`
> 复用旧结果，输出 `BUILD SUCCESSFUL` 但根本没执行测试。

## 三、工程外依赖（仅改 native 桥接时需要）

`app/src/main/cpp/astro_bridge.c` 是 Kotlin 与 astrometry.net 引擎之间的 JNI 桥接。
改它之后必须重建 `libstellar_solver.so`。

### 3.1 依赖清单

```
<astrometry-local>/                  # 维护者本机为 C:\dev\astrometry-local
  ├── src/include/astrometry/        # astrometry.net 0.97 头文件
  ├── lib/solver/libastrometry.a     # 以下 8 个静态库（arm64）
  ├── lib/util/libanutils.a
  ├── lib/util/libanfiles.a
  ├── lib/util/libanbase.a
  ├── lib/catalogs/libcatalogs.a
  ├── lib/libkd/libkd.a
  ├── lib/qfits-an/libqfits.a
  ├── lib/gsl-an/libgsl-an.a
  └── cross/{lib,include}/           # cfitsio 3.47 交叉编译产物（libcfitsio.a + 头文件）

<android-ndk-r26d>/                  # NDK r26d（Windows 原生 clang 17）
```

### 3.2 一个关键实测结论

**Windows 版 NDK 的 clang 能直接链接 Linux ELF 格式的 `.a` 静态库**
（2026-09-17 实测）—— 不需要 WSL、虚拟机或 Linux 机器。

这也是项目能把构建从服务器搬回本机的前提。反过来，Linux/macOS 上用对应的
NDK 也应当成立（同族工具链），但**未经实测**。

### 3.3 重建步骤

Windows：直接用仓库内脚本。

```bash
tools\build_so.bat                    # 默认输出到 jniLibs/arm64-v8a/
tools\build_so.bat <自定义输出路径>
```

> 该脚本依赖三项硬编码绝对路径（NDK / astrometry-local / 桥接源码）。
> 脚本会在缺依赖时报错退出，但**不会**告诉你从哪里获取 —— 那是本文档的事。

Linux / macOS：脚本是 Windows 批处理且路径写死，需要自行翻译。等价命令：

```bash
NDK=<your-ndk>/toolchains/llvm/prebuilt/linux-x86_64/bin
CC=$NDK/aarch64-linux-android21-clang
AN=<astrometry-local>
CROSS=$AN/cross

# 1) 编译桥接
$CC -O2 -fPIC -DANDROID -pthread \
    -I"$AN/src/include" -I"$CROSS/include" \
    -c code/app/src/main/cpp/astro_bridge.c -o /tmp/astro_bridge.o

# 2) 链接（-z max-page-size=16384 是 Android 14 之后 16KB 页面的要求）
$CC -shared -o code/app/src/main/jniLibs/arm64-v8a/libstellar_solver.so \
    /tmp/astro_bridge.o \
    -Wl,--allow-multiple-definition \
    -Wl,-z,max-page-size=16384 -Wl,-z,common-page-size=16384 \
    "$AN/lib/solver/libastrometry.a" \
    "$AN/lib/util/libanutils.a" "$AN/lib/util/libanfiles.a" "$AN/lib/util/libanbase.a" \
    "$AN/lib/catalogs/libcatalogs.a" "$AN/lib/libkd/libkd.a" \
    "$AN/lib/qfits-an/libqfits.a" "$AN/lib/gsl-an/libgsl-an.a" \
    "$CROSS/lib/libcfitsio.a" \
    -lm -ldl -lz
```

### 3.4 诚实说明：这一步尚未脚本化

`astrometry-local` 是怎么产出的（astrometry.net 0.97 源码配置、cfitsio 3.47 的
交叉编译参数），**目前没有完整的可复现脚本** —— 依赖目录是被直接搬到本机的。
本文件把「需要什么」讲清楚了，但「怎么从零产出它们」仍需参考各上游项目的
构建文档自行完成。这是已知的缺口，欢迎补一份可复现脚本。

## 四、测试覆盖说明（重要）

CI（GitHub Actions）跑 **168 项**，比本地少 11 项：workflow 带
`-PskipPhotoTests=true`，跳过 6 个依赖**不入库的实拍素材**的测试类：

| 测试类 | 依赖 |
|---|---|
| `RealPhotoMatchTest` | `testdata/realphotos`（含私拍原图） |
| `Photo12RegressionTest` | `testdata/photos12` |
| `NarrowFieldRegressionTest` | `testdata/narrowfield`（DSS 巡天图 + 真值） |
| `PhaseTimingBench` | `testdata/gray12` |
| `TieredCatalogTest` | 同上 |
| `SyntheticMidFieldTest` | 同上（含 DSS 对照） |

素材不入库是**隐私与体积上的必要取舍**（含私拍原图），但代价是这 6 个类承载的
**真值回归**（74° 宽场、暗星、10°~20° 窄场 —— 历次关键修复的唯一保护）只在维护者
本机生效。

**CI 侧的补偿**：`SyntheticRegressionTest` 是一层**纯合成素材的替代回归** ——
用星表按已知 WCS 渲染合成图，不读任何外部素材，覆盖宽场与中场。它是本机真值
回归的**降级保护，而非等价替代**：合成图是理想素材，它验证的是「匹配管线在
已知真值下能否解出」，无法替代真实照片上的假阳性守卫与素材缺陷暴露。
