# App 优化空间与实施建议（2026-11-01）

> 当前代码：v1.5.90 / versionCode 110。
> 本轮按开发者要求只分析，未修改业务代码、构建 APK 或开展修复。
> 本文讨论体验、性能与工作流提升；已确认的正确性 / 安全问题单列于 `docs/111`。
> 收益与成本为代码层面的预估，不是手机实测结果或排期承诺。

## 1. 优化目标

优先改善四个用户感知最明显的环节：**选图进入识别更顺畅、等待更可理解、取景更稳定省电、结果更便于使用和分享**。

已有的历史 WCS 持久化、原生索引缓存、投票线程池复用、图层状态同步、后台导出及查看器重绘合并应保留。后续优化建立在这些能力上，不把已实现的功能重复列为待开发项。

## 2. 优化机会总表

| 方向 | 当前依据 | 建议 | 用户收益 | 成本 |
|---|---|---|---|---|
| 首页与首次使用 | 四个拍摄 / 导入按钮并列；未配在线 Key 用 errorContainer 展示 | 两个主入口，导入方式在入口内选择；在线配置使用中性说明 | 更容易开始使用，减少“必须配置 Key”的误解 | 低～中 |
| 导入与相册 | 选择器回调同步复制文件；缩略图每次进入格子解码；相册最多取 600 条 | 异步导入与进度、失败计数、有界缩略图缓存、按需分页 | 大图和多选响应更好，滚动 / 返回更连贯 | 中 |
| 识别等待与失败反馈 | 有阶段文案和星点展示，进度主要是字符串与无限动画 | 结构化阶段事件、已用时间、当前引擎与下一步；明确失败后的操作 | 用户更容易判断在做什么、值得等多久 | 低～中 |
| 图像处理与求解调度 | 同张图多次转灰度；双引擎竞速、批量 worker、投票池可能同时运行 | 求解级预处理复用，按设备统一分配 CPU / 内存，试验延迟启动第二引擎 | 减少重复工作、长尾耗时、发热 | 中～高 |
| AR 与相机 | vsync 持续重绘，预览匹配按核数每 5 / 8 秒运行 | 绘制缓冲复用、HUD 降频、按移动 / 温度 / 校准状态调整分析频率，提供省电档 | 取景更稳定，长时间观星负担更低 | 中 |
| 结果与导出 | 查看、求解、导出主要使用同一份最长边 2200px 的位图 | 按查看 / 求解 / 导出分辨率分层；聚合保存分享入口，增加标签密度档位 | 更清楚地看图，更方便发图，输出质量可选 | 中～高 |
| 历史与批量工作流 | 历史最多 50 条且支持 CSV；批量处理状态主要留在当前页面 | 先增加筛选、收藏、失败项重试与导出重试；长任务需求明确后再做持久队列 | 旧照片更好找，失败后少做重复工作 | 中 |
| 天象与暗适应 | 天象仅按 epoch 计算；已有四主题、Pro 参数与找星导航 | 按位置提供本地观测条件，返回前台刷新；相机普通 / 专业控件分层，统一夜视与无障碍验收 | 提示更贴近现场，夜间操作更省心 | 中～高 |

## 3. 具体分析

### 3.1 首页与使用门槛

代码依据：`ui/home/HomeScreen.kt:98`、`:180`、`:202`、`:219`、`:284`；`ui/I18n.kt:30`、`:41`。

首页同时给出拍照、原图相册、兼容相册、FITS / RAW 四个操作，再往下是天象、历史、演示、设置和 Key 状态。已有“原图优先”的合理策略，但用户仍需先理解多个导入路径的差异。

建议保留「拍照识星」「导入照片」两个显著入口。进入导入后默认使用原图路径，在失败、权限不足或用户明确选择时再呈现兼容路径；FITS / RAW 保留在同一入口内的专业选项。兼容方式仍有必要，应保留 EXIF 可能缺失的解释。

未配置 Key 当前使用红色状态，文案还引导先体验离线演示，容易使人误以为普通照片也不能离线识别。可改为「离线识别可用，在线辅助未配置」的中性状态，并在实际需要在线时说明启用条件。

冷启动也可一并优化：`StarCamApplication` 预热临时 `SettingsRepository`，首页另建实例，而 `apiKeyCache` 是实例字段。预热可能暖到系统层，但没有直接复用该实例的内存缓存；可改为应用范围的异步设置状态，并减少首屏对 Key 检查的依赖。未测量真实冷启动，不据此宣称有固定毫秒收益。

### 3.2 导入、缩略图与内存

代码依据：`HomeScreen.kt:98`、`:118`；`util/ImageUtils.kt:142`、`:163`；`ui/gallery/GalleryScreen.kt:107`、`:229`、`:303`；`ui/history/HistoryScreen.kt:270`。

选择器回调中直接逐文件复制，复制函数是同步流操作。可在用户选定后立即呈现导入状态，把拷贝和元数据读取放入 IO 任务，显示完成张数、失败张数和取消操作；尤其适合大 FITS / RAW 或多选素材。不能假设 URI 来自快速本地存储，云盘提供方也可能较慢。

相册与历史格子已有后台解码，但没有跨格子重建的有界缩略图缓存。建议按文件标识、修改时间、尺寸和方向缓存缩略图，对可见范围做有限预取；避免无限保存 Bitmap。相册当前只取最近 600 张，可按需分页和日期 / 相册筛选，减少“旧照片不见了”的疑惑。

内存应按任务阶段管理：预览用小图，求解用足够分辨率，导出按用户选择分配。FITS 大图的边界问题先按 `docs/111 D02` 处理，再评估高分辨率导出。

### 3.3 识别速度与等待体验

代码依据：`astro/steps/LocalMatcherStep.kt:49`、`:71`、`:158`；`NativeSolveStep.kt:63`；`LocalStarMatcher.kt:580`、`:591`；`ui/result/ResultScreen.kt:325`、`:420`；`data/StatsStore.kt:79`。

可以并行推进两类优化：

- **减少实际工作**：同一次识别为 SEP、box-blur、原生求解、诊断快照分别转灰度。单张 2200×1650 的 `FloatArray` 约 13.8MiB，转换还创建同尺寸 `IntArray`。建议按求解建立预处理上下文，复用灰度、元数据和需要的分辨率层级；先核实 JNI 对缓冲区的写入与所有权，不能未经确认就让可变数组跨线程共享。
- **让等待可解释**：当前已有引擎文案、星点与取消按钮，可进一步统一为“准备图片 / 检测星点 / 本地匹配 / 原生复核 / 在线排队”的结构化状态，展示已用时间和接下来尝试什么。阶段没有可靠完成比例时保留不定进度，避免伪造百分比。

并发应看整个 App，而不是单张图：普通批量有两路任务，每路可能启动双引擎，匹配器还使用投票池。可以给交互识别、预览标定和批量任务设统一资源预算，前台交互优先，批量按内存和设备温度退让。

可试验“短暂本地快路径后再启动原生”的竞速策略，或调整候选排序来改善困难照片的长尾；都需用固定真值集比较成功率、误报率和耗时分位数，不能只追平均耗时。取消与时限的正确性先按 `docs/111 D01` 补齐。

失败页已有三类星点数量提示。可增加具体操作，例如返回相机并打开曝光帮助、改用另一求解策略、只重试失败的阶段。星点数多不等于真实恒星多；模糊、拖线、背景过亮等质量提示只能作为辅助证据，不宜仅凭一个阈值直接拒绝照片。

### 3.4 AR 流畅度、耗电与相机控件

代码依据：`ui/camera/CameraScreen.kt:192`、`:295`、`:308`、`:443`、`:833`、`:1333`；`astro/LayeredRenderer.kt:117`、`:149`、`:262`、`:418`。

相机同时承担预览、传感器融合、星图绘制、定期星点匹配与曝光控制。建议明确三种运行需求：移动找星时优先跟手，稳定观测时降低不必要的后台计算，拍摄长曝光时减少与求解 / 动画竞争。

可先复用绘制缓冲与标签布局数据，再把数字 HUD 的更新频率与连续星图绘制分开；预览分析频率从“仅看 CPU 核数”扩展到画面变化、姿态稳定度、标定新鲜度、内存与热状态。提供省电 / 流畅档位时，需要测目标可见性与姿态延迟，不能只验证平均帧率。

FOV、航向标定、AR 开关、找星、EV、ISO、快门等控制已存在。可按普通与专业操作分层，并明确显示“传感器就绪 / 等待定位 / 已标定 / 需重新校准”等状态；当前“自动标定”还需先解决 `docs/111 D05` 的时序问题。

### 3.5 看图、标签与分享

代码依据：`ui/result/ResultViewModel.kt:148`；`ResultScreen.kt:607`、`:758`、`:815`；`ui/result/ZoomableImageViewer.kt:88`。

当前最长边 2200px 的处理图兼任结果显示与导出基图，查看器支持缩放与图层切换。可以让识别继续使用受控尺寸，同时为查看和导出设置不同质量档位；高分辨率输出需带内存估算或分块处理，并严格保持方向与 WCS 一致。

现有图层开关偏功能分类，后续可增加「简洁 / 标准 / 详细」标注密度预设、偏好记忆，以及字号 / 对比度设置。复杂背景下优先展示用户选择的目标与主要星座，再显示次级标签；它需要可见性验收，不能只以标签数量评价。

保存连线图、保存当前标注、原图对比等已有能力可归入清晰的导出 / 分享面板，提供输出预览、质量与图层选择，并直接调用系统分享。不是每次操作都需要新增独立按钮。

### 3.6 历史与批量工作流

代码依据：`data/HistoryStore.kt:29`、`:196`；`ui/history/HistoryScreen.kt:74`；`ui/batch/BatchScreen.kt:60`、`:76`、`:151`。

历史已经保存 WCS 并支持 CSV，优先增加日期 / 星座筛选、收藏和最近拍摄入口即可，不必先增加大而全的观测地图。缩略图可以按需要区分“已识别”与“原图不可用”等状态。

批量可优先补齐失败项重试、已识别但未导出的单独重试、逐张结果预览与共享图层设置；减少用户重新选择整批照片的次数。长任务需要后台恢复时，再引入持久任务记录与队列；在短批次需求下先完成页面内操作即可。

### 3.7 天象与夜间使用

代码依据：`astro/TonightSky.kt:55`、`:111`；`ui/home/TonightSkyCard.kt:57`；`ui/theme/Theme.kt:19`。

天象现在主要按时间与太阳距角给出通用窗口，可在取得用户允许的位置后加入本地目标高度、适合观测的时段及月亮影响，并明确区分通用建议与当前位置计算结果。首页回到前台或跨日时刷新，避免一份 `remember` 结果长期不变。

已有夜视红、深空蓝、纯黑、纯白四主题。下一步价值在统一验收：相机控件、弹窗、系统栏、等待动画与导出提示是否遵从夜视；放大字体、英文长文案、横屏和小屏下是否完整；删除、找星、图层等触控区域是否易于操作。这些需真机与实际布局检查，本轮未评定具体控件的对比度或触达合格率。

## 4. 建议先后顺序

1. **先改善高频操作**：首页在线状态与导入入口、异步导入、等待阶段与失败后的明确操作。成本相对小，也便于观察用户是否少走弯路。
2. **再处理主要资源开销**：重复图像预处理、全局并发预算、AR 绘制复用与分析降频。以同机同素材测量实际收益，正确性问题仍按 `docs/111` 单独验收。
3. **随后改善作品与复用**：结果标签密度、导出 / 分享面板、历史筛选、失败项重试。
4. **最后按需求扩展**：原图级导出、本地化天象、可恢复批量队列等较大工作项。

不改变既有“手机场景做到约 10°，不投入 5° 以下”的范围决策；深域预构建仍遵循暂不实施的决定。星表 / NGC 扩充和分发渠道扩展另行评估，不混入本轮性能优化排期。

## 5. 怎么判断优化有效

先在同一设备、固定公开素材和固定设置下建立基线：

| 环节 | 应记录的指标 |
|---|---|
| 冷启动与导入 | 到首屏可操作时间、选择完成到图片可见时间、主线程长任务 |
| 求解 | 冷 / 热启动耗时、各阶段耗时、中位数和 P95、成功率、误报率、取消后停止耗时 |
| AR | 帧时间分布、分配速率 / GC、HUD 延迟、移动时标定稳定性、固定时长的耗电与热状态 |
| 内存 | 单张 / 多张 / FITS 各阶段峰值、返回上一页后的存活对象与保留位图 |
| 用户流程 | 选图到结果所需操作数、失败后的重试完成情况、导出成功率 |

现有 `StatsStore.summary` 以成功率与平均耗时为主；可扩展本地统计与诊断，不引入未经授权的遥测。JVM 单测耗时不能充当真机求解或 AR 性能。

本轮仅检查代码路径与现有文档，没有新跑 App、基准测试或布局验收，因此不作“会快多少秒 / 省多少电”的量化承诺。实施前先测量对应环节，实施后用相同条件复测。
