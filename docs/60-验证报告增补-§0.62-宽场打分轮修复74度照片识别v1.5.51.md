# 验证报告增补：§0.62 宽场打分轮 —— 修复 74° 照片识别失败 v1.5.51

## 一、问题（用户 2026-09-13 报告，延续 §0.61）

小米 REDMI Turbo 5 Max 拍摄的 30s 星空照片（南宁，秋季四边形，EXIF 35mm 等效 26mm）
识别失败。对照 App（爱观天拍照认星 V6.6）1 秒内以 99% 匹配解出。

§0.61 已修复官方引擎侧的 FOV 先验错配；但**自研引擎（LocalStarMatcher）仍 UNSOLVED**，
当时归因为"内置星表在亮星稀疏天区覆盖不足（§0.43 已知项）"。本报告推翻该结论。

## 二、独立真值获取（推翻"星表覆盖不足"假设）

用 astrometry.net nova 解出同一张照片（API 上传 + 尺度过先验 45~75″/px）：

| 项 | 值 |
|---|---|
| 中心 | RA 0.676° / Dec 23.204°（秋季四边形） |
| 比例尺 | 65.344″/px @4096px → **121.6″/px @2200px** |
| 视场 | 74.4° × 55.8° |
| logodds / nmatch | 1806 / 424 |
| parity / index | +1 / 4116 |

把内置星表按该真值 WCS 投影进 2200×1650 帧，与本地检测星点比对：

```
mag<=3.5  inframe= 13  在 5px 内命中 12
mag<=4.0  inframe= 25  在 5px 内命中 24
mag<=4.5  inframe= 53  在 5px 内命中 52
mag<=5.0  inframe=103  在 5px 内命中 101
```

**该天区 mag≤4.0 有 25 颗星、检测到 24 颗** —— 星表覆盖完全充足，
"星表太浅"不是失败原因（此前 §0.43 的 7 颗估算只统计了索引域的一个子集）。

## 三、真实根因：逐星投票在宽场被伪三角形淹没

用真值 WCS 跑匹配器的 `debugVoteTable`，逐个照片星看真实星（trueHip）拿到多少票：

| 照片星 | 真 HIP 票数 | 该星最高票（伪 HIP） |
|---|---|---|
| P#1 | 9 | 14 |
| P#4 | 9 | 19 |
| P#6 | 6 | 17 |
| P#8 | 7 | 17 |
| P#10 | 11 | 19 |

**真 HIP 得 4~11 票，伪 HIP 得 14~19 票** —— 真对应全部被挤出。

量化投票管线对真三角形的通过率（照片星 14 近邻枚举、星表索引域 mag≤4.0）：

| 环节 | 真三角形通过 |
|---|---|
| 枚举（非退化） | 1611 |
| 命中严格比值窗 ±0.012 | 424（26.3%） |
| 命中宽松比值窗 ±0.05 | 1469（91.2%） |
| 通过第 4 星几何验证 | 869（53.9%） |
| **同时通过宽松窗与验证（最终投票）** | **839（52.1%）** |

即过半真三角形确实投了票，但**伪三角形以更高密度投出更集中的票**：

- 星表索引域 mag≤4.0 共 514 颗星 → 33924 个三角形，落在 9719 个比值桶里；
- 宽场下真三角形的边长比失真 median **0.019**（> 严格窗 0.012），因为照片是
  **gnomonic 投影**：像素距离 ∝ tan(θ) 而星表索引存的是纯角距 θ。
  失真随角距增长（20° 时 +4.3%、40° 时 +20.2%、50° 时 +36.6%），
  所以只有 26% 的真三角形能落进严格窗，而伪三角形（数值上凑巧接近）
  反而更容易进严格池。

在 34° 窄场（apod4）该失真 median 仅 0.006，落在严格窗内，故窄场一直正常 —— 
**这是一个只在 60°+ 宽场暴露的架构缺陷**。

## 四、修复：宽场打分轮（§0.62）

投票轮全败时，追加一轮"候选三角形逐个拟合 + 按整组一致性打分"：

1. 与投票轮相同地枚举照片三角形、查索引取候选星表三角形；
2. 对每个候选做三点相似拟合（照片像素 → 星表切平面）；
3. 把**全部**星表星经模型逆映射回像素，统计落在检测星 8px 内的颗数；
4. 取得分最高者作为初始对应，再展开为全部对齐对，交给原有
   RANSAC + 精拟合 + 内点门限流程（伪解仍由 plausibleFov / skySpan 把守）。

关键实测：

| 假设 | 平均对齐星数 | 最大 |
|---|---|---|
| **真三角形**（用真值配对，独立 Python 台） | **16.8 / 25** | 18 |
| 伪三角形（14902 次随机采样） | 1.0 / 25 | 3 |

分离度 16 倍 —— 逐星投票把这组极干净的信号平均掉了，整组打分则完整保留。

**注意**：上述 16.8 是"已知道真值配对"的上界。生产环境里打分轮不知道配对，
它在索引给出的候选三角形里择优，用户照片最终胜出候选对齐 7 颗（见下）。
因此判决门槛不能只看绝对数，必须看**对齐率**：

日志（修复后，2200×1650 帧）：
```
seed pi=5  -> (1118.29, 646.93) vs (1118.50, 648.99)  dd=2.06px
seed pi=10 -> ( 951.18, 529.26) vs ( 950.32, 527.78)  dd=1.48px
seed pi=9  -> ( 954.19,1025.45) vs ( 954.83,1024.87)  dd=0.64px
seedOk=3
```

### 4.1 判决门槛：对齐率（标定实测）

绝对对齐数不可直接当门槛 —— 伪解（尺度坍缩把整片天区压进画面）能拿到
13~21 的绝对数，比真解的 7 还高。真正有区分度的是**对齐率 = aligned / inFrame**：

| 样本 | aligned | inFrame | **rate** | 判定 |
|---|---|---|---|---|
| 用户南宁照片（真解） | 7 | 26 | **0.27** | SOLVED |
| pleiades（伪） | 21 | 183 | 0.11 | UNSOLVED |
| apod1（伪） | 13 | 139 | 0.09 | UNSOLVED |
| apod3（伪） | 15 | 175 | 0.09 | UNSOLVED |
| apod5（伪） | 19 | 235 | 0.08 | UNSOLVED |
| apod2（伪） | 14 | 198 | 0.07 | UNSOLVED |
| m44-1910（伪） | 5 | 99 | 0.05 | UNSOLVED |

真解 inFrame=26 恰好等于该天区 mag≤4.0 的真实星数（画面真实覆盖），
而伪解 inFrame 高达 139~235（整片天区被压进画面）→ 对齐率被稀释。
取 `SCORED_MIN_ALIGN_RATE = 0.20`（真伪之间有 2.5 倍以上间隔，居中偏保守），
并配 `SCORED_MIN_ALIGNED = 6`、`SCORED_MIN_IN_FRAME = 4` 两个下限。

### 4.2 匹配必须一对一

首版打分允许多颗星表星命中同一颗检测星，导致伪解恒得满分（45/45 = work 上限，
实测 pleiades/apod1/2/3/5 全部如此）。改为**一对一占用**后伪解回落到 13~21，
真伪才可比。

## 六、附带改动

- **星表域统一**：新增 `debugForceCatalogMag`，把"投票索引域 / 第 4 星验证网格 /
  内点统计域"从三个各自硬编码的阈值（4.0 / 4.0 / 4.5）统一为单一 `catalogMag()`，
  消除三域不一致（历史教训：仅加深索引而验证域不动会让暗星三角形被整体否决）。
- **候选数上限可调**：`debugCandidateCap`（生产默认 18），用于证伪"真候选被
  take(18) 挤出"的假设 —— 实测提到 600 仍不解，故该假设不成立，保留为调试开关。
- **调试观测点**：`debugScoredBest`（打分轮最佳对齐数）。

## 七、遗留

- 打分轮让失败路径变慢（~10s → ~26s，仅在投票全败后触发；成功路径不变）。
  后续可加"对齐数下界"提前剪枝或时间预算。
- 60°+ 宽场的**投票轮**本身仍被伪三角形污染；打分轮是兜底而非替换。
  根治方向：索引改用 gnomonic 感知的比值（或直接存三角形内角），
  使宽场真三角形回到严格窗内。
