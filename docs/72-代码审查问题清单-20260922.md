## 摘要

**算法核心是可信的** —— 单桶索引 + 有界 top-K 没能构造出漏解反例，分级星表域「五个域统一切换」
的取向正确，`horizon`/罗盘投影的数学逐式核对无误，`testdata/` 红线未触碰，全仓零 `TODO/FIXME`。

**风险集中在两处**：

1. **「星表域」被实现成了进程级可变全局状态**（写入方独占一把锁、读取方完全裸奔），
   而域切换的代价（9.3s 索引构建 + 16 倍候选密度）正好落在一条**长驻后台求解路径**上；
2. **相机与渲染层的分配/生命周期**：离开相机页不解绑、AR 每帧大量分配、
   结果页主线程合成全分辨率位图。

| 级别 | 条目 | 说明 |
|---|---|---|
| 高 | 8 | 影响隐私/耗电/崩溃/静默失败，建议发版前处理 |
| 中 | 11 | 稳定性与体验，建议排期 |
| 低 | 一批 | 注释漂移、死代码、i18n 双机制 |

## A. 高优先级

### A1 离开相机页不解绑相机 ✓
`ui/camera/CameraScreen.kt:267-281`（`DisposableEffect` 的 `onDispose`）、`:316`、`:430`

`provider` 在 `:316` 局部获取，`onDispose` 只做 `stopTracking` / `stopListening` /
`analysisExecutor.shutdown()`，**没有 `unbindAll()`**；它只出现在 `:430`（下一次进入相机页时）。
而 `bindToLifecycle` 的 owner 是 **Activity**，跳转到结果页/主页时 Activity 并未销毁。

**后果**（三条并发）：
- 相机常开 → 状态栏隐私指示常亮、持续耗电（用户可感知）
- `ImageAnalysis` 仍每 5~8s 投递帧 → 向已销毁的组合状态 `post` 写入
- `analysisExecutor` 已 `shutdown()`，投递命中 `RejectedExecutionException`；
  若 CameraX 未回收 `ImageProxy`，`KEEP_ONLY_LATEST` 流可能挂死

**建议**：把 `ProcessCameraProvider` 提到 `remember`/`LaunchedEffect` 外，`onDispose` 里
`unbindAll()` 之后再 `shutdown()`。

### A2 深域兜底没有准入闸门 ✓
`astro/LocalStarMatcher.kt:1100-1139` + `ui/camera/CameraScreen.kt:361`

触发条件只是「浅域整条阶梯无解」（`:1101`），对**任何失败帧**都成立——白天的预览帧、
室内、纯噪声帧。`PROGRESS.md` 说的「只在失败路径付一次」实际是「**每个失败帧都付一次**」：
首帧付 9.3s 构建，之后每帧跑 16 倍候选密度的深域阶梯。

另外 `StarSolver.kt:229-244` 的 `localSteps()` 把 LOCAL_MATCHER 排在官方引擎**之前**，
而官方引擎才是能解窄场的那个 → 窄场照片端到端等待被拉长。

**建议**：给深域加显式准入（调用方传 `allowDeepRetry`，或按 EXIF 视场 ≤30° 区分）；
预览路径默认不启用。

### A3 切域锁只保护写入方，读取方完全无保护 ✓
`astro/LocalStarMatcher.kt:1119-1126`（写）vs `:653 / :245 / :1938 / :1772 等`（读）

`synchronized(domainLock)` 只包住「深域重试」，而 `catalogMag()` 的 6 个读取点全在锁外。
两个真实调用点在不同线程上：`StarSolver.kt:319,652`（`Dispatchers.IO`）与
`CameraScreen.kt:361`（相机分析线程）。代码层面没有任何东西阻止两者并行 ——
代码注释里「App 内求解本就串行」是**假设而非保证**。

**后果不止「串域」**：一次 `matchInternal` 要读 6 次 `catalogMag()`。若线程 B 在 A 恢复域之前
读到 6.5 拿到深域索引、随后 A 恢复成 4.0，B 的验证网格/内点统计又变回浅域 ——
正是 §0.43 记录的「只改其中一个域完全无效」形态，表现为**静默 UNSOLVED**（比变慢更难查）。

**建议**：把「域」从全局状态降级为求解上下文（`mag` 作为参数透传到
index/catGrid/scoreTable/countInliers），或至少用 `ThreadLocal`；若坚持全局，读侧也必须取同一把锁。

### A4 `projMap` 是整份死重量 ✓
`astro/LocalStarMatcher.kt:919`（每三角形写 9 个桶）、`:1772`（`queryCandidates` 定义）

全仓 `grep queryCandidates|projMap` 在 `LocalStarMatcher.kt` 之外**零命中**；
文件内 `queryCandidates` **只有定义、没有任何调用点**，`projMap` 只在它内部被读。

9 桶存储 ⇒ 深域 55.6 万三角形 → projMap ≈ **500 万条引用**。这个数字与项目自己的记录
完全对上（`PROGRESS.md` 记「mag≤6.5 → 5,000,886 条」，即 55.6万×9）。
即：**当年被判定内存不可行的那部分被完整保留成了永不查询的死数据**，如今还多了一个域、
常驻进程。粗估 30~60MB JVM 堆量级。

**建议**：深域不建 projMap（`magLimit > PROD_CATALOG_MAG` 时跳过），
或直接删掉 `projMap` + `queryCandidates` 整条死分支。

### A5 `indexCache` 是无锁读的普通 HashMap ✓（v1.5.62 引入的回归）
`astro/LocalStarMatcher.kt:633-634`、`:651-658`

```kotlin
@Volatile private var indexCache: HashMap<Float, StarIndex> = HashMap()
...
private fun index(): StarIndex {
    val mag = catalogMag()
    indexCache[mag]?.let { return it }        // :653 锁外读
    synchronized(this) { ... put ... }        // :654-656 锁内写
}
```

`@Volatile` 只保证引用发布的可见性，不保证 `HashMap` 内部结构安全。v1.5.61 的
「单槽缓存 + volatile 双检」是安全的，换成 `HashMap` 后成为真正的数据竞争：
最坏情况是重复构建一次 9.3s 的深域索引 + 一次额外大对象分配。

**建议**：改 `ConcurrentHashMap`，或把首检挪进 `synchronized(this)`。

### A6 AR 每帧大量分配（打破「零每帧分配」硬性要求）✓抽查
- `astro/ArSkyProjector.kt:233 / 250 / 264 / 288` —— 每帧逐元素 `new` `Star2D` / `Line2D` /
  `Messier2D` / `Solar2D`。全天 mag≤5.2 约 2000 颗 → **~2000 个对象/帧**、12 万/秒
- `astro/ArSkyProjector.kt:243` —— `withIndex()` 每元素一个 `IndexedValue`
- `astro/ArSkyProjector.kt:61 / 184` —— `floatArrayOf(...)`、`FloatArray(3)` 在函数体内
- `astro/LayeredRenderer.kt:90/111/128/141/145/167/...` —— 每帧新建 **9 个 `Paint`**
  （已核实均为 `Paint(Paint.ANTI_ALIAS_FLAG).apply {...}` 写在函数体内）
- `astro/LayeredRenderer.kt:158` —— `m.obj.label(isEnglish)` 每次调用新建 String（110 个梅西耶 × 60fps）
- `astro/LayeredRenderer.kt:259` / `OverlayRenderer.kt:160` —— `shrink()` 每帧每线一个 `FloatArray(4)`
- `util/DeviceOrientationTracker.kt:163-231` —— 姿态链每帧 10+ 个 `FloatArray`；
  `:199` 每帧 `new GeomagneticField(...)`（地磁模型构造不轻量）；
  `:214-220` `Pair<Double,Double>` 装箱；
  `:188` + `LocationHelper.kt:42-60` 每帧 2 次 `checkSelfPermission`（Binder IPC）→ 120 次/秒

**影响**：GC 压力 → 低端机频繁 minor GC、掉帧、发热。这正是「跟手但烫」类问题的典型根因。

**建议**：`ProjectedSky` 预分配并行 `FloatArray`；`Paint` 按 `density+night` 做缓存
（照 `CameraScreen.kt:205-255` 的 `NavPaints` 模式）；`QuatMath` 加 `xxxInto(out, ...)` 变体；
地磁/定位结果按时间窗缓存。

### A7 主线程合成全分辨率位图
`ui/result/ResultScreen.kt:344` 与 `:599`、`ui/result/ZoomableImageViewer.kt:237-249`

`renderAnnotatedBitmap` 新建 ARGB_8888 位图（2200px 级 ≈14MB）并跑全星表投影绘制，
却写在**点击回调**（主线程）里；同一函数在 `SaveToGalleryButton`（`:645-658`）里
却正确地放在了 `Dispatchers.IO` —— 同一操作两套实现。旧 `annotatedBitmap` 从不 `recycle()`，
反复切换图层 = 反复十几 MB 原生分配。

**建议**：统一走 IO；渲染前确认无引用后 `recycle` 上一张。

### A8 Pro 手动曝光在离开相机页时不清除
`ui/camera/CameraScreen.kt:502-532`

`clearCaptureRequestOptions()` 只在 `proMode` 变 false 时调用。叠加 A1（相机未解绑），
离开时若 `proMode=true`，**AE 关闭与最长 30s 曝光会留在相机设备上**，
下次不重绑就不会恢复 → 用户看到黑屏/极暗画面。

**建议**：`onDispose` 里若 `proMode` 则显式 clear。

## D. 已核实无误（不必再查）

- **单桶索引 + 有界 top-K 没有漏解**：`bucketKey` 与 `quantizeKeys` 量化一致（同 256 级、同钳位），
  旧「存 b±1 查 b±13」与新「存 b 查 b±14」在钳位边界上覆盖等价，没有「旧能查新查不到」的边角；
  `triBefore` 与旧比较器同键、去重键唯一故为全序，`p == cap` 跳过与 `.take(cap)` 等价。
  **唯一风险是脆性**：两个量化参数必须永久同步，任何单边改动会静默缩小召回，
  而现有 176 项单测不覆盖这一点 → 建议加一条断言 `bucketKey(r2,r3) == quantizeKeys(r2,r3,0).single()`。
- 地平线直线方程与 8 方位罗盘的针孔投影推导（手算核对无误）；`save/restore` 配对正确。
- `testdata/` 红线：`git ls-files` 为空、`.gitignore` 已忽略、未进 `assets/`、未打入 APK。
- `allowBackup="false"` ✓；运行时权限声明与请求路径完整 ✓；`uses-feature` 均 `required="false"` ✓。
- 无 `lateinit`、无 `GlobalScope`/裸 `Thread`、无 TODO/FIXME；`ListenableFuture.await` 取消语义正确。
