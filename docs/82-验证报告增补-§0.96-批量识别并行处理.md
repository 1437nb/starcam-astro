# 82 · 验证报告增补 §0.96 —— 批量识别的并行处理

> 版本：v1.5.70（versionCode 90）
> 日期：2026-10-05
> 来源：开发者提问「能不能在勾选多张星空图片的时候并行处理」

---

## 1. 改了什么

批量识别（勾选多张 → 逐张识别 → 渲染标注 → 存相册）原先是**单协程串行** for 循环，
现改为**有界并发**：

- 任务队列 + `workers` 个协程从队列取活（`synchronized` 保护取任务）；
- **并发度按内存定**：`ActivityManager.isLowRamDevice` 为真 → **1**（退回串行），
  否则 **2**。上限即 2，不随核数放大；
- 每张的"识别中/成功/失败"状态与成功计数都回到主线程更新（Compose 状态必须在主线程写），
  计数用 `AtomicInteger`；
- 位图回收（§0.81 的 `try/finally`）**逐 worker 保留**，退出路径一条不少。

## 2. 为什么可以并行（逐项核实，不是推测）

| 共享状态 | 现状 | 结论 |
|---|---|---|
| native 求解入口 | `solve_job_t` 每次调用 `calloc`（**不是**全局静态） | 并发调用互不影响 |
| 索引缓存 | 加载循环持 `g_index_mutex`，且**在 `run_with_timeout` 之前释放** | 只有首次加载会互斥，求解本身不互斥 |
| 并发求解本身 | §0.67 当年专门做过 **3 线程并发求解**验证（三次 nstars 各不相同、`ALL RETURNED CLEANLY`） | 已受支持 |
| 本地匹配器 | `solveLock` **整段互斥**（星表域是对象级状态，§0.77 的决定） | 安全，但并发走到这一步会**排队**（见 §4） |
| 识别历史 / 统计 | §0.92 起 `@Synchronized` | 线程安全 |
| 识别日志 | `SolveLogStore.line` 内 `synchronized(this)` + 文件级 append | 线程安全 |
| `StellarSolverNative.lastFail*` 等诊断全局 | 无锁 | 并发时会互相覆盖 —— **只影响诊断数字**，不影响解算结果（失败页在批量流程里不展示） |

## 3. 内存是真正的约束

每张"在飞"的照片峰值约 **30~80MB**：解码后的 2200px 位图（约 14.5MB）+ 求解中间数组
（灰度 FloatArray 等约 14.5MB）+ 渲染输出位图（约 14.5MB）。这也是原实现刻意串行的原因
（§0.81 的注释写着"9 张串行处理若不回收，原生堆峰值可达 100~200MB"）。

所以并发度**不按核数放大**，而是按内存：低内存设备 1、常规设备 2。2 路时峰值约
60~160MB，落在现代手机堆上限（通常 192~512MB）之内；低内存设备退回串行保持原状。

## 4. 已知的性能边界（说清楚，别期待过高）

**若某张照片最终由"内置星表"引擎解出，它的求解段会被 `solveLock` 串行化**，跟并行度无关。
也就是说：

- 并行的收益来自：JPEG 解码、叠加渲染、存相册（这三段不持锁）与**官方引擎**求解段；
- 本地匹配器求解段在多 worker 下只是排队（不会互相踩，但也不会更快）。

要突破这一点需要把星表域从"对象级状态 + 全局锁"改成"每次求解独立实例"（catalogMag 及
其索引/网格/打分表都随实例走）—— 那是一次结构性改动，另议。

另：官方引擎内部本身已是多线程（§0.15 的 dsmooth 双 pass 并行），2 路并发在 2 核设备上
可能互相争抢；4 核以上通常净收益为正。

## 6. 遗留

- **真机未测**：需要一张多图批量任务实测（重点看：低内存设备是否退回串行、2 路时是否
  稳定、相册里 9 张是否都完整）。若出现 OOM 或相册写入失败，把并发度降到 1 即可（一行）。
- 并发度目前写死 2/1；若将来想按"可用堆"动态定（`memoryClass`），可以再调。
- 诊断字段（`lastFail*`、`debugScored*`）在并发下会串台，批量流程不展示它们，暂不处理。
