# StarCam v1.5.66 更新说明

**主题：识别不再挑设备；界面按 Material 3 重做；结果页显示识别耗时**

这一版修的是最让人费解的一类故障：**同一张照片，在开发机上稳定解得出来，在手机上却认不出**。
根因既不在星表深度、也不在提星阈值，而在打分轮的一个**时间预算**——它把「设备快慢」
变成了识别成败的变量。

## 修复内容

### 1. 打分轮预算：从「3 秒墙上时钟」改成「2 万个候选」（§0.87）

打分轮是宽场照片的兜底：投票失败后，对每个候选三角形做三点相似拟合、把星表星逆映射回
画面，按**对齐率**（对齐数 / 画面内星表星数）判决。它的候选按「与照片边长的比值偏差」
升序排列，而照片是 gnomonic 投影、真三角形的比值偏差最大 —— 于是**真解总是排在候选
序列的最后一位**。实测 12 张演示照中走打分轮的 8 张无一例外（218/218、1116/1116、
8730/8730，重复运行稳定）。

原来给这一轮设了 3 秒预算（本意是限制失败路径的耗时），后果是：**候选串没跑完，就必然
错过唯一正解**。开发机上那 218 个候选只要 0.2 秒、余量 15 倍；手机上（冷启动、降频）
会被切在检查点 → 浅域失败 → 深域重试 → 显示"认不出"。

改用**候选数**上限后，结果与设备速度无关。打分轮统计串新增 `CUT=cap` / `CUT=soft`
标记，失败页可以直接看出某一轮是否被截断。

### 2. 主星表解不出时，换第二个检测器再试（§0.88）

同一张照片上，两个提星器给出的星表可以差很多：手机端的 SEP 提出 177 颗（混有大量非星
峰），本地 box-blur 只给 32 颗。前者把打分轮的邻域表与候选生成挤坏（打满 2 万候选仍只有
8/206），后者 16/30 轻松过门。现在主星表浅域无解时，会用备用星表在浅域再试一次，成功
即采用；两者都失败才进深域重试。

### 3. 有兜底就不先付满额：识别更快（§0.89）

顺着上一条：既然有备用列表兜底，就不该先为一份可疑列表跑满 2 万候选。现在主星表先只跑
2000 个候选试探（同一台手机上从 24.5 秒降到 2.4 秒量级），失败即转备用列表，两者皆败
才回到主星表的完整预算。**顺序变了、搜索空间没变小。**

### 4. 结果页显示识别耗时（§0.90）

成功页信息面板与失败页各显示一行「识别耗时」。口径只计求解本身、不含照片解码。
中英双语：不足 1 分钟保留一位小数，超过 1 分钟用「分 + 秒」。

## 界面：Material 3 重做（§0.85）

- 字阶按 M3 规范重排（此前是默认排印），建立 5 档圆角体系（此前是 6 处零散半径），
  深浅两套主题补齐 `surfaceContainer*` 色调阶梯，并补上 M3 未定义的「成功」语义色。
- 相机叠加层的功能色与「零每帧分配」的绘制代码**保持不动** —— 夜间红光模式依赖它们。

## 星点计数与失败页修正（§0.86）

界面上的「检星 N 颗」此前显示的是**喂给匹配器的截断列表长度**（上限 200），而不是真实
检出总数，于是常出现"明明满天星却只显示 197 颗"。现在原生层会额外给出未截断的总数，
显示与匹配器输入解耦。失败页也改为**逐轮显示**（浅域 / 深域分别列出投票轮与打分轮的
统计）—— 以前只看得到最后一遍（深域）的数字，会把人误导到错误的方向。

## 验证

- 全量单元测试 **181 项 0 失败**（含 12 张真实照片回归 `true=12 / false=0 / miss=0`，
  以及假阳性对照 apod3 / apod5 / pleiades 全部保持 UNSOLVED）。
- 新增回归测试：`ScoredRoundBudgetTest`（钉住"打分轮必须跑完整串才能解出"）、
  `FallbackStarListTest`（主星表被污染时备用列表必须接管并解到正确天区）、
  `SolveTimeFormatTest`。
- 真机实测：此前认不出的那张 76° 广角欠曝照片已能识别。

## 已知边界

- 主星表被污染时，浅域会先花约 2.4 秒试探（手机端），随后由备用星表解出 —— 即
  "能认出来，但要等几秒"。这一层还能再优化（按列表规模自适应上限、或先跑便宜检测器）。
- 画面里有大片非星空区域（遮挡、地面）时，可检测星点少，识别率天然偏低。

## 安装

- `release` 包与历史版本同一签名证书，可直接**覆盖升级**，无需卸载。
- `debug` 包含调试日志，供排查问题时使用；与 release 包签名不同，不能互相覆盖。
