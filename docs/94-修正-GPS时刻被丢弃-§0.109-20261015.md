## 1. 发现（验证过程中的意外收获）

**现象**：用 App 的真实读取链（`ExifPriorsReader.read()` + androidx ExifInterface 1.3.7）
读一张真实手机照片 `testdata/userphoto/photo.jpg`（GPS 原始值 `(17, 25, 46)`，即
2026-09-11T17:25:46Z），解析结果却是：

```
epochSec = 1789084800 = 2026-09-11T00:00:00Z     ← 当天零点！时分秒被丢掉了
正确值   = 1789147546 = 2026-09-11T17:25:46Z
```

**根因**：`GPSTimeStamp` 在标准 EXIF 里是 RATIONAL 三连（`17/1,25/1,46/1`），而
**androidx ExifInterface 读出来的是格式化后的 `"17:25:46"`**（实测 1.3.7，与仓库依赖版本一致）。
而 `parseUtcEpoch` 一直是按 `"num/den,num/den,num/den"`（**逗号+斜杠**）解析的：

```kotlin
val parts = time.split(",")          // "17:25:46" → 只有一个元素
fun frac(v) = if (!v.contains("/")) v.toDoubleOrNull() ?: 0.0   // 解析失败 → 0.0
val h = frac(parts[0])               // → 0.0
```

→ 时/分/秒全为 **0** → epoch 恒为"当天 UTC 零点"。

## 2. 影响与历史（逐版对照）

| 版本 | 对 RATIONAL GPS 时间的实际行为 | 月亮标注最大偏差 |
|---|---|---|
| ≤ v1.5.74（`SimpleDateFormat` 宽松解析） | 拼出 `"… 0:0:0"` → **当天零点**（静默错误） | ~±12h × 0.55°/h ≈ **±6.6°** |
| v1.5.75（§0.100 换严格 `DateTimeFormatter`） | 单数位格式解析失败 → **回落 DateTimeOriginal（本地时间）** —— 意外更接近真值 | 0°~与时区差相关 |
| v1.5.76（§0.105 我的修法） | 日期 + `atTime(0,0,0)` → **又变回当天零点**（这次是所有情况） | **±6.6°** |

结论：这条缺陷**不是 §0.105 引入的**（≤1.5.74 就有），但 §0.105 的修法把它从"部分回落到
本地时间"变回了"一律零点" —— 对 GPS 照片是一次**行为回退**，必须尽快修。

**§0.105 分析前提的更正**：二期审计（与我的复核）都假设 `parseUtcEpoch` 收到的是
`"22/1,30/1,15/1"` 的原始形态，由此推出"59.5% 的秒数解析失败"。真机路径上
androidx 给的是 `"HH:MM:SS"`，所以"59.5%"这个数字描述的是一个**不存在的输入形态**。
真实的失效形态是上面这张表 —— 教训：**解析器的输入格式必须用真实依赖版本实测确认**，
不能凭 EXIF 规范的存储形态推断。

## 3. 修复（§0.109）

`parseUtcEpoch` 改为**两种形态都认**，且认不出时**返回 null（由调用方回落
DateTimeOriginal）而不是退化成 0:0:0**：

```kotlin
private fun parseGpsTimeOfDay(raw: String?): Triple<Int,Int,Int>? {
    if (t.contains(':')) { …按 "H:M:S" 解析（androidx 形态；容忍无前导零、缺秒、小数秒） }
    else                 { …按 "num/den,num/den,num/den" 解析（少数机型的原始形态） }
    // 时解析失败 → null（绝不 0 点）
}
```

## 4. 回归测试（两条防线）

1. **`ExifPriorsTimeParseTest`**（纯函数层，13 项）：新增冒号形态（`"22:30:15"`、
   `"8:5:9"`、`"08:05:09"`、缺秒按 0）与"**认不出必须 null、不得变零点**"两组断言。
2. **`ExifPriorsGpsTimeRealFileTest`**（真文件层，3 项，CI 跑）：夹具是**带真实 GPS EXIF 的
   JPEG**（`src/test/resources/exif-probe/`，由 `tools/make_exif_probe.py` 在公开演示图上注入
   GPS 生成），走 `ExifPriorsReader.read()` 全链路断言 epoch 等于 GPS 的 UTC 时刻：
   - 探针 A（12:05:09，**单数位**，无 DateTimeOriginal）→ `1730462709`（12:05:09Z，不是零点 1730419200）；
   - 探针 B（14:30:15 + DateTimeOriginal）→ `1730817015`（GPS 优先于本地时间）；
   - 无 EXIF 文件 → 安全降级为空值。
   这条测试在 v1.5.76 上会红（实测同一夹具返回零点）—— 这就是它的价值：**只按原始分式形态
   写断言的老测试挡不住这个 bug**。

**A/B 实测**（验证机/本机同一夹具）：
```
修复前：epochSec=1730419200  = 2024-11-01T00:00:00Z   （探针 A）
修复后：epochSec=1730462709  = 2024-11-01T12:05:09Z   ✓
真照片：1789084800（零点） → 1789147546 = 2026-09-11T17:25:46Z ✓
```

## 5. 顺带修掉：一条只在非 UTC 机器上会红的既有断言

`localEpochUsesSystemZone` 的期望写成 `utc + 偏移`，正确关系是 **`local = utc − 偏移`**
（同一串墙上时间在 UTC+8 下的时刻更早）。它在 UTC 机器（验证机、CI）上偏移为 0 恰好恒成立，
只有在 +8 时区的机器上跑才现形 —— 本次在构建服务器（Asia/Shanghai）本地跑测时暴露并修正。
教训：**时区相关的断言要在非 UTC 环境跑一遍**。
