## 1. 问题：两处共享 `SimpleDateFormat`，且在批量并发路径上

§0.96 起批量识别为**两 worker 并行**（`BatchScreen`）。两处格式化器是
**组合级 / object 级共享**实例，被并发调用：

| 位置 | 原实现 | 并发调用方 | 出错后果 |
|---|---|---|---|
| `ui/batch/BatchScreen.kt:67`（第 111 行用） | `remember { SimpleDateFormat("yyyyMMdd_HHmmss", Locale.getDefault()) }` | 两个 worker 各自 `format()` 生成相册文件名 | 文件名时间错乱；重则 `ArrayIndexOutOfBoundsException` 被外层 `catch` 吞掉 → **静默丢条目** |
| `astro/ExifPriors.kt:78,81`（第 176/187 行用） | `object ExifPriorsReader` 的 `utcFormat` / `localFormat` | `BatchScreen` 两 worker → `solarSystemForPhoto`；单张流程 `StarSolver` | EXIF 拍摄时刻错乱 → **太阳系标注位置错误**（月亮每小时走 0.55°，错标比不标更糟）；异常同样被吞 |

`SimpleDateFormat` 非线程安全（内部 `Calendar` 是可变状态），并发使用属**已知崩溃形态**。

> 审计只报了第一处；《待修清单》核实后发现第二处（同属批量并发路径，且是 object 级共享），
> 两条一并修 —— 本次即按核实版的结论执行。

## 2. 改动：换线程安全格式化器，语义逐条保持

两处均改为 `java.time.format.DateTimeFormatter`（**不可变、线程安全**），先例
`data/SolveLogStore.kt` §0.81（该处 2026-09 已按同一思路修过）。

| 语义点 | 旧（SimpleDateFormat） | 新（DateTimeFormatter） |
|---|---|---|
| 线程安全 | ❌ 内部可变状态 | ✅ 不可变，可安全共享 |
| UTC 解析 | `utcFormat`（`timeZone=UTC`） | `LocalDateTime.parse(t, fmt).toEpochSecond(ZoneOffset.UTC)` |
| 本地解析 | `localFormat`（默认时区） | `LocalDateTime.parse(t, fmt).atZone(ZoneId.systemDefault()).toEpochSecond()` |
| 坏输入 | `parse` 抛异常 → 捕获返回 `null` | 解析抛 `DateTimeParseException` → 捕获返回 `null`（对外语义不变） |
| 首尾空白 | `parse` 原本容忍 | 显式 `.trim()`（保持容忍） |
| 文件名 | `StarCam_<yyyyMMdd_HHmmss>_$i.jpg` | **不变**（见下） |
| Locale | 文件名用 `Locale.getDefault()` | 改 `Locale.US`（纯数字模式；规避非公历区域如泰历产生错误年份） |

**关于「文件名加任务序号防同秒撞名」**（审计建议）：核实 `_$i` 即**任务序号**、
批内唯一，原实现就已满足；本次不改命名。

## 4. 验证

1. **新增回归测试** `ExifPriorsTimeParseTest`（10 项，进 CI 常规执行）：
   - 语义锁定（反射直调 private 解析函数，锚定**手算常量** `1723501815`，不依赖
     java.time 现算，避免同源循环论证）：GPS UTC 秒值、`-` 分隔容错、整数形式
     GPSTimeStamp、本地时区解释（与 UTC 的差值 = 该时刻**时区偏移**，在 UTC 与
     Asia/Shanghai 下均成立）、坏输入返回 `null`、尾随空白容忍；
   - **线程安全回归**：8 线程 × 200 轮并发调用两处解析，全部结果必须正确且无异常；
   - **防回退守卫**：反射断言 `ExifPriorsReader` 不再持有任何 `SimpleDateFormat` 字段。
2. **CI（GitHub Actions）**：`unit-test` 全绿 —— 运行号与实测项数见 `PROGRESS.md`
   回填（预期口径：22 类 / 185 项；CI 不跑依赖 `testdata/` 的 8 个真图/回归类）。
3. **本机限制（如实说明）**：服务器 1.87GB 内存跑不了 Gradle（见 PROGRESS
   2026-10-08），本次未在本机执行全量单测（全量 200 项，含 15 项真图回归）。
4. 改动文件的 Kotlin 语法/API 解析检查：0 语法错误（用 Gradle 缓存内的
   kotlin-compiler 单独编译改动文件，缺依赖报错均为 classpath 级联）。

## 5. 未覆盖 / 风险

- `BatchScreen` 的**文件名生成路径无自动化覆盖**（Compose UI），本次只证明
  「格式化器线程安全」；文件名唯一性依赖 `_$i`，与改动前一致。
- 真机批量（≥2 张并发）建议纳入下一次真机验证清单（与 §0.96 的批量手测一并做）。
- `DateTimeFormatter` 对**格式严重畸形**的 EXIF 字符串比 `SimpleDateFormat`（宽松模式）
  更严格：畸形日期（如 2 月 30 日）会按 SMART 规则夹取到月末而不是滚动到下月，
  极端输入可能由「有值」变为 `null` → 走"无拍摄时间"降级。属更保守的方向，
  真机上如遇此类照片，表现是太阳系标注缺失而非标错。
