# 验证报告增补 §0.15 — 手机预算模拟：官方引擎 11/12 + 差距诊断（2026-08-28）

> 可直接粘贴进 `StarRecognizer\docs\验证报告.md`。

## 模拟方法

在服务器（2 核 x86_64）上按手机 App 的官方引擎调用逐项对齐复刻：

| 环节 | 手机 App | 服务器模拟 |
|---|---|---|
| 输入 | ≤2200px 长边（decodeSampledBitmap） | 2200px LANCZOS 副本（12 张全转） |
| 段 1 | 3°~40°，限 12s 墙钟 | `--scale 3-40 --cpulimit 96`（CPU 秒） |
| 段 2 | 40°~120°，限 16s 墙钟 | `--scale 40-120 --cpulimit 128` |
| 星点数 | JNI：simplexy 全部星点 | `--depth 400` |
| 求解 | solver_t 单线程 | solve-field（solver 同源，单线程核心） |

8 核手机 28s 墙钟 ≈ 224 CPU 秒（solver 单线程——折算按 n 核用足才成立，
见"差距诊断"）。

## 结果：11/12 在手机预算内解出

```
SEG2-SOLVED 4963 4974 4984 4998 5031 5040 5049 5068 5076 5087 5092
FAILED      5057（41° 变焦——正是 §0.14 降采样重试轮的覆盖对象）
```

- **全部命中段 2（40°~120°）**：该分段果然是主战场，App 盲解分段配置正确。
- 对照实验：depth 1000 同样秒解（4974: 1.8s / 5040: 2.1s / 4998: 7.2s，
  log-odds 29~133）→ **depth 不是瓶颈**（JNI 全星点 ≠ 劣势，反之可能在噪声下更稳健）。
- 结论：**App 的盲解预算、分段、输入规模在服务器等参数下足以解 11/12**，
  与 App 实机记录的 6/12 之间的差距不在这些环节。

## 差距诊断（按嫌疑排序）

1. **提星质量（最大嫌疑）**：solve-field 提星前有 image2pnm → FITS 的
   量化/背景管线，并可调 `--sigma/--uniformize`；App JNI 直接把手机 JPEG
   解码灰度喂 simplexy_set_defaults()。手机 JPEG 的 Gamma/噪声形态差异
   会直接改变星点列表 → quad 匹配率。此环节无法在 x86 服务器精确复刻
   （现有 .so 为 arm64，JNI 参数不可调）。
2. **索引加载计入预算**：JNI 每次 solve 都 index_load 8 档（~11MB），
   每次 0.5~2s，两段多次调用吃掉部分 28s 墙钟（未缓存句柄）。
3. **单线程墙钟折算**：28s 墙钟 = 28 CPU 秒；模拟中最慢仅 7.2 CPU 秒，
   理论上够，但若 1+2 叠加，边缘照片会被挤出预算。
