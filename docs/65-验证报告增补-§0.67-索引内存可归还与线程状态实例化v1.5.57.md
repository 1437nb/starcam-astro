# §0.67 索引内存可归还 + 求解线程状态实例化（v1.5.57）

> 修复日期：2026-09-17
> 动因：审计清单第七项「索引 11MB 常驻内存，无释放接口」。
> 该项的难点不在接口本身，而在**释放时机的安全性**——必须先解决 §0.65
> 遗留的 `solve_thread_leaked`（detach 线程仍可能在使用索引），否则一释放就段错误。

## 1. 先修前置：求解线程状态从全局改为实例级

### 问题

§0.65 引入的泄漏保护用了两个**进程级单例**：

```c
static volatile int solve_done;
static int solve_thread_leaked;   /* 本次调用是否 detach 了线程 */
```

正确性依赖「solve 从 JNI 串行进入」这个**隐式前提**，而且有真实缺陷：
`run_with_timeout` 每次进入都执行 `solve_thread_leaked = 0`。若上一次调用泄漏了
线程、下一次调用正常结束，标志被清零，调用方就会对**仍被读取的内存**执行
`solver_free` —— use-after-free。

### 修法

`job` 改为每次调用堆分配，完成标志挂在 job 上，泄漏状态用 out 参数返回：

```c
typedef struct {
    solver_t* sp;
    volatile int done;   /* worker 置 1 表示 solver_run 已返回 */
} solve_job_t;

static int run_with_timeout(solver_t* sp, double seconds, int* out_leaked);
```

调用方按**本次**的 `leaked` 决定是否 `solver_free`，不再读全局标志。

另加 `g_leaked_threads` 原子计数（只增不减，见下节说明），供索引释放接口判断
当前能否安全回收。

## 2. 索引释放接口

### 原生侧

```c
JNIEXPORT jint Java_..._StellarSolverNative_releaseIndexes(JNIEnv*, jclass);
JNIEXPORT jstring Java_..._StellarSolverNative_indexCacheStats(JNIEnv*, jclass);
```

`release_indexes()` 持锁检查 `g_leaked_threads == 0` 才逐档 `index_free()`
（官方提供的释放接口）并清零缓存；否则**拒绝释放**返回 0。
`indexCacheStats()` 返回 `{"cached":N,"loads":M,"leakedThreads":K}` 供诊断。

顺带修掉一个静默失败：原 `get_or_load_index` 在缓存满 16 档时静默 `return NULL`，
调用方只能看到 `no-index-loaded`，无法区分「没打包索引」和「缓存满了」。
现改为打 stderr 说明原因。

### Kotlin 侧

新增 `StarCamApplication`（manifest 注册 `android:name=".StarCamApplication"`），
在 `onTrimMemory(level >= TRIM_MEMORY_RUNNING_LOW)` 时调 `trimIndexCache()`。

阈值选 `RUNNING_LOW` 而非更早的级别，是为了避免用户正在连续识别时把索引丢掉、
导致下一次识别变慢。释放后下次求解会自动重新加载（多一次磁盘读取）。

## 3. 验证（x86_64 主机，真实桥源码 + JNI 替身）

六项全通过：

```
A) 初始              {"cached":0,"loads":0,"leakedThreads":0}
B) 单线程求解        solved 后 {"cached":8,"loads":8}      ← 索引加载 8 档
C) releaseIndexes()  freed=8 → {"cached":0,"loads":8}      ← 释放成功，加载计数保留
D) 释放后再求解      {"cached":8,"loads":16}               ← 自动重建（关键：可还也可重建）
E) 并发 3 线程       三线程分别返回 nstars=2076/1964/2049   ← job 实例化生效，互不干扰
F) 再次释放          freed=8
=== ALL RETURNED CLEANLY ===
```

E 项是本次改造的直接证据：旧版三个线程共用一个 `solve_done`，会是竞态；现在各
返回各自的星点数，说明状态确实隔离。

另跑提星回归（`extractStars` 六张真实照片 ×2 轮）全部 `ok=1 n=200`，无崩溃。

## 5. 设计取舍（诚实记录）

**`g_leaked_threads` 只增不减。** pthread_detach 之后无法 join，线程真正何时结束
我们无从观测，所以这个计数是「曾经泄漏过的次数」而非「当前仍在跑的线程数」。
后果：一旦发生过一次超时 detach，索引释放就**永久失效**（`g_leaked_threads > 0`
恒成立），11MB 再也不会被归还。

这是刻意的保守选择——宁可少还 11MB，也不能 use-after-free 崩在用户手机上。
要真正修好需要更强的基础设施（如给每个 worker 注册一个可查询的完成标志、
或把 detach 改成有界 join），超出本次范围。

**实际影响有限**：超时 detach 是罕见路径（需要 `quit_now` 在 5 秒宽限期内都没被
solver 采纳）。正常识别不会触发，索引释放照常工作。
