## 2. §0.91 接缝投影中心：改了什么，以及为什么报告的严重性被高估

### 2.1 改动

`LocalStarMatcher.verifyCandidate` 的投影中心原为算术平均：

```kotlin
val ra0 = (eA.ra + eB.ra + eC.ra) / 3.0     // 跨接缝时算到天区对面
val dec0 = (eA.dec + eB.dec + eC.dec) / 3.0
```

改为同文件既有的 **`sphericalMean(eA, eB, eC)`**（球面单位向量平均，RA 跨 0°/360° 安全）。
这是**漏改的一处** —— `fitPairs` 早已改过，注释里还留着 §0.60 的教训（「算术平均 117° 偏出真实中心」）。

### 2.2 实测：接缝天区并不会「整片零产出」

用合成星场（`SyntheticSkyRenderer`，不读外部素材）扫描接缝影响面，**并关掉打分轮**
（把既有的 A/B 开关 `debugMinAligned` 设为极大），使投票轮成为唯一出路：

| 赤经中心 | 12° | 15° | 20° | 25° 视场 |
|---|---|---|---|---|
| **0.0° / 0.5° / 1.0° / 359.5°（跨接缝）** | 解出 | 解出 | 解出 | 解出（dec=45 的 0.0° 一例失败，但同几何下 30.0° 也失败） |
| 8° / 20° / 30°（不跨接缝） | 解出 | 8°/20° 各有一例失败 | 解出 | 8°/3° 有失败 |

结论：**失败与「是否跨接缝」无关**，只与「该视场里恰好有哪些亮星」有关。原因是
`verifyCandidate` 只验证**单个候选三角形**：跨接缝的三角形会被算错中心而丢弃，
但同一视场里不跨接缝的三角形不受影响 → 投票轮照常解出。

即该缺陷是「**丢一部分候选**」，不是报告所说的「该天区零产出、只能靠打分轮兜底」。
修复后重跑同一扫描，失败场与修复前几乎逐位相同（如 `60.59°/104.4` → `60.58°/104.3`），
进一步印证它不是这些失败的成因。

### 2.3 回归测试

新增 `RaSeamRegressionTest`（**不依赖外部素材，CI 中照常执行**）：两组同几何、
只差赤经中心（0.3° 跨接缝 vs 30° 对照），并**关掉打分轮**，断言投票轮必须能解出。
它钉住的是「接缝天区可用」，而不是那个具体实现细节。

## 3. §0.92 / §0.93 另外两项首波修复

### 3.1 §0.92 存储写入串行化（S7）

`HistoryStore.save/remove/clear` 与 `StatsStore.record` 都是「load → 改 → 写回」，
而写方有两条线程路径（结果页在主线程、批量识别在 IO 线程）。并发时后写覆盖先写，
**历史条目与统计会静默丢失**。

四条写路径统一加 `@Synchronized`（对象级监视器）；底层是 SharedPreferences，
`edit().apply()` 自身原子，因此只需保证「读-改-写」整段互斥，无需文件锁。

### 3.2 §0.93 结果页 IO 下沉（S6 残留）

结果页的 `LaunchedEffect` 默认跑在主调度器上，此前直接在主线程执行：
`StatsStore.record`（500 条 JSON 全量重写）、`HistoryStore.save`、
`HistoryStore.nearestConstellation`（遍历全星表算角距）。三者已包进
`withContext(Dispatchers.IO)`。

**仍未下沉的（本次刻意不动）**：`showSuccess` 内的 EXIF 读取、`LocationHelper.getBestLocation()`
（阻塞式定位）与星图投影计算仍在主线程 —— 它们要重排 `state` 赋值时机，属
S6「IO 全部下沉」那一档，单独做。

### 6.1 S9 本机做不了（环境限制）

`compileSdk`/`targetSdk` 升 35 需要 `platforms/android-35` 平台包，本机只装了 `android-34`
且网络受限（Maven/Google 源不可达），**无法下载**。需在有网络的环境执行
`sdkmanager "platforms;android-35"` 后再升，并回归相机预览比例与沉浸式布局
（targetSdk 35 强制 edge-to-edge）。

### 6.2 S4 的验证边界（如实说明）

「编译通过 + 符号齐全 + 进包逐字节一致」；其运行期行为需真机或 host 侧桥接测试才能覆盖
（本机无 x86 编译器、无 Android 运行时，见 docs/81 §1 的环境说明）。

### 7.1 M3 的**行为差异**（如实记录）

滑动窗口的局部累加用 `double`，而原积分图是 `float` 逐点累加后大数相减（抵消误差明显）。
窗口均值在阈值附近因此会有微小差异，实测影响：

- **5087 的内点数由 25 → 14**（天区 `ra=349.77 dec=24.15`、视场 76.3° 均不变，判定仍 TRUE-SOLVE）；
- 5092 仍为 13（与 §0.43b 记录的 13 一致）；
- **12 张全部 TRUE-SOLVE、0 假阳性**，`apod3/apod5/pleiades` 仍保持 UNSOLVED、apod4 仍解出。

即：新实现更贴合「60×60 窗口均值 > 全局 mean+6σ」这条既有规则（更准），但它是**掩码边界上的行为变化**，
记录下来以备将来对照（若某天真要逐位对齐旧行为，可改回 float 累加）。

### 7.2 第三波**未做**的部分及原因

| 项 | 为什么没做 |
|---|---|
| **S5** 原生超时泄漏模型重做 | 属并发 + 生命周期改动（`solver_free` 与 detached worker 的所有权），改错就是 use-after-free。项目对 native 改动的既有标准是**先建 host 侧桥接测试**（§0.65 那次用 x86_64 主机 A/B 验证过），本机无 x86 编译器、无 Android 运行时，无法功能验证 → 不做盲改 |
| **S2** 星表外置二进制 | 多文件重构（8 个生成文件 + 名称表 + 访问路径 + `ArSkyProjector` 的触发时机），会影响冷启动路径，需独立设计与全量回归 |
| **S3 的 `abiFilters`** | 这是**发行策略决定**：声明 `abiFilters += "arm64-v8a"` 会让 32 位/x86 设备**装不上**（目前是装上后静默降级）。另一条路（补齐 32 位 .so）需要整套 astrometry 交叉产物，本机不具备 → 交开发者定 |

| **M7 权限分级 / M8 AR 重组** | 都要动 `CameraScreen.kt`（1600+ 行，且 `AGENTS.md` 有「须保持零每帧分配」硬约束），属设备侧回归项 |
| **M9** I18n 迁移资源系统 | 272 行 getter + 全部界面调用点，是一次专门的迁移 |
| **S9** targetSdk 35 | 本机缺 `platforms/android-35` 且网络受限（见 §6.1） |
