## 1. 问题（审计原文，读码确认成立）

`code/app/src/main/cpp/astro_bridge.c` 的超时路径：`quit_now` 置位后宽限期内仍未返回，
调用方 `pthread_detach(th)` 并放弃 `solver_free`（方向正确：线程可能还在读那块内存，
free 会 use-after-free）。**但被 detach 的 worker 只置 `job->done = 1`**：

- 不 `free(job)`、不 `solver_free(job->sp)`、不减 `g_leaked_threads`；
- 代码注释声称的 `leaked_thread_fn` 包装**在仓库里并不存在**（grep 全无）——承诺的接盘
  逻辑从来没写。

后果：**超时一次，整个进程永久进入不可回收模式** ——

- `solve_job_t`（含 solver 指针）永久泄漏；
- solver 及其持有的星点表（约百 KB）永久泄漏；
- `g_leaked_threads` 只增不减 → `release_indexes()` 此后**永久拒绝**回收 8 个 FITS 索引
  （实测合计 11.09 MB）。

## 2. 修复：单字所有权状态机

### 2.1 状态机（`solve_job_t.state`）

用一个原子字同时承担「完成通知 + 所有权移交」，取代原先单独的 `done` 标志：

| 状态 | 含义 |
|---|---|
| `JOB_RUNNING` | worker 在跑，**调用方**持清理权（正常路径） |
| `JOB_DONE` | worker 已返回且清理权仍在调用方（调用方 join + free） |
| `JOB_DETACHED` | 调用方超时让渡，**worker** 负责 `solver_free` + `free(job)` + 计数递减 |

**为什么必须是一个字**：分设 `done` / `handed_off` 两个标志时，worker 的"置完成"与
调用方的"取让渡"之间存在窗口，双方可能都认为自己该释放（double free）或都认为对方会
释放（继续泄漏）。单字 CAS 使这两个动作互斥：

- worker 收尾：`CAS(RUNNING → DONE)`；若换出的是 `DETACHED` → 自己 `solver_free` +
  `free(job)` + `g_leaked_threads--`；
- 调用方让渡：宽限期满后 `CAS(RUNNING → DETACHED)`；若换出的是 `DONE` → 说明 worker
  恰在此刻完成，清理权仍在自己 → 正常 `join` + `free`（不算泄漏）。

### 2.2 调用方必须"切断"（新引入的风险，必须同批处理）

接线之前：线程被 detach 后没人释放，调用方即使继续读 `sp`（`solver_did_solve`）也只是
"读一块没人释放的内存"。**接盘之后，worker 会在任意时刻 `solver_free(sp)`（连带释放
field）** —— 调用方若再读 `sp` / `field` 就是 use-after-free。因此：

- `run_solver` 在 `leaked` 分支**立即返回**，此后不再触碰 `sp`；星点数提前存入
  `nstars`（`solver_set_field` 之前），JSON 组装一律用 `nstars` 而非 `field->N`。

### 2.3 计数语义修正

`g_leaked_threads`：由「曾经泄漏过的次数（只增不减）」改为「**当前**仍在跑的 detach
线程数」——worker 退出时自行递减。索引回收闸门（>0 拒绝回收）语义不变（在飞时拒绝），
但泄漏线程结束后**可以重新放行**。

## 3. 主机测试（审计要求："必须补一条强制走 detach 路径的 native 测试"）

新增：

- `code/app/src/main/cpp/bridge_host_test.c` —— 直接 `#include` 被测源（取得 static
  函数可见性），为 astrometry.net 求解 API 提供桩实现（本测试只验证超时/所有权逻辑）；
- `tools/run_bridge_host_test.sh` —— 构建 + 运行（自动推断 JDK 的 `jni.h`；astrometry
  头文件路径可用 `ASTROMETRY_INCLUDE` 覆盖）。

四个场景 / 16 项断言：

1. **正常路径**：不标记泄漏、solver 由调用方释放（恰好一次）；
2. **强制让渡**（假 solver 故意忽略 `quit_now` 并睡过宽限期）：标记让渡、计数 +1 →
   worker 退出后**归零**、`solver_free` 由 worker 恰好一次；
3. **索引回收闸门**：泄漏线程在飞时**拒绝**回收（防 UAF）；线程结束后**放行**
   （旧实现永久拒绝）；
4. **让渡之后的正常求解**（回归）：行为与场景 1 一致。

**A/B 证据（证明测试抓得住旧 bug）**：对修复前的 bridge（`git show HEAD:` 取源，并把
假 solver 的睡眠调到超过旧版固定 5s 宽限期）跑同一套测试，恰好失败在审计描述的三处：

```
✗ worker 退出后计数应归零（实际 1）—— 旧实现只增不减
✗ 让渡路径应由 worker 恰好 solver_free 一次（实际 0）—— 旧实现零次（永久泄漏）
✗ 线程结束后应能回收索引（freed=0, index_free=0）—— 旧实现永久拒绝
```

修复后 **16/16 全过**。

## 4. `.so` 重编（修复必须进二进制才对用户生效）

用 NDK r26d + 迁移资产的交叉静态库重编 arm64 产物：

- **踩到并修掉一个坑**：服务器脚本 `/opt/build_so_server.sh` 缺
  `-Wl,-z,max-page-size=16384`（它早于 16KB 页那批工作），按其链接出来的 `.so` 是
  4KB 对齐 —— 直接替换会**破坏 Google Play 的 16KB 页要求**（旧包是 0x4000）。
  已按 `tools/build_so.bat` 的参数补齐重链，并**把这两个标志补进服务器脚本**（防复现）。
- 结果：`5,068,144 B`（旧 `5,067,976 B`）；`PT_LOAD` 对齐**全部 0x4000**；6 个
  `Java_com_starcam_*` 导出符号与旧包**逐一相同**（`nm -D` diff 为空）。

## 5. 未覆盖 / 风险

- **真机（arm64）未复测**：本批验证止于主机测试 + 二进制静态检查。建议真机补一次

  `leakedThreads` 回落 0、且之后 `releaseIndexes` 能真正释放索引；

  仍为 5.0s，行为不变；
- 计数器与 `release_indexes` 的闸门语义变化见 §2.3——保守方向不变（在飞时一律拒绝）。
