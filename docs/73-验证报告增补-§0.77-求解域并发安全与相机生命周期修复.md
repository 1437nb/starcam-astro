# §0.77 求解域并发安全与相机生命周期修复

> 本报告记录 2026-09-22 代码审查后的一批修复。审查范围：`code/app/src/main/java/`
> 全部 61 个 Kotlin 源文件 + `AndroidManifest.xml` + 构建配置。
> 审查结论：**算法核心可信**（单桶索引 / 有界 top-K / 分级星表域取向均无误），
> 问题集中在「星表域被实现成进程级可变全局状态」与「相机/渲染层的分配与生命周期」两处。
> 本次修复 A 类（高优先级）中的 6 条。

## 一、修复清单

### A1 离开相机页不解绑相机

**位置**：`ui/camera/CameraScreen.kt`

**问题**：`ProcessCameraProvider` 是 `LaunchedEffect` 内的局部变量，`DisposableEffect`
的 `onDispose` 拿不到它，只做了 `stopTracking` / `stopListening` / `analysisExecutor.shutdown()`。
而 `bindToLifecycle` 的 owner 是 **Activity**（相机页只是 Activity 内的一个页面），
切到结果页/主页时 Activity 并未销毁 —— 相机因此**从不自动解绑**。三个后果并发：

1. 相机常开 → 状态栏隐私指示灯常亮、持续耗电（用户可感知）
2. `ImageAnalysis` 仍每 5~8s 投递帧，向已销毁的组合状态 `post` 写入
3. 投递命中已 `shutdown()` 的 `analysisExecutor`（`RejectedExecutionException`），
   且未被回收的 `ImageProxy` 可能让 `KEEP_ONLY_LATEST` 分析流挂死、之后不再出帧

**修复**：新增 `cameraProviderRef: AtomicReference<ProcessCameraProvider?>`，
绑定前存入；`onDispose` 里 `unbindAll()`，并把 `shutdown()` 挪到解绑**之后**（顺序不能反）。

### A8 Pro 手动曝光在离开相机页时不清除

**位置**：`ui/camera/CameraScreen.kt`

**问题**：`clearCaptureRequestOptions()` 只在 `proMode` 切回 false 时调用。叠加 A1
（相机未解绑），离开时若 `proMode=true`，**AE 关闭 + 最长 30s 的手动快门会留在相机设备上**，
用户再次进入看到黑屏/极暗画面。

**修复**：`onDispose` 中若 `proMode` 则显式 `Camera2CameraControl.clearCaptureRequestOptions()`，
与 `proMode` 切回 false 时的处理保持一致。

### A3 切域锁只保护写入方（**本次唯一踩坑项，见第二节**）

**位置**：`astro/LocalStarMatcher.kt`

**问题**：`synchronized(domainLock)` 只包住「深域重试」这一次写入，而 `catalogMag()`
的 6 个读取点（三角形索引 `index()` / 验证网格 `catGrid()` / 打分表 `scoreTable()` /
假设展开 / 内点统计 `countInliers()`）**全在锁外**。两个真实调用点在不同线程上
（星图页 `ImageAnalysis` 分析线程 `CameraScreen.kt`、`StarSolver` 的 `Dispatchers.IO`），
代码层面没有任何东西阻止二者并行 —— 代码注释里「App 内求解本就串行」是**假设而非保证**。

危害不止「串域」：一次求解要读 6 次 `catalogMag()`，若线程 B 在 A 恢复域之前读到深域、
随后又变回浅域，**同一次求解内**就会出现「深域索引 + 浅域验证网格」，
涉及暗星的三角形被整体否决（§0.43 实测的形态）→ **静默 UNSOLVED**，比变慢难查得多。

**修复**：`runtimeCatalogMag`（对象级 `@Volatile`）+ `solveLock`；`match()` 整个包在
`synchronized(solveLock)` 内并转发给新增的 `matchLocked()`。`debugForceCatalogMag`
同时恢复为**只读覆盖**语义（此前被当成运行时域状态机用，污染了调试字段的语义）。

### A5 `indexCache` 是无锁读的普通 HashMap（v1.5.62 引入的回归）

**位置**：`astro/LocalStarMatcher.kt`

**问题**：v1.5.61 的「单槽缓存 + `@Volatile` 双检」本来是安全的；v1.5.62 换成
`HashMap<Float, StarIndex>` 后，`@Volatile` 只保证引用发布的可见性、不保证 `HashMap`
内部结构安全，而读取在锁外、写入在锁内 → 真正的数据竞争。最坏情况是重复构建一次
9.3s 的深域索引 + 一次额外的大对象分配。

**修复**：改 `ConcurrentHashMap`，双检保留（保证 9.3s 的深域构建只发生一次）。

### A4 `projMap` 是整份死重量

**位置**：`astro/LocalStarMatcher.kt`

**问题**：`projMap`（§0.71b 投影感知键）每三角形写 **9 个桶**，而它的唯一消费者
`queryCandidates` **全仓零调用点**。全仓 `grep queryCandidates|projMap` 在
`LocalStarMatcher.kt` 之外零命中，文件内 `queryCandidates` 只有定义、没有任何调用。

9 桶 × 55.6 万三角形 ≈ **500 万条引用** —— 这个数字与 `PROGRESS.md` 记载的
「mag≤6.5 → 5,000,886 条」精确吻合。即：**当年被判定内存不可行的那部分，
被完整保留成了永不查询的死数据**，如今还多了一个域、常驻进程。

**修复**：删除 `projMap` 字段、构建逻辑、`queryCandidates`，以及只服务它的
`projectedRatios` / `unitVec` / `tanAbout` 三个函数；清理 3 处互相矛盾的注释。
顺带省掉索引构建时每三角形一次的 gnomonic 计算。

### A2 深域兜底没有准入闸门

**位置**：`astro/LocalStarMatcher.kt` + `ui/camera/CameraScreen.kt`

**问题**：深域重试的触发条件只是「浅域整条阶梯无解」，而这个词对**任何**失败帧都成立
—— 白天的预览帧、室内、纯噪声帧。相机预览是每 5~8s 一次的长驻循环，所以
「只在失败路径付一次」实际是「**每个失败帧都付一次**」：首帧付索引构建，
之后每帧跑一遍 16 倍候选密度的深域阶梯。而预览用的是主摄广角（≈67°~77°），
本就落在浅域覆盖的宽场里 —— 深域是给 ≤30° 窄场照片兜底的。

**修复**：`match()` 新增 `allowDeepRetry: Boolean = true`；预览路径
（`CameraScreen.kt` 的 `ImageAnalysis` 回调）传 `false`。
**默认 `true` 是刻意的**：`StarSolver` 的照片求解路径与全部现有测试行为逐位不变。

## 二、踩过的弯路：ThreadLocal 与投票轮的线程池

A3 的第一版实现选了 `ThreadLocal<Float>`，理由是「按线程隔离天然免锁」。
**这是错的**，而且错得很隐蔽 —— 它让 apod3 从「解出 8.5° / 20 内点」退回 UNSOLVED。

根因：投票轮内部**并行执行**：

```kotlin
val pool = Executors.newFixedThreadPool(chunkCount)   // LocalStarMatcher.kt:1572
futures.add(pool.submit(Callable { voteChunk(local, work, from, to, idx, maxSide) }))  // :1579
```

`ThreadLocal` 在 worker 线程上会退回 `initialValue()`，也就是 `PROD_CATALOG_MAG`（**浅域**）。
于是深域兜底时主线程按深域取索引、worker 却按浅域口径工作，深域阶梯静默失效。

**结论**：星表域是**整次求解的属性**，不是线程的属性 —— 必须让所有参与线程看到同一个值。
线程隔离与「求解内部有并行」这两件事从根本上冲突。

最终方案「对象级状态 + 求解入口互斥」同时满足两条约束：
域在一次求解内稳定（worker 与主线程同值），且两个并发求解不会互相改域。

## 五、影响与风险

- **行为不变性**：`allowDeepRetry` 默认为 `true`，`StarSolver` 与全部现有测试走原路径；
  A4 删除的是零调用点的死代码；A5 只换容器类型。宽场 `photo12` 12/12、窄场回归、
  `apod3` 真值断言均无退化。
- **A3 的代价**：并发求解现在会排队。考虑到预览路径已关掉深域（A2）、浅域求解在秒级，
  最坏情况是预览的浅域求解短暂等一次照片求解。
- **未做真机验证**：A1/A8 需要真机确认隐私指示灯与 Pro 模式恢复正常；
  A2 的收益（预览不再每帧跑深域）也建议在真机上看识别耗时日志确认。
- **内存收益未实测**：A4 删掉的 500 万条引用按 `PROGRESS.md` 对 96 万三角形 ≈ 59MB 的
  估算外推，应在 30~60MB JVM 堆量级，但**本次未做实测**，建议在真机上用
  Android Studio Profiler 或 `dumpsys meminfo` 对比。
