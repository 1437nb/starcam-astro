# 86 · 验证报告增补 §0.102 —— 并发日志归属与失败现场防碰撞（P0-2.4）

> 版本：v1.5.75（工作区，未发布）
> 日期：2026-10-09
> 来源：外部审计报告（2026-10-06）P0 第 2.4 条 +《待修清单（核实版）》§2.4
> 说明：承接 §0.100（P0-2.1）、§0.101（P0-2.2/2.3），同为批量识别链路的并发正确性修复。

## 1. 问题（审计原文要点）

1. **日志行无归属**：`SolveLogStore.line(context, msg)` 不带任何 per-solve 标识；
   `StarSolver` 只有**首行**带照片名。批量识别自 §0.96 起两 worker 并行，两条求解的
   日志行会**互相穿插**，事后无法按行归属（v1.5.74 release note 自认的"已知边界"）。
2. **失败现场同秒互相覆盖**：目录名 `fail-yyyyMMdd-HHmmss` 只有**秒级**精度 ——
   两个 worker 同一秒失败会写进同一目录，`report.json` 与 `input.gray.gz` 同名直接覆盖，
   最终可能得到"报告来自照片 A、像素来自照片 B"的**缝合怪现场**。

## 2. 改动

### 2.1 `data/SolveLogStore.kt`

- **求解会话**：`beginSolve(imagePath): Session`
  - `solveId = "S%03d"`，由进程内 `AtomicInteger` 递增 —— 并发开会话不重号（批量两 worker 实测）；
  - `Session.prefix = "[S042][photo5031.jpg] "`（照片名**只取文件名**，隐私约束不变）；
  - `Session.line(context, msg)`：该次求解的**每一行**都带上前缀；
  - `Session.dumpFailure(...)`：目录名与报告都带 solveId。
- **失败目录命名**（新纯函数，便于单测）：
  `failDirName(ts, solveId) = "fail-<yyyyMMdd-HHmmss>[-<solveId>]"`
  - 带 solveId 后**同秒也撞不上**；
  - 无 id 时退化为旧格式（向后兼容未接会话的调用方）。
- `dumpFailure(..., solveId, ...)`：报告内写入 `solveId` 字段，便于 report.json 与日志行、
  与界面上的同一次求解对上号。

### 2.2 `astro/StarSolver.kt`

- `solve()` 入口创建会话（`val log = SolveLogStore.beginSolve(imagePath)`）；
- 9 处日志行改走 `log.line(...)`；失败转储改走 `log.dumpFailure(...)`。

### 2.3 有意未改 / 未采纳

- `CameraScreen` 的"AR 预览分析异常"行**不带会话前缀**：它不是求解会话，已有独立语义，
  且按分钟节流，保持原样；
- 首行 banner 仍保留照片名（`=== 开始识别 photo5031.jpg …`），与新前缀重复一次 ——
  保留是为了兼容既有文档引文与开发者的阅读习惯；
- **未采纳审计标注为"更优"的"内存缓冲、结束整段原子追加"**：现设计是**立即落盘**，
  进程被杀/崩溃时**已经写下的行仍在**，这正是诊断转储的核心价值；缓冲会以
  "崩溃丢日志"换取"行序整齐"。前缀已经解决了"按行归属"这个真问题，
  故本批不做缓冲，如实记录此取舍。

## 3. 验证

1. **新增 4 项单测**（并入 `SolveLogStoreTest`）—— **本机用真实编译器 + JUnit 直跑
   13/13 通过**（原有 9 项 + 新增 4 项）：

   ```
   JUnit version 4.13.2
   .............
   OK (13 tests)
   ```

   - `solveId` 唯一、格式 `S001…`、前缀含照片名且**只取文件名**；
   - 照片名 null / 纯空白时前缀只含会话号；
   - **8 线程 × 100 次并发开会话 → 800 个 ID 全部唯一**（模拟批量两 worker 上限场景）；
   - **同秒不撞**（P0-2.4 核心回归）：同一 `LocalDateTime` 下 `S001` 与 `S002` 的目录名
     不同；无 id 时退化为 `fail-<时间戳>`。
2. 语法/引用检查：`SolveLogStore.kt` + `StarSolver.kt` 一起编译 —— **0 语法错误**，
   会话 API（`beginSolve` / `Session.line` / `Session.dumpFailure` / `failDirName`）
   的调用全部解析通过。
3. **CI（GitHub Actions）**：`unit-test` **全绿** —— run `37889956652`，
   **23 类 / 198 项 / 0 失败 0 错误**（含本报告新增 4 项，`SolveLogStoreTest`
   现为 13 项）；`secret-scan` 通过。
4. 本机限制（如实说明）：服务器 1.87GB 内存跑不了 Gradle；落盘路径（真实目录创建、
   gzip 写出）依赖 Android Context/外部目录，沿用既有测试边界 —— 靠端到端手工验证。

## 4. 未覆盖 / 风险

- **真机建议补测一条**：批量 ≥2 张、刻意制造同秒失败，确认日志目录出现
  `fail-<时间戳>-Sxxx` 两份互不覆盖的现场（本机无法造 Android 落盘环境）。
- 日志行新增 `[Sxxx][照片名]` 前缀后视觉噪音略增（换来可过滤 + 可归属）；
  文档中引用的旧格式日志行与今后的新日志会略有差异，属预期。
- 失败现场仍保留最近 10 份（`MAX_FAIL_DIRS`），沿用不变。
