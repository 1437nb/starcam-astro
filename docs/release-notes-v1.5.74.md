# StarCam v1.5.74 更新说明

**主题：识别提速 —— 74 秒变回约 5 秒；批量识别并行；版本号随处可查**

## 背景：一条"绕远路"的识别链

上一版（v1.5.69）已经能识别那张 76° 欠曝广角照片，但在真机上要 **74 秒**。开发者的识别日志
把时间去向摊开得很清楚：

```
19:20:00  提星：… 全图检出177颗 / 取最亮177颗 …            ← 3.1 秒，很快
19:20:44  内置星表：主星表(172颗)浅域未匹配，改用 box-blur 备用星表(28颗)命中
19:20:45  内置星表成功 · 内点 16 颗 耗时=46451ms
```

- 负责"提星"的那一步只用 **3 秒**；
- 真正吃掉时间的是**主星表那条路**——它把投票轮的五轮阶梯全部跑完，**66 秒**之后仍然解不出；
- 而**另一张更小的星表（box-blur，28 颗）2.1 秒就解出来了**。

也就是说：解药一直就在手边，只是排在一条死路后面。

## 修复

### 1. 星表选择顺序：便宜的先试（§0.97 / §0.97b）

本地引擎现在**先用 box-blur 星表**（星少、阶梯短、成本低），**SEP 星表降为备用**
（检出能力更强，弱星场景仍然兜底；它需要通过既有的"与 box-blur 重合率 ≥30%"核验才参与）。

这不是拍脑袋的顺序调整：**项目本地的真值回归台（12 张演示照、假阳性对照、窄场台）
本身就是用 box-blur 星表跑的** —— 换过来之后，生产路径与回归保护的口径终于一致了
（此前"生产跑 SEP、回归跑 box-blur"，回归其实没有在保护生产的那条路）。

> 开发过程中的一段插曲值得记下：第一版改动因为 Kotlin 的"try 块取末表达式"取值方式，
> 把**预览用的星表**当成了匹配输入，导致备用机制静默失效、真机反而退化到 230 秒。
> 该问题**只在内部调试包中出现**，从未进入任何发布版本；修复时同时加了一道自查——
> 若"备用表与主表是同一个对象"，提星诊断会直接打印 `【内部告警：备用表与主表相同，
> 备用机制将失效】`，这类失效再也藏不住（详见 `docs/83` §6）。

### 2. 批量识别并行（§0.96）

勾选多张照片批量识别时，原先是一张一张串行处理，现改为**有界并发**：任务队列 + 2 个
工作协程（**低内存设备自动退回串行**）。并发度按内存而不是按核数定——每张"在飞"的照片
峰值约 30~80MB（2200px 位图 + 求解中间数组 + 渲染输出）。

可行性是逐项核实过的：原生求解器每次调用自带任务对象（非全局静态）、索引加载有互斥且
在求解前释放、历史的统计与识别日志都已线程安全。

### 3. 版本号随处可查（§0.99 / §0.99b）

- **设置页标题栏下方**常显「版本：x.y.z」（不用滚动、不依赖任何折叠状态）；
- **识别日志的第一行**带上版本：`=== 开始识别 photo… App=v1.5.74` ——
  以后反馈问题时，日志本身就是"跑的是哪一版"的答案。

## 验证

- 12 张真实照片回归 **12/12 正确解出、0 假阳性**；假阳性对照（apod3/apod5/pleiades
  必须保持未解出）全部通过；合成回归 3/3（含**窄场 12° 与中场 20°** 两个必须靠深域
  兜底的用例）。
- CI（GitHub Actions）全套通过；原生库本版未改动。
- 真机实测：由开发者确认。

## 已知边界（如实记录）

- **失败路径上"深域重试"仍可能白跑最多 60 秒**：深域是给 ≤30° 窄场兜底的，宽场照片走深域
  在数学上过不了门。曾尝试按密度换算加一道闸门直接跳过，但判据（浅域最优候选的画面内
  星数）会被尺度坍缩的伪候选污染，实测会让窄场误伤，已回滚。要做需要先有可信的视场估计。
- **识别日志的每行不带照片名**：多张照片同时识别时无法按行归属，有待补上。
