## 1. 真机日志给出的决定性证据

开发者提供的识别日志里，5031 那次**干净**的尝试（无其他照片并发）：

```

00:54:11.563  提星：sep=2.0σ 全图检出177颗/取最亮177颗（边界剔除5颗→172颗） flux=1.1~133.2

00:55:23.143  内置星表成功：内置星表 · 内点 12 颗 scale=124.69" 耗时=74770ms
```

拆开看：

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 解码 + SEP 提星 + box-blur 检测 | **3.1 秒** | 快，不是瓶颈 |
| 主星表（SEP 172 颗）走完它那条路 | **约 66 秒** | 投票轮五轮全跑 + 打分轮试探，**仍解不出** |
| 备用星表（box-blur 28 颗） | **2.1 秒** | **一次就解出**（内点 12） |

其余 11 张照片：**1.3 ~ 12.5 秒**解出（因为它们的投票轮在前几轮就命中，不用跑完）。

**结论**：问题不在"提星"，也不在"备用机制没生效"——备用机制**生效了**（2.1 秒解出），
只是它排在一条 66 秒的死路**之后**。而 §0.89 那个"低成本试探"只限制了**打分轮**的候选数
（2000），**投票轮阶梯没有上限**，于是 SEP 那条路照样能烧掉 66 秒。

另外可换算出一个关键常数：同一套代码在开发机上跑 5031 的整条链只要 ~5 秒，真机 66 秒 ⇒
**这台真机约比开发机慢 13 倍**。这解释了为什么"本地 1~5 秒"的事，到手机上就是几十秒。

## 2. 改动：首选换成便宜的那张表

`StarSolver` 的本地引擎分支不再把 SEP 表当首选，而是：

- **首选 = box-blur 表**（星少、阶梯便宜；本例 28 颗）；
- **备用 = SEP 表**（检出能力更强，弱星场景仍兜底——需通过既有的 §0.72 重合率核验，<30% 则不参与）；
- 两者都失败才进深域重试（顺序不变）。

### 为什么可以换（不是拍脑袋）

1. **本地真值回归台本来就是用 box-blur 表跑的**：12 张演示照、假阳性对照（apod3/apod5/
   pleiades 必须保持 UNSOLVED）、窄场台，全部以 `detectStarsGray`（box-blur）为检测器。
   换过来等于**让生产首选与回归保护口径一致** —— 以前"生产跑 SEP、回归跑 box-blur"，
   回归其实没在保护生产的那条路。
2. **成本不对称**：box-blur 表 ≤100 颗（本例 28），SEP 表最多 200 颗（本例 172）；投票轮
   的阶梯成本随工作集与命中桶数膨胀，表越小越便宜。
3. **能力不丢**：SEP 表降为备用后，弱星/暗场照片仍会在首选失败后用到它（含其完整阶梯）。

## 4. 本次日志暴露的另两处问题（未修，已有方向）

## 5. 追加：深域闸门尝试**失败并已回滚**（§0.98 未落地）

拿到第二张真机失败页后（浅域 `cand=20016 scored=20000 work=45 ms=21059 CUT=cap`、
最优 8/206；深域 `CUT=time` 白跑 60 秒），我按 §0.87 的密度换算试着加一道**算术闸门**：
若 `minAlignRate × 密度比 × inFrame_shallow > 工作集上限(45)`，则深域在数学上不可能过门，
直接跳过 —— 按 5031 的数据（inFrame_shallow=206）能省掉那 60 秒。

**实现后发现判据不成立，立即回滚**：`SyntheticRegressionTest` 的
**窄场 12° 与中场 20° 用例当场变成 UNSOLVED** ✗（宽场 65° 不受影响）。

根因：我用的 statistic（浅域打分轮**最优候选**的 inFrame）**被尺度坍缩的伪候选主导** ——
浅域失败时那个"最优候选"通常是塌缩型伪解，它的 inFrame 很大，与该照片的真实视场无关。
于是闸门把**该走深域的窄场**也一并挡掉了。

**结论**：在匹配器内部做这道闸门，需要一个**可信的视场估计**（不是"最优候选的 inFrame"）——
可行方向是让调用方把视场传进来，或用已匹配三角形的隐含尺度反推。这属独立题目，不做半成品。

回滚后复验：窄场 12° / 中场 20° / 宽场 65° 三个合成用例全部恢复 SOLVED；12 张演示照
12/12、0 假阳性；CI 口径 21 类 / 175 项 / 0 失败；`LocalStarMatcher.kt` 与提交零差异
（回滚到源码级干净）。

**因此那条 60 秒的深域浪费仍在**（如实记录）：在 §0.97 的新顺序下，它只在
"box-blur 表也失败"时才发生。

## 6. §0.97 **本身引入过一个回归**，已修（§0.97b）

真机日志（01:31 / 01:56 两次 5031）显示：§0.97 装上后 5031 从「2.1 秒解出」退化成
**230 秒 / 320 秒失败** ✗。指纹是失败行里的 **「星点 172 颗」** —— 喂给匹配器的其实是
SEP 那张 172 颗的表，而不是我"首选"的 box-blur 表。

### 根因（我自己的 Kotlin 控制流错误）

`StarSolver` 的本地引擎分支是 `val stars = try { … }`，而 **try 的值取最后一个表达式**。
我把末尾那个表达式同时用作了"给界面预览的列表"，并且在 §0.97 里特意把它设成**更全的
SEP 表**（预览更饱满）—— 于是：

1. `stars` 变成 SEP 表（172 颗），**首选被顶掉**；
2. `fallbackDetected` 也是 SEP 表 → 匹配器里 `fallbackDetected !== detected` 为假
   → 判定「**没有备用**」→ box-blur 表**从未被使用**（备用机制静默失效）；
3. 结果：SEP 表那条 60 秒的路照跑，深域再 60 秒，官方引擎再兜底失败 → 230 秒失败。

而**提星诊断行打印的是"意图"（首选 box-blur(28颗)，备用SEP(172颗)）**，与"实际匹配输入"
（172 颗）不一致 —— 日志里那两行放在一起就是铁证。

### 修复（§0.97b）

1. 引入显式变量 `chosen` 并在 try 末尾显式返回它 —— **不再依赖末表达式**；
2. 新增自查：若"备用表与主表是同一个对象"，提星诊断行追加
   `【内部告警：备用表与主表相同，备用机制将失效】` —— 这类失效再也藏不住。

### 为什么本地回归没发现

本机测试直接调用 `LocalStarMatcher`，**不经过 `StarSolver` 的设备分支**（那条路要 Android
的位图与检测）—— 所以"哪张表被传进去"这件事没有任何本地覆盖。这次是靠真机日志里的
「星点 N 颗」抓出来的。

### 验证（修复后）

12 张演示照 `true=12 false=0 miss=0`；合成回归 3/3（含 **窄场 12°、中场 20°** 两个必须靠
深域兜底的用例）；`FallbackStarListTest` 2 项；CI 同口径 175 项 0 失败。

预期真机：5031 ≈ 提星 3.1 秒 + box-blur 表 2.1 秒 ≈ **5 秒**；失败行（若有）里的
「星点 N 颗」应显示 **28**（真实匹配输入）。
