# 验证报告增补：§0.64 检测上限提升与投票阈值量纲兼容 v1.5.54

## 一、问题（用户 2026-09-14 报告）

用户手机拍的原始星空照片**识别不了**；在相册里把**对比度拉到最高**后，
同一张照片**可以识别**。

提供两张截图：
- 失败：识别结果页显示「内置星表 → 官方引擎」两轮全败，**检测到 40 个星点**；
- 成功：相册编辑导出的版本（1650×2200 竖版）叠加正确。

## 二、本地复现的结论：无法复现

在开发机上穷尽了各种复现路径，**全部稳定解出**（内点 24~25）：

| 复现方式 | 结果 |
|---|---|
| 原始 `.gray`（2200×1650，从 4096 直缩） | SOLVED inl=25 |
| 精确复刻 app 解码链路（4096 →inSampleSize=2→ 2048 →放大→ 2200） | SOLVED inl=25 |
| 检测星数 30 / 35 / 40 / 45 / 50 / 60 / 80（覆盖截图里的 40） | 全部 SOLVED inl=25 |
| 相册对比度 ×1 / ×2 / ×3（`ImageEnhance.Contrast`） | 全部 SOLVED inl=24~25 |
| 直方图自动拉伸（autocontrast） | SOLVED inl=25 |
| 横版 vs 竖版（EXIF 旋转两种朝向） | 均 SOLVED |
| 模拟 SEP flux 量级（brightness 折算为净流量，缩放 8~30 倍） | 全部 SOLVED inl=25 |

检测质量本身也良好：**检出的前 40 颗里 39 颗是真实星表星（97.5%）**，
前 100 颗 99% 命中。星表覆盖充足（§0.62 已证该天区 mag≤4.0 有 25 颗）。

**结论：这不是算法在本机可复现的缺陷，而是真机环境特有的差异。**
需要失败原图才能在开发机精确重放（见 §六 新增诊断转储）。

## 三、从截图能确定的关键事实

1. **"40 个星点"= `detectStars` 的旧默认上限**
   （`StarSolver` 回退分支调用 `detectStars(currentDisplay)` 用默认值 40，
   而 SEP 路径上限是 200）。
   → 说明真机上 **SEP 提星失败并回退到了 box-blur 检测器**，
   这与 §0.20 记录的已知问题一致（部分机型 ROM 上 `.so` 内 simplexy 提星 0 颗）。

2. 官方引擎同样失败 —— 但官方引擎有 `extStars`（JVM 提星）兜底，
   两者都失败说明真机喂入的像素与开发机不同。

## 四、本轮落地两项确定收益的改进

### 4.1 检测上限 40 → 100

40 是宽场欠曝照片的瓶颈：只保留最亮 40 颗时 mag 5~6 的星被截断。

实测（12 张离线演示照片，`gray12` 素材）：

| 照片 | n=40 内点 | n=100 内点 |
|---|---|---|
| 5040 | 37 | **51** |
| 5092 | 19 | **24** |
| 4974 | 35 | **36** |
| 4984 | 51 | **52** |
| 5049 | 19 | **23** |
| 5087 | 9 | **11** |

上限不宜超过 150：**apod5（假阳性对照样本）在 n≥150 时会被噪声星凑出
6 内点的假解**（实测 n=150/200 均误报 SOLVED ra=57.5 dec=24.9）。
取 100 是在"多检出暗星"与"不引入假阳性"之间的实测平衡点。

### 4.2 投票阈值量纲兼容

`voteThresholds` 的"头部陡峭"判据原用**绝对数**（`≥900 的星数 ≥10`）。
该 900 是按 box-blur 检测器的亮度量级（连通域灰度和，~数千）标定的；
而 SEP 路径喂入的是 simplexy 的 **flux**（背景减除后的净流量，量级小得多），
绝对判据在 SEP 下恒不成立 → sharp 通道形同虚设。

现补一个**相对形态**判据作为兜底：头部陡峭与否只看「第 20 亮星 / 最亮星」的比值
（≥0.55），与检测器量纲无关；相对判据生效时 sharp 阈值也按最亮星比例给出
（`top × 0.20`，等价于原 900/典型最亮 4154 ≈ 0.22）。

## 六、新增诊断转储（用于定位真机问题）

`StellarSolverNative.dumpLocalFail()`：本地匹配失败（或低内点被官方复核拒绝）时，
把**匹配器实际吃到的像素**与**检出的星点列表**落盘（仅 debug 构建）：

- `local_fail_latest.gray`：int32 宽 + int32 高 + float32 灰度（与测试台同格式，可直接重放）
- `local_fail_latest.txt`：note / 尺寸 / 检出星数 / 每颗星的 x,y,brightness

位置：应用外部文件目录（`Android/data/com.starcam.astro/files/`）。

与既有的 `gray_dump_latest.gray`（官方引擎失败转储，§0.28）互补 ——
此前只覆盖官方引擎路径，本地匹配器失败没有任何数据留存，
这正是本次无法定位真机问题的原因。
