# 验证报告增补：§0.69 官方引擎星点来源优先级缺陷 —— 修复 74° 广角照片识别失败 v1.5.58

## 一、问题（用户 2026-09-17 报告，延续 §0.64）

用户手机（REDMI Turbo 5 Max）拍摄的星空照片**识别不出来**；在相册里把**对比度拉到 100%**
后「能识别」。用户强调「这个 bug 依然没有被修复」——§0.64 曾把同类报告判为
「真机特有、开发机无法复现」。

**本轮的不同点：用户提供了原始照片文件**（3071×4096，30s / f1.5 / ISO100 / 26mm 等效，
2026-09-12 01:25 拍摄），在开发机上**直接复现了失败**。§0.64 无法复现的原因随之明确：
那次拿到的是截图而非原图。

## 二、独立真值（astrometry.net 0.97 官方 `solve-field`）

在构建服务器上把 astrometry.net 0.97 编译成 x86_64 主机版（`/tmp/host-an`），用与 App
相同的尺度先验区间求解同一张照片：

| 项 | 值 |
|---|---|
| 中心 | RA 0.6586° / Dec 23.1894° |
| 视场 | **51.9° × 66.0°**（原图帧）；App 帧（1649×2200）≈ 56.4° × 75.2° |
| 比例尺 | 66.09″/px @3071px → 123.04″/px @2200px |
| **nmatch** | **141**，log-odds **765**，index 4118 |
| 提星 | **simplexy 找到 4478 个源** |

**这与旧照片（南宁 74° 秋季四边形）是同一片天区**（中心相距仅 0.022°），
旧照片能解、新照片解不出 —— 排除了「天区冷门」「星表覆盖不足」。

## 三、根因：官方引擎被喂了 40 颗星，simplexy 被完全跳过

### 3.1 对照实验（决定性）

用官方 `solve-field` 控制变量：

| 输入 | 结果 |
|---|---|
| simplexy 全量（4478 源） | ✅ **solved**，nmatch=141 |
| `--objs 40`（只取最亮 40 个源） | ❌ **did not solve** |

App 恰好走的是**后一条路**。原因在 JNI 桥接层（`astro_bridge.c`）：

```c
/* 星点来源优先级：外部星点 → simplexy */
if (ext_stars) { ... field = starxy_new(ext_n, ...) ... }   /* ← 先 */
if (!field) { field = detect_stars(...); }                   /* ← 后，被跳过 */
```

只要 Kotlin 侧传了 ≥4 颗外部星点，`.so` 里的 simplexy **永远不会运行**。
而 Kotlin 侧（`StellarSolverNative.kt`）传的是：

```kotlin
LocalStarMatcher.detectStars(bitmap, 40)   // ← 上限写死 40
```

### 3.2 这段「外部星点优先」是怎么来的（为什么不能简单怪它）

2026-08-30 真机观察到部分 ROM 上 `.so` 内 simplexy 提星 0 颗，当时为**绕开**该问题
把外部星点放在了前面 —— 属于合理的临时兜底。

**但 §0.65 已经查明「提星 0 颗」的真因**：`simplexy_set_defaults()` 内部是
`memset(整个结构体)`，而桥在它之前填了 `image/nx/ny` → 三个字段被清零（外加
`simplexy_free_contents` 非法 free JNI 指针、成功判据 `rc` 语义反了）。三处修复后
simplexy 完全正常。

**遗留问题：「外部星点优先」这条绕行逻辑没跟着撤。** 于是修复了 simplexy 反而带来
副作用 —— 它提出的数千颗星被 40 颗外部星点挡在门外。

### 3.3 为什么 40 颗不够（量化）

广角欠曝照片里，能被 App 的 JVM 检测器排进前 40 的几乎全是 mag ≲ 4 的亮星：

- 该天区 mag≤4.0 的星表星有 **27 颗**，但检测端只找到 **10 颗**；
- 检测到的 170 颗里，**46 颗是 mag 4.5~5.5**（全部落在索引域 mag≤4.0 之外）；
- astrometry 索引（4100 系列）本身覆盖到更暗的星，simplexy 能提出 4478 个源 ——
  **它不缺星，是被我们挡住的**。

## 四、修复

### 4.1 桥接层（`astro_bridge.c`）：恢复 simplexy 优先

```c
starxy_t* field = NULL;
starxy_t* ext_field = NULL;
/* 外部星点先构造好但**不立即采用** */
if (ext_stars) { ... ext_field = starxy_new(ext_n, ...) ... }

field = detect_stars(gray, w, h, plim_override, ...);   /* simplexy 优先 */
if (field && field->N >= 4) {
    if (ext_field) { starxy_free(ext_field); ext_field = NULL; }  /* 丢弃外部星点 */
} else {
    if (field) { starxy_free(field); field = NULL; }
    if (ext_field) { field = ext_field; ext_field = NULL; }        /* 兜底 */
}
```

外部星点**保留兜底能力**（simplexy 真的失败时仍然顶上），但不再抢占优先权。
两条路径都不泄漏 `ext_field`。

### 4.2 Kotlin 侧：兜底星点上限 40 → 200

`StellarSolverNative.solveBitmapImpl` 里传给引擎的 `extStars` 上限从 40 提到 200
（与 `sepDetectStars` 默认值同量级），避免兜底路径本身星点过少。

## 六、构建环境迁移：从服务器回到本机（本次一并完成）

用户要求「所有编译必须在本机运行」。已完成：

**关键前提（实测发现）**：Windows 版 NDK clang **可以直接链接 Linux ELF 格式的
`.a` 静态库** —— 不需要 WSL、虚拟机或 Linux 环境。这一条打通后，`.so` 构建就能
完全落在本机。

迁移的资源（放在工程外，不入库）：

```
C:\dev\astrometry-local\
  ├── src\include\astrometry\     astrometry 0.97 头文件（145 个）
  ├── lib\{solver,util,catalogs,libkd,qfits-an,gsl-an}\*.a   8 个静态库
  └── cross\{lib,include}\        cfitsio 3.47 交叉产物
```

新增构建脚本 `tools/build_so.bat`（Windows 批处理，CRLF 行尾）：
```bash
cd C:\starword && tools\build_so.bat [输出路径]
```

实测：本机构建 `.so` 耗时 **不到 1 分钟**，产物 5,067,816 字节、6 导出符号齐全、
符号总数 2780（与服务器产物完全一致）。本机构建 APK **3 分 16 秒**（服务器需
数分钟且受 1.8GB 内存限制、多次 OOM）。
