## 1. 问题

### P0-2.2：用中文文案前缀判成败

原实现（`ui/batch/BatchScreen.kt`）：

```kotlin
val ok = !note.startsWith("未能") && !note.startsWith("无法") &&
         !note.startsWith("渲染") && !note.startsWith("处理")
```

把 **UI 文案当作控制流契约**。后果是"静默错判"：改一句文案、加个标点、或界面切到英文
（本项目 I18n 是**运行时切换**的，文案随时会变）——判据就失效了，而且不会报错，
只会把成功显示成失败（或反之）。等于把"随时会爆"的引线焊在主流程上。

### P0-2.3：保存失败仍计入"已导出"

原实现（同文件）：

```kotlin
saved.incrementAndGet()          // 无条件执行
loc ?: "已识别但保存相册失败"     // 只生成文案，不影响计数
```

计数器只有一个且**无条件自增**，汇总文案"已选 N 张 · **成功并导出** M 张"在
相册写入失败时说了假话——用户以为导出了，相册里其实没有。

## 2. 改动

### 2.1 新增 `ui/batch/BatchOutcome.kt`（纯 JVM，可单测）

- `sealed interface BatchOutcome`：`Saved` / `SolvedButSaveFailed` / `SolveFailed` /
  `ProcessingFailed`，各带 `note`（**仅供显示**），另有派生属性 `solved` / `exported`；
- `class BatchTally`：三计数 `solved` / `saved` / `failed`（原子计数，两 worker 并发记账）
  与 `snapshot()`；
- `data class BatchCounts`：供界面状态更新的计数快照。

分类依据是**失败发生在哪一步**（决定用户该做什么）：

| 原字符串（改动前） | 新类型 | 含义 |
|---|---|---|
| 无法读取照片文件 | `ProcessingFailed` | 解码失败（识别之前） |
| 未能识别（亮星不足或视场不支持） | `SolveFailed` | 识别本身没解出 |
| 渲染失败（结果缺坐标系） | `ProcessingFailed` | 识别之后、导出之前的处理失败 |
| 处理异常：… | `ProcessingFailed` | 未知异常 |
| （保存成功） | `Saved` | 识别 + 导出都成功 |
| 已识别但保存相册失败 | `SolvedButSaveFailed` | 成果可用但**没落到相册** |

### 2.2 `BatchScreen` 接线

- `processOne` 返回 `BatchOutcome`（不再是 `String`）；
- 列表状态由**类型映射**：0 排队 / 1 识别中 / **2 已导出** / 3 失败 /
  **4 已识别·未导出**（新增；保存失败不再显示成 "✓ 已导出"）；
- 计数改由 `tally.record(outcome)` 按类型记账；汇总改用三计数。

### 2.3 `I18n.Batch`

- `summary(total, solved, saved, failed, finished)`：中英双语按三计数显示
  （"已选 N 张 · 识别成功 X 张 · 已导出 Y 张 · 失败 Z 张"，失败为 0 时不显示该段）；
- 新增 `solvedNotExported`（"已识别 · 未导出" / "Solved · Not exported"）。

**有意的可见行为变化**：保存失败的照片此前在列表里标 "✓ 已导出"（自相矛盾，因为同一条目
下方还写着"已识别但保存相册失败"），现在标"已识别 · 未导出"，汇总也不再把它算进"已导出"。
