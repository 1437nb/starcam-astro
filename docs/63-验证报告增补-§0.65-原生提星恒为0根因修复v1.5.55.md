# §0.65 原生提星恒为 0 的根因修复（v1.5.55）

> 修复日期：2026-09-17
> 涉及文件：`app/src/main/cpp/astro_bridge.c`、`app/src/main/jniLibs/arm64-v8a/libstellar_solver.so`
> 上一版已知问题：用户真机照片「原图识别不了，相册拉高对比度才能识别」，
> 当时归因于「部分真机 ROM 上 .so 内 simplexy 提星 0 颗（疑 arm64 数据竞争）」。

## 1. 结论先行

**「真机 ARM64 数据竞争」是误判。** 真正原因是 `astro_bridge.c` 里三个确定性
C 层缺陷，其中前两个互相掩盖，在 x86_64 上 100% 复现，与 CPU 架构无关。

| # | 缺陷 | 后果 |
|---|---|---|
| A | `simplexy_set_defaults()` 内部是 `memset(整个结构体)`，而桥**先**填 `image/nx/ny`、**后**调它 | 三个字段被清零 → `simplexy_run` 面对 NULL 图像 → 提星恒 0 |
| B | `simplexy_free_contents()` 会 `free(s->image)`，而 `s.image` 指向 `GetFloatArrayElements` 返回的 ART 堆指针 | 对 JVM 托管内存非法 `free` → 修好 A 之后立刻会踩这个 |
| C | `extract_stars_impl` 用 `if (rc != 0 \|\| npeaks <= 0)` 判失败，但 `rc=0` 才是失败（`dmask` 未标记任何像素） | 语义反转 → SEP 路径**永远**返回 `extraction-failed`，Kotlin 侧「SEP 优先」三级降级从未生效 |

A+B 的耦合关系值得记录：A 把 `image` 清零成 NULL，于是 B 的 `free(NULL)` 无害，
隐式地为 B 兜了底。只修 A 会让 B 立刻显形（非法 free ART 堆内存）。**必须同修。**

## 2. 证据链

### 2.1 A 的证明（顺序实验）

同一张真实照片、同一份 simplexy，只改字段填写顺序：

```
A) bridge order : after set_defaults -> image=(nil) nx=0 ny=0
A) simplexy_run rc=0 npeaks=0  => ZERO STARS (bug)
B) correct order: image=0x7f5184e4b010 nx=800 ny=526
B) simplexy_run rc=1 npeaks=2063  => stars found
```

`simplexy_set_defaults` 的实现（上游 `util/simplexy.c:151`）：

```c
void simplexy_set_defaults(simplexy_t* s) {
    memset(s, 0, sizeof(simplexy_t));   /* ← 抹掉调用方已填的 image/nx/ny */
    simplexy_fill_in_defaults(s);
}
```

### 2.2 B 的证明

按修复后的顺序跑完提星，进程在 `simplexy_free_contents` 处崩溃：

```
image 800x526
A) ... (略)
B) simplexy_run rc=1 npeaks=2063  => stars found
Segmentation fault (core dumped)
```

上游实现会 `free(s->image)`，而该指针来自 JNI：

```c
float* g = (*env)->GetFloatArrayElements(env, gray, NULL);
s.image = g;                              /* ART 堆，只能由 Release...Elements 归还 */
...
simplexy_free_contents(&s);               /* ← 对 ART 堆 free → 未定义行为 */
```

这解释了「独立 arm64 可执行正常 462 颗、APP 内 0 颗」的历史观测：独立程序用
`malloc` 缓冲区，`free` 合法；APP 内是 ART 堆，行为不可预期。

### 2.3 C 的证明

上游 `simplexy_run` 只在两处返回：`util/simplexy.c:334`（`dmask` 失败，无超阈值像素）
返回 0，`util/simplexy.c:491` 返回 1。所以 **`rc=0` = 失败**，旧条件 `rc != 0` 恰与
真实语义相反。加上 A 使 `npeaks` 恒为 0，旧判据恒真。

## 4. 附带修复

| 项 | 修改 |
|---|---|
| `maxStars` 截断 | 原来按扫描序直接截断（留下图像上半部分），改为按 flux 降序取前 k（`top_k_by_flux`） |
| `thresholdBgMultiple` 参数 | 原来完全被忽略，现在映射到 `simplexy.plim` |
| JNI 数组长度校验 | `n != w*h` 时先 `ReleaseFloatArrayElements` 再返回，原实现直接 return 泄漏 |
| 超时判定 | `run_with_timeout` 返回三态：`RUN_OK/RUN_TIMEOUT/RUN_SPAWN_FAILED`；旧版 `pthread_create` 失败返回 -1，在 `else if (timedout)` 里被当成超时 |
| join 无期限 | 置 `quit_now` 后加 5s 宽限期；仍未退出则 `pthread_detach` 并置 `solve_thread_leaked`，调用方跳过 `solver_free`（否则释放线程正在读的内存 → 段错误）。宁可泄漏一个 solver 也不崩用户手机 |
| `solve_job_t` 位置 | 从栈移到静态 `g_solve_job`：线程若被 detach，栈上 job 会随函数返回失效 |
| `quit_now` 有效性核实 | 读上游 `solver/solver.c` 确认被真实轮询（749/970/1022/1120/1259 行），机制有效，保留 |
| `simplexy_free_contents` | 新增 `release_simplexy()` 只释放 simplexy 自有的 x/y/flux/background/*L 数组，**不动** `image/image_u8` |
| 补丁依赖移除 | 旧桥调用自打补丁的 `simplexy_set_nthreads(1)` 禁用 dsmooth 并行；本次改用上游原版（本就串行），去掉该调用与相关死代码 |

## 7. 对用户报告的重新解释

用户三条反馈现在全部有确定解释：

1. **「原图识别不了，相册拉高对比度就能识别」**——不是对比度问题。SEP 路径恒失败，
   只能回退到 JVM box-blur 提星；两条路径对同一张图的检出数不同，高对比度恰好让
   box-blur 那一路过了阈值。修复后 SEP 路径真正生效，不再依赖这条偶然性。
2. **「部分真机提星 0 颗」**——所有真机都提星 0 颗（C 判据恒真）；之所以看起来
   只有「部分」机型出问题，是因为另一些机型靠 box-blur 回退救回来了。
3. **「离线演示 12 张超过 1 分钟」**——回退路径 + 官方引擎提星 0 颗的双重开销。

## 8. 遗留与后续

- `solve_thread_leaked` 是进程级单标志，依赖「solve 从 JNI 串行进入」这一前提；
  若将来支持并发求解需改为按 solver 实例记录。
- 上游原版 dsmooth 为串行实现，提星速度低于曾打补丁的多线程版本。若将来要恢复并行，
  必须先解决 arm64 正确性（当年 0 颗的真因已查明与并行无关，可重新评估）。
- 官方引擎的 `detectRates` 等路径未做穷尽回归；本次只覆盖 `solve/solvePriors/
  extractStars` 四条导出。
